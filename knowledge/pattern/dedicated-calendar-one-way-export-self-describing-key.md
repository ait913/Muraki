## Context

自アプリのデータ (授業・シフト・予約など) を OS のカレンダー (EventKit / CalendarContract 等) に反映したいとき。
シフトボード型の「アプリ専用カレンダーを作ってそこにだけ書く」方式を採る場合の設計骨格。

## What

**1. 方向を先に 1 本に決める。専用カレンダーは書き出し専用にする。**
自アプリの正典 (サーバ DB) と OS カレンダーの両方を真にすると、同時編集の解決 (LWW / tombstone) が要り、
カレンダー API はたいていバックグラウンド配信を持たない (前面化 diff 前提) のでズレが残る。
「読み込みたい」要求は**別カレンダーを読み込み対象に選ぶ**という独立機能で満たす。
専用カレンダーを読み込み対象から**構造的に除外**すれば「自分が書いたものを自分が読み戻して二重化する」経路が消える。除外は 2 層 (一覧から隠す + 取得時に集合から引く) にする。

**2. 対応表を持たない。識別子を成果物自身に埋める。**
「アプリ側の項目 ⇄ OS 側のイベント」の対応表を UserDefaults / サーバに持つと必ず実体とずれる
(再インストールで飛ぶ / ユーザーが OS 側で 1 件消す / 端末が 2 台になる)。
イベントの `url` のような**自由書き込みができて往復するフィールド**に `myapp://<kind>/<id>/<日付>` を書けば、
毎回カレンダーを読むだけで真の状態が分かる。差分は「読んだ owned 集合 vs 望ましい集合」で純関数にできる。

**3. owned / foreign / 重複 の 3 分割で守る。**
- owned = 自分のスキームの識別子を持つ → create / update / delete の対象。
- foreign = 識別子が無い (ユーザーが手で足した) → **一切触らない**。件数だけ数えて可視化する。
- 同じ識別子が 2 件以上 → 決定的な順序で 1 件を残し残りを消す (過去の不具合の自己修復)。

**4. 「空」と「不明」を区別する。**
取得に失敗した / 前提データ (時間割・アカウント) を一時的に持たない状態を「対象 0 件」と解釈すると、
掃除フェーズが**書き出し済みを全消しする**。API は `hasActiveX: boolean` のような明示フラグを返し、
クライアントは kind ごとに「掃除してよいか」を決める (`prunableKinds`)。取得が throw したら plan を作らず中止する。

**5. 差分判定は「無限チャーン」を潰す形で書く。**
書いた値と読み戻した値が**表現として一致しない**フィールドがあると、毎回 update が走り続ける。典型:
- 終日イベントの終了日 (包含 / 排他の 2 解釈) → **日付に落として比較**する。書くときは両解釈で同じ日になる値 (最終日 23:59:59) を選ぶ。
- 未設定文字列 (`nil` vs `""` vs 空白) → 正規化してから比較。
- 秒未満の誤差 → floor してから比較。

**6. 再作成の暴発条件を明示する。**
カレンダーの識別子は sync-proof でないことが多く (EventKit の `calendarIdentifier` はヘッダ明記)、
ユーザーが OS 側で削除もできる。フォールバックは「id → title 完全一致 → 作成」の 3 段。ただし作成してよいのは:
- 一覧が**空でない** (空 = ソース未ロードの過渡状態。ここで作ると次回に重複する)
- 書き出し実行パスから呼ばれている (一覧構築や読み込みパスからは作らない)
- 同一セッション内で作成に失敗していない
の全部を満たすときだけ。

**7. 書き込みは主スレッドから外す。**
学期ぶん・年間ぶんで数百件になる。Swift なら I/O 境界を `actor` にして、
プラットフォーム型 (`EKEvent` 等) を actor の外へ出さず `Sendable` な値型だけ返す。

## Why

この 7 点はどれも「実装後に踏むと原因が分かりにくい」種類の失敗に対応している:
二重化 (1)、再インストール後の孤児 (2)、ユーザーデータの誤削除 (3)、
一時的な状態での全消し (4)、CPU とネットワークを食い続ける無限 update (5)、
カレンダーが増殖する (6)、UI が固まる (7)。
いずれも「動いているように見える」状態を経由するので、設計段階で条件を言語化しないと出荷される。

## How to apply

- 設計 doc に **owned / foreign の判定規則** と **prunable の決め方の表** を必ず書く (Reviewer はここからテストを書ける)。
- 差分計算・識別子の組み立て・カレンダー解決は**プラットフォーム SDK を import しない純関数**に切り出す。
  I/O 境界 (実 store) はテストできないので、テストできる部分を最大化する。
- 識別子フィールドが本当に往復するか実機確認できないときは、**初回書き込みの直後に読み戻して検証**し、
  失敗したらエラーとして可視化して書き出しを止める (壊れたまま書き続けて重複を量産しない)。
- 展開済み occurrence を個別に書くか、繰り返しルールとして書くかは**方向で決める**。
  一方向なら展開方式が圧倒的に単純 (例外の往復が要らない)。代償は
  「繰り返しバッジが出ない」「窓の外に未来分が出ない」の 2 点だけなので、明示して受容する。
