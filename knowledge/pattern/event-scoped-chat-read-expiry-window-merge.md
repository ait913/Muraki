## Context
bloom のビーコン (集合) 中チャット。会話はビーコン終了 + 24 時間で「読めなくなり、サーバーからも消える」裁定。既存の掃除は 21 時の日次バッチだけで、似た寿命の `beacon_stamps` は実際には最長 48 時間残っていた。一覧の取得は当初 `?after=<id>` の差分で書かれかけた。

## What
1. **期限は読み出しの SQL で判定する** (`closed_at > now - 24h`)。物理削除は engine の 30 秒 tick を 10 分に 1 回 (起動直後は必ず)。日次バッチや「終了時に削除を予約」は、前者は期限を最長 2 倍に延ばし、後者は再起動で予約が消える。読み出しが正確なら掃除の遅れは「見えないまま数分残る」だけになる。
2. **差分取得 (`after`) は削除・ブロック・退出の消去を運ばない。** 「最新 N 件の窓 + 古い方へ `before`」で取り、窓の範囲内で端末にあって応答に無い id を消す。1 催しの会話が数十件なら毎回最新窓で足りる。
3. 窓の合流は 3 つの到着順を 1 本で収める: (a) WS 先着の GET が送信中の行を含む → **端末が作る `client_id`** で送信中の行と同一視 (本文一致は「了解」2 回で取り違える)、(b) POST 応答先着で古い GET が後着 → 「GET 開始後に POST で入った id は消さない」(mutation 世代)、(c) 削除直前に始まった GET が後着 → 墓標。`client_id` は UNIQUE (催し, user, client_id) にして送信の冪等キーも兼ねる。
4. WS は保存後の薄い event を**専用の kind** で。既存の「催しが変わった」kind に相乗りすると、発言ごとに重い派生 (地図の集計) が再計算される。

## Why
期限と掃除を分けると「正確さ」と「ストレージの寿命」が別の仕組みになり、どちらの失敗も他方を壊さない。差分カーソルは追記専用のログでしか正しくなく、削除がある時点で窓の合流が要る。

## How to apply
- 寿命付きの UGC (催し・一時グループ・期限付き共有) を設計する時は、寿命の表に「読み出しの条件」と「物理削除の契機・最長遅延」を別の列で書く。既存の掃除バッチの実際の頻度を `Tick` / cron から確かめてから相乗りを決める。
- 一覧 API に `after` を提案されたら、その資源に削除・可視性の変化 (ブロック・退出) があるかを先に問う。あれば最新窓 + `before`。
- 楽観送信には端末生成の `client_id` を付け、DB の一意制約で冪等にする。合流の挙動仕様に (a)(b)(c) の 3 行を必ず置く。
