## Context

同じ機能を「自分用」と「グループ用」の 2 文脈で出す画面 (カレンダー / 時間割 / タスク一覧 / ダッシュボード)。
最初は片方を作り、後からもう片方をコピーして分岐させる、という育ち方をしがち。

atender では月カレンダーが `PersonalCalendar` と `RoomCalendar` に分かれており、ユーザー (Touri) から
「個人の方で直したレイヤーバグがルーム側に残ってる。そもそもタブ自体の実装も違うのでは」という指摘が出た。

## What

**フォークしている場所を数えると、共通なのは「中身」で、分かれているのは「殻」だった。**

| | 状態 |
|---|---|
| セル描画 (`CalendarMonth`) | **既に共通**。build 14/15/16 のセル修正は両方に効いていた |
| グリッド (`TimetableGrid`) | **既に共通** |
| ScrollView 設定 / 月ヘッダー / FAB / データ取得 / 高さの伝播 / 学期文脈 | **全部フォーク** |

そして**実機に出たバグは全部「殻」側**だった:

- `scrollClipDisabled` の有無 → スクロール中の中身が上のチップに描き出される
- 月ヘッダーが別部品 → `<` `>` がセグメントに重なる
- 片方だけ `available` (利用可能高) を渡していない → 行高が固定値に張り付く
- 片方だけ FAB が残存 (もう片方では長押しに置換済)
- データ取得の文脈が非対称 (UI で選んだ学期 vs 既定学期) → 同じ画面の 2 タブが別の学期を表示

**「共通コンポーネントを作ったから統一されている」は誤り。** 共通なのは葉であって、
バグが宿るのは葉を並べる枠組みの方だった。

## Why

葉 (セル / 行 / タイル) は「引数を受けて描くだけ」なので、最初から共有しやすく、共有されると
修正が自動で両方に効く。一方の殻は「状態を持つ」「非同期を持つ」「ホスト画面に依存する」ため
コピーされやすく、コピーされると**修正が片方にしか効かない**。しかも殻の差分は
スクロール・レイヤー・高さ・読み込みといった**目で見ないと分からない層**に出るので、
ユニットテストが全部緑のまま片側だけ壊れ続ける。

## How to apply

### 1. フォークの棚卸しは「殻の項目」で表を作る

差分表の行を、**中身の見た目でなく殻の属性**で立てる:
スクロールコンテナの設定 / ヘッダー部品 / 浮遊ボタン / データ取得と force フラグ /
サイズの伝播 (`available` 等) / 読み込み・失敗の表現 / 文脈パラメータ (期間・学期・テナント)。
ここに 1 行でも「片方だけ」があれば、それは仕様差か手抜きかを**1 行ずつ裁定する**。

### 2. 殻を 1 個の部品にして、データ源と機能をオプションで注入する

```swift
CalendarScreen(store: store,            // データ源 (ローダを注入した汎用ストア)
               options: .personal,      // 同期バナー / 警告グリフ / 長押し作成 の可否
               available: height,
               originMonth: origin) { ctx in
    PersonalDaySheet(...)               // 文脈固有の子画面は ViewBuilder で注入
} headerAccessory: {
    EmptyView()                         // ルームなら ICS 取り込みボタン
}
```

- **文脈固有の生データは 1 個のジェネリック `Extra` に閉じる**。殻自身は `Extra` を読まず、子 builder に渡すだけ。
  Payload に `personalOccurrences` と `roomEvents` の両方を持たせると、3 つ目の文脈でまた増える。
- **オプションは「データで決まるもの」を含めない**。「出席ドットを出すか」はフラグでなく
  「ローダが `daySummaries` を空で返すか」で決まる。冗長なフラグは 2 箇所に真実を作る。

### 3. 片方だけの機能を落とさないことを「対応表」で証明する

行 = 片方だけが持っていた機能、列 = (行き先 / 維持・移設・保全)。**捨てる行をゼロにする。**
移設したもの (FAB → ヘッダーの accessory 等) は「削除」でなく「移設」と書く。
呼び出し元 0 の孤児は**消さずに保全して報告**する (消すかはプロダクト判断)。

### 4. 逆向きにも 1 個ずつ裁定する

「もう片方だけが持っていた機能を、統一後にこちらでも有効にするか」を全件書く。
`有効 / 無効 + 理由 1 行`。理由が書けないものは、たいてい仕様差でなく手抜きなので有効にする。

### 5. ★ 殻の中で「横にページングする」なら、カード外殻とヘッダーはページャの外に置く

カード面 (背景 + 角丸 + 影) ごと横 `ScrollView` に載せると、**clip 境界がカードの縁と一致して影が左右で切れる**
(atender では実機 FB として 2 回出た)。`scrollClipDisabled` で逃がすと隣ページが枠外に見える。

```
外殻 (bgElevated + Radius + shadow)      ← 静的
  ├ ヘッダー帯 (全ページ共通)             ← 静的
  └ ScrollView(.horizontal, paging)      ← ここだけが滑る
```

副次的に「ヘッダーが揺れない」「ページの自然高がそのまま外殻の高さになる」利点も付く。
横ページング自体の実装形 (窓を広く取って index リセットを書かない) は
`library/swiftui-nested-horizontal-paging-ios26.md` を参照。

### 6. 殻の共通規格は「1 個の modifier」に落とすと再発しない

`scrollClipDisabled` の有無のような 1 行の差は、部品化しない限り必ずまたズレる。
`.atenderPageScroll()` のような**名前の付いた規格**にして、コメントに
「なぜこの組み合わせなのか (どの実機 FB を潰したのか)」を書いておく。
