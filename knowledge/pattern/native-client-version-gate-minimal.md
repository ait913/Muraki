## Context

Web + API + ネイティブアプリ (iOS/Android) を 1 リポジトリで持つ個人〜小規模プロダクトで
「各成果物のバージョンと対応関係を管理したい」と言われたとき。
atender (Web/API 同時デプロイ + TestFlight 配布の SwiftUI アプリ) で 2026-07-17 に採用。

## What

### 1. 管理すべき次元を数える — 大抵 1 次元しかない

要望は「Web × iOS × API の対応表」に見えるが、**成果物ごとに「ズレが residual するか」が非対称**:

| 組み合わせ | ズレるか | 管理要否 |
|---|---|---|
| Web × API | 同一 commit から同時デプロイなら一過性。ズレても **reload で自己修復** | 不要 |
| ネイティブ × API | **ユーザーが更新するまで永続**。端末に無期限に残る | **必要** |

→ 管理対象は「API が受け入れる最小 client build」の **1 次元 = サーバのコード定数 1 個**。
3×3 の表も semver も要らない。**採番は手動のまま。自動化するのは「事実の申告」だけ。**

### 2. 「今やらないと後で不可能」なものだけを先に入れる

これが本パターンの中心。判定基準は **「後から追加した時、既に配った古いビルドに効くか」**:

| 施策 | 後から足せるか | 結論 |
|---|---|---|
| client が全リクエストで版数を名乗る (`X-Atender-Client: ios/<build>`) | **不可**。配布済バイナリにヘッダは後付けできない | **今入れる** |
| 起動時の互換チェック + 更新催促画面 | **不可**。催促 UI を持たないビルドは催促できない | **今入れる** |
| `GET /version` のフィールド追加 | 可 (サーバ側だけ。client の Codable/JSON は未知キーを無視) | 後でよい |
| サーバ定数の値変更 (最小 build の引き上げ) | 可 | 後でよい |
| 版数の自動採番 / CI / tag | 可 | 要るまでやらない |

**旧ビルドを救う方法は存在しない**ことも明記する (User-Agent 等で識別できても、催促 UI がバイナリに無ければ「原因不明で操作不能なアプリ」になるだけ)。それが「今入れる」理由そのもの。

### 3. 2 経路を持つ — 役割が違うので冗長ではない

| 経路 | 役割 | 単独では足りない理由 |
|---|---|---|
| 起動時に `GET /version` → 比較 | **UX**。操作前に催促画面を出す | 起動後に最小 build が上がった長寿命セッションを捕まえられない |
| サーバが **426** を返す | **強制 (権威)**。次のリクエストで必ず止まる | 未ログインで何も叩かないユーザーは気付けない |

client 側は 426 を **status だけで**判定し (401 の扱いと対称)、body を読まない。
→ エラー envelope が壊れていてもゲートは動く (envelope に既知の不具合を抱えるプロジェクトでも導入できる)。

**426 で「サインアウト」させないこと。** 401 と 426 は別物で、token を消すと解除後に再ログインを強いる。

### 4. フェイルオープンを原則にする

判定できない入力は**必ず通す**: ヘッダ無し (Web と旧ビルド) / 形式不正 / `/version` 到達不能 / 版数が非数値。

- 新設 middleware が全ユーザーを巻き込んで落とす余地を消す
- **サーバ定数の初期値は「誰も弾かれない値」(= 実在する最小 build 以下)** にする。ゲート機構は入るが初回は無効同然で、実効化は次に上げるときの意図的な操作になる

### 5. 壊れ得る依存は「壊れても診断に閉じる」位置に置く

commit SHA の露出 (例: Coolify の `SOURCE_COMMIT` ランタイム注入) は環境に依存する。
**ゲート判定を commit に乗せない**:

- commit SHA には順序が無く「これ以上/以下」を表現できない
- 注入が効かないと `"unknown"` になる — 壊れ得る入力にゲートを乗せることになる

→ 判定は **build 番号 (単調増加する整数、client 自身が知っている)**、commit は **診断専用フィールド**。
注入が外れても被害は「`commit: "unknown"` と表示される」だけで、ゲートは完全に動く。

### 6. 定数を「誰も回さないつまみ」にしない

値の上げ方を doc に規則として書く。atender の規則:

- 上げるのは **主要機能が壊れる / データが壊れる**ときだけ。部分的な不具合は対象外 (配布チャネルの更新通知に任せる)
- 上げるときは **修正を含む最初の build 番号**にする
- **「これから配る build >= 定数」を必ず確認** — 逆にすると配った直後に全員が 426 で自滅する

★ ただし**「主要機能が壊れる」の判定は人間の気付きに依存する**。これを機械化するのは契約テストの仕事であり、
**版数管理は「壊れたと気付いた人が定数を上げられる」状態を作るだけで、「壊れたことに気付く」仕組みではない**。
両者を同じ設計 doc に混ぜると「版数を入れたから契約は安全」という誤読を生む。

### 7. ヘッダの形式は最小に留める

`<platform>/<build>` のみ。marketing version や OS 版数を今の形式に詰めない。

理由: **形式の作り込みに now-or-never 性は無い**。追加情報が要るようになったら別ヘッダを additive に足せばよく、
それは「将来ビルドでのみ可能」という点で最初から情報を詰めた場合と何も変わらない。
now-or-never なのは「全リクエストが版数を名乗る」ことだけ。

### 8. 付与点は session/interceptor 1 箇所に集約する

request builder 各所にばら撒かない。iOS なら `URLSessionConfiguration.httpAdditionalHeaders`:

- 1 箇所で `APIClient` も `AuthStore` も将来の呼び出し元も全部カバーできる
- **`httpAdditionalHeaders` は `URLProtocol` スタブから観測できる** (macOS Swift で実測、2026-07-17) ので、既存のスタブハーネスで検証できる
- ★ **テスト用スタブ session も必ず同じファクトリ経由で作らせること** (`APIConfig.makeSession(protocolClasses:)`)。
  テストが自前で `URLSessionConfiguration` を組むとヘッダが付かず、**本番と違う経路を検証する偽陰性**になる

## Why

- 「バージョン管理」の要望は成果物の数だけ次元があるように見えるが、**次元の数を決めるのは成果物の数ではなく「ズレの residual 性」**。自己修復する組み合わせは管理対象にならない
- 版数管理の施策は「今やる/後でやる」を**好みや工数ではなく、配布済バイナリに効くかどうかで機械的に切れる**。この基準を使うと、大抵の施策 (tag/CI/semver/自動採番) は「後でよい」に落ち、残るのは 2 つだけになる
- ゲートは**アプリを使用不能にする最終手段**。だからこそ初期値・フェイルオープン・上げる条件を先に決めておかないと、いずれ過剰 block を生む

## How to apply

新規に「版数対応を管理したい」と言われたら:

1. 成果物ごとに「ズレが residual するか」を書き出す → 管理次元を数える (大抵 1)
2. 施策を「配布済バイナリに後から効くか」で 2 分する → 効かないものだけ今やる
3. サーバ定数 1 個 + `GET /version` + client ヘッダ + 426 + 起動時チェック、で組む
4. フェイルオープンを全経路に適用し、定数の初期値は「誰も弾かれない値」にする
5. 定数の上げ方の規則と、「これは drift 検出ではない」ことを doc に明記する
6. 本番でゲートの生死を確認できるプローブを用意する (例: 実在しない `ios/0` を送ると 426、送らないと 401 → **成功・失敗・未デプロイで返り値が全て異なる**)
