## Context

rotate-on-use の refresh トークン (使用ごとに旧トークンを DELETE) を、前景 + 背景
headless isolate + WS の 3 経路から呼んでいたモバイルアプリで、17 日間 100% 401 の
恒久ロックアウトが起きた。設計し直しの過程で固まった型。

## What

4 点セットで設計する。1 つでも欠けると同じ事故に戻る。

1. **単一所有者**: refresh を実行し結果を保存できるコンポーネントを**プロセス内で 1 つ**に
   決める。他の実行主体 (背景 isolate 等) は「トークンが要る仕事」自体を持たせず、
   仕事をローカル DB に積んで所有者に送らせる。**「読み取り専用トークンストア」は多くの場合
   死荷重** — access をディスクに置かない規約と、refresh の唯一の用途が rotation で
   あることが両立すると、読み取れる値に使い道が無くなる。
2. **AuthExpired を単一の確定イベントにする**: refresh の結果を `ok / authExpired /
   transient` の 3 値で返し、**認証層の失敗時に呼び出し側が勝手にトークンを消さない**
   (「refresh 失敗 → clearTokens()」は他経路が保存した有効トークンを消す最悪手)。効果
   (トークン破棄・キャッシュユーザー破棄・WS 停止・サインイン画面へ) の適用点も 1 箇所に集約。
   ネットワーク断・5xx・タイムアウトは必ず transient 側に振る。**認証状態の失効は同期的に
   確定させ (state を先に signed-out にして router を決める)、Keychain 削除等の後始末は
   失敗を捕捉して再試行する** — 後始末の失敗で state 更新に届かないと「user 有り・token 無し」
   を自分で再生産する。加えて**発火抑制・進行中応答の破棄・後始末の中止判定は「認証世代
   (int カウンタ、サインイン成功で +1)」1 つで行う**: DI コンテナが保持する API クライアントは
   再サインイン後も同一インスタンスなので「インスタンス生涯 1 回」のフラグでは 2 回目の失効が
   redirect せず、遅延した me/refresh 応答が消したはずの user を復活させる。
3. **失効例外を業務例外の継承外に置く**: `AuthExpiredException` を通常の
   `ApiException` の**サブクラスにしない**と、既存の `on ApiException catch (_) { /* オフライン扱い */ }`
   が自動的に素通しする。既存の握りつぶし箇所を 1 つずつ書き換えずに済み、書き換え漏れも起きない。
   自動リトライ機構 (Riverpod 3 の既定 10 回指数バックオフ等) からもこの型で除外する。

4. **クライアント側を直さずサーバーの「猶予窓」で競合を救おうとしない**。直前ハッシュを N 秒
   受理する緩和は、**2 経路競合を収束させない**: A/B が R0 を読む → A の通常更新で current=R1 →
   B の猶予更新で current=R2 → B が R2 を保存 → 遅延した A が R1 を上書き保存 → R1 は current
   でも prev でもなく死ぬ。しかも使用済みトークンを N 秒再利用できる分、[RFC 9700 §4.14.2]
   (https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14.2) が求める再利用検知 (family 失効)
   や送信者制約を入れていない実装では replay 耐性だけ下がる。sha256 しか保存しない設計では
   Okta 式の「猶予内は同じトークンを返す」も実装できない (平文保持が要る)。**緩和策は採る前に
   最悪インターリーブを 1 本書き下す**。単一所有者化が済めば競合自体が消え、残る「応答消失」は
   AuthExpired → 再サインインで回復する (死なない)。

観測: 401 のアクセスログには**理由コード** (`no_bearer` / `bad_token` / `access_expired` /
`refresh_unknown` / `refresh_expired`) と、失効 access の**未検証 sub** を出す。理由なしの
401 ログは「誰がなぜ弾かれたか」を答えられず、恒久ロックアウトを何週間も見逃す。

## Why

- isolate 間ロックを探すのは「書き込み経路が複数ある」前提を温存する発想。経路を 1 本に
  できないかを先に疑うと、ロックも grace も要らない部分が大半になる。
- rotate-on-use は「最後に成功した 1 本だけが生きる」設計なので、**2 つの保存先が同じ鍵を
  共有した瞬間に相互破壊が確定する**。競合確率の問題ではなく構造の問題。
- 認証失効は「エラー」でなく「状態遷移」。例外として各所で解釈させると、解釈が 1 箇所でも
  ずれた所 (握りつぶし・自動リトライ) で無限ループか無反応になる。

## How to apply

- 設計 doc に「トークンを保存できるクラスの全列挙」を書く。2 つ以上あったら設計をやり直す。
- 背景実行が必要とする API 呼び出しは、まず「ローカルに積んで前景で送る」で足りるか検討し、
  足りない場合だけ専用スコープトークン等を別設計にする (代償は doc に明記)。
- OS のセキュアストレージのオプション (iOS Keychain の `kSecAttrAccessible` 等) を変える時は、
  そのオプションが**読み取りクエリの一致条件に入っていないか**プラグイン実装を読む。入っている
  場合は「旧オプションで読む → 削除 → 新オプションで書く」の移行を設計に書く (書かないと
  既存ユーザー全員のトークンが不可視になり全員再サインインになる)。
