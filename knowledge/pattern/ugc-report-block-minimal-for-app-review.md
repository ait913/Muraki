## Context

App Store 審査 (Guideline 1.2 User-Generated Content) は UGC を持つアプリに (1) 不適切コンテンツのフィルタ手段 (2) 通報と timely な対応 (3) 迷惑ユーザーのブロック (4) 連絡先の掲示 を要求する。「24 時間以内」「EULA 明記」は現行原文に無い (二次情報)。役割なし・対等モデルの小規模グループ SNS (bloom: 3〜8 人、リーダー無し) で、追放機能や運営ダッシュボードを作らずにこれを満たす必要があった。

## What

1. **ブロックはユーザーペア単位・グループ非依存・双方向不可視**。`blocks(blocker_id, blocked_id)` 1 表。SQL 述語 `blockedPair(a,b)` を store に 1 箇所だけ定義し、投稿一覧・メディア配信・アバター・RT fan-out・接近判定・提案成立の各クエリに埋め込む。アプリ側では一切フィルタしない (サーバーが唯一の認可関門)
2. **切るのは「人に由来するもの」だけ**: 投稿・アバター・位置ピン・到着時刻・接近通知・提案の同席・相手起点の push。**グループ状態 (ビーコンの存在、誰が来るか、匿名集計の地図) は残す**。小規模グループで集合の存在まで隠すと主機能が壊れる
3. **通報は投稿単位・固定理由 + 任意コメント**。1 件目で通報者本人だけ非表示 (個人の判断)、未解決の distinct 通報者が閾値 (グループ上限 8 人なら 2) に達したら全員から自動非表示 (`posts.hidden_at`) + 投稿者本人にだけ「運営確認中」。これで (1) フィルタ と (2) timely を人間キュー無しで機械的に担保する
4. **証跡は投稿削除後も残す**: `post_reports.post_id / author_id / reporter_id` は `ON DELETE SET NULL`。`resolved_at` で運営の対応済みを記録し、閾値カウントは未解決分だけ数える (復帰後の再通報が即再非表示にならない)
5. **運営対応は psql 手順書** (確認 / 削除 / 復帰 / 除名)。除名はアプリ機能にせず、退出処理と同じ後始末を SQL で書く。検知は構造化ログ (`post_auto_hidden`) の grep
6. **同意は端末 kv 1 回だけ** (OK 1 タップ + 規約リンク)。サーバー列は要件外
7. **連絡先はプロフィール系シートに 3 行** (規約 / プライバシー / mailto)。OS 連携は既存ブリッジで
8. 通報の動線は「⋯ → 理由 (5 行を直置き) → 確認」の 3 タップ。「通報する → 理由」の 2 段シートにすると 4 タップになる

## Why

- ペア単位にすると退出・再参加・複数グループ共有で状態が漏れない。グループ単位だと「別グループでは見える」穴が残る
- 片方向ミュートは 1.2(3) の趣旨 (加害者から被害者を遮断) を満たさない。一方でグループ状態まで隠すと 3〜8 人では機能が成立しないので、境界を「人由来 / グループ由来」で引く
- 閾値の自動非表示は「運営が寝ている間」の timely response を代替する。閾値 1 だと 1 人の嫌がらせ通報で誰でも消せる、3 以上だと小規模グループで届かない
- 証跡を SET NULL で残すと、運営が後から「消えた投稿に何件通報があったか」を読める。CASCADE だと自己削除で通報が蒸発する

## How to apply

- 設計時に「ブロックで見えなくなるもの」の表を **経路ごと (REST / WS fan-out / snapshot / push / 集計) に 1 行ずつ** 書く。fan-out は送信側 (`PosFanout`) と snapshot 側 (`GroupRTState`) の両方にフィルタが要る
- push の遮断は `notifyFrom(actor, recipients, n)` のような 1 ラッパーに寄せ、`grep "s.notify("` で全呼び出しを列挙してから置換対象を決める
- Reviewer には「第三者には影響しない」「解除で戻る」の負のコントロールを必ず組ませる (ブロック効果だけ検証すると過剰フィルタを見逃す)
- 審査回答文には「通報 → 通報者に即非表示、N 人で全員非表示、運営確認」の仕組みを 2 文で書く。録画には通報 → ブロック → 相手の投稿が消える、の 1 動線を入れる
