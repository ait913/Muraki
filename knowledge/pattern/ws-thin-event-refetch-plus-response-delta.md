## Context

リアルタイム共有アプリで「ホストが操作したらメンバーの画面が即動く」を作るとき、
WS で何を配るかの選択肢は 3 つある: (a) 変更後の値を全部配る (b) 差分を配る
(c) 「変わった」だけ配って受け側が REST で取り直す。

omatase (Go の WS 1 本 + REST) で、**サーバーが「メンバーごとに違う導出値」を返している**
状況でこれを決めた。room は event 単位の一層で、hub はメンバーごとに違う payload を配れない。

## What

**変更の種類で 2 つに割る。**

| 種類                                             | 配るもの                                        | 受け側                       |
| ------------------------------------------------ | ----------------------------------------------- | ---------------------------- |
| **構造の変更** (親子関係・対象範囲・状態遷移)    | `event_changed { reason, ...ids, at }` の**薄い通知** | REST の snapshot を 1 回引き直す |
| **高頻度の個人応答** (チェック / 完了 / いいね)  | **差分** (`{ target_id, member_id, state:"on"|"off" }`) | 手元の配列を足し引きするだけ |

### 薄い通知側の規約

- **受け側は `reason` で分岐しない。** どの reason でも同じ 1 本の再取得に落とす。
  そうしておけば**未知の reason を後から足しても旧クライアントが壊れない** (前方互換)
- `reason` / 付随 ID はログと将来の細分化のためだけに載せる
- 再取得は **debounce (100-200ms) + ジッタ (0-250ms) + in-flight 1 本 + dirty フラグ**で畳む。
  ジッタは「ホストの 1 操作で全員が同時に GET する」を散らすため
- 再取得の契機は WS 通知だけではない: **接続確立 / 再接続 / 前景復帰 / 時刻境界**も同じ 1 本に入れる

### 差分側の規約

- 差分にするのは「payload が snapshot と別形で、かつ小さく、かつ回数が多い」ものだけ
- 逆に「全置換 API の結果」(項目リスト・対象メンバー) は**差分の形が snapshot とほぼ同じ**になるので、
  差分を作ると snapshot の二重実装になる → 薄い通知側に入れる
- 適用は**純関数 1 個**にして共有する (`applyResponse(state, data) => state`)。
  クライアントが 2 種 (RN + Web) あっても実装は 1 個

## Why

- **導出をクライアントに複製しない。** 「今どれが current か」はサーバーがメンバーごとに計算している。
  生値 (override) を配って各自に計算させると、Go と TS で導出が 2 実装になり、
  ずれたときの症状が「人によって違うものが表示される」= 最も再現しにくい形になる
- **薄い通知は fan-out が均一。** メンバーごとに違う payload を作る必要がなく、hub は
  「room に配るだけの口」でいられる (認可も導出も REST 側に残る)
- **差分を高頻度側だけに限ると、再取得の嵐を防ぎつつ実装量が増えない。**
  チェック 1 個ごとに全員が snapshot を引くと、項目数 × 人数のリクエストになる
- 「追加のみ」の互換規約 (type 追加 / フィールド追加は安全、削除・意味変更は禁止) と組み合わせると、
  **WS に version を載せずに** 新しい通知を導入できる

## How to apply

1. 変更を起こす REST ハンドラを列挙し、**保存成功後に**どちらの type を配るか表にする
   (保存失敗時は配らない。配信失敗はログのみ)
2. 「構造」に入れたものは、受け側の再描画範囲を表に書く (どの画面が何を引き直すか)
3. 再取得が壊してはいけないものを明記する: **接続由来の状態 (presence)** /
   **snapshot に含まれない履歴 (チャット)** / **送信中の楽観更新**。
   これを書かないと「再取得のたびにオンライン表示が消える / 押した直後に巻き戻る」が出る
4. 時刻で自動的に変わる導出値があるなら、**次の境界時刻を計算して 1 点狙い撃ちで再取得**する
   (ポーリングにしない = 「リアルタイムは WS 1 本」の規約に触れない)
