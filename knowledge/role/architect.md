# Architect の職業的習慣ノート

召集されたら最初に読む。**過去の自分 (歴代 Architect) が実際に踏んだ穴**から蒸留した現役の習慣 (20 本以内を維持)。新しく踏んだら自分で追記・置換し、古びたら捨てる (INDEX 対象外、再生成不要)。2026-07-31 に Opus 5 移行で全面圧縮 (原本: ai-audit/archive/20260731-muraki/role/architect.md)。

1. **横断的変更 (母数・型・命名規約) では、影響を受ける既存テストを grep で機械的に洗い出してから移行リストを書く。** 目視列挙の漏れが初回実装 14 件全滅を生んだ (sessions/2026-06-11)。**一覧に項目を足す変更 (slash の項目・`EVENT_KINDS`・MCP ツール) では、件数だけでなく「絞り込みの文字」「末尾 N 件 (`slice(-N)`)」で照合しているテストも grep する** — wasawasa 3c で slash に「データベース」を足すと「タ」→ task だけ、のテストが「タ」を含むラベルで割れ、`EVENT_KINDS.slice(-8)` と MCP の `tools.slice(-9)` は末尾に足した瞬間に別物を指す (2026-10-07)。**出力の既定形式を変える変更 (通知本文を文字 → Block Kit 等) は、機能のテストファイルでなく「既定経路の出力文字列」で grep する** — wasawasa の既定文面 (`[デプロイ完了]` 等) の完全一致は p2-notify だけでなく smoke・gate-fixes-alt・p3a・E2E に散っていた。カスタム経路を使うテスト (変わらない) も「変えない」行として根拠つきで表に載せる (2026-10-07)
2. **導出値の手計算を doc に書かず、生成規則だけを書く。ただし「機械的に取れる規則」は対象全件で走らせてから書く** — 1 例で効く規則は 1 例の規則。規則が実在しないなら設計が与える定数の列に置き、Developer に再導出させない (gotcha/design-doc-derived-counts-vs-generative-rule.md, 2026-07-30)。**Reviewer 用に具体値 (色 hex・座標列) を doc に書くよう求められたら、規則を scratchpad のスクリプトで実走して得た値だけを書く** — 色相の手計算で 130.5° と書きかけ、実走で 134.9° だった (2026-09-18, bloom M2)。**実走も測り方で嘘になる**: 画像から色を採るとき領域全体の平均・円平均・ヒストグラム最頻は肌や小物が混ざる (ネイビーのケープが「hue 6°」と出た)。対象部位のパッチ中央値を狙って採り、値を書く前に元画像でその部位を目視する (2026-09-24, bloom キャラ v2)
3. **契約を明記する: コンポーネントの公開 prop 契約、型付き言語では DTO の Optional 性・enum・public API・init まで。** 欠落すると Reviewer が推測して偽陰性になる (gotcha/design-must-specify-component-prop-contract-for-render-tests.md, gotcha/design-doc-must-specify-swift-type-signatures.md)。**既存の 1 クラスから機能を切り出して別クラスに分離する設計では、切り出す機能が OS 側で「1 プロセスに 1 個しか持てない」役割 (delegate 登録・シングルトン) を伴っていないか確認し、伴うなら元クラスの型宣言 (conformance) からも明示的に外し、新クラスの登録箇所 (`AppDelegate` 起動時の 1 行等) まで書く** — 型シグネチャの削り忘れは 2 クラスが同じ delegate を取り合う実装不能な契約になる (2026-08-21, bloom: LocationBridge→NotifBridge 分離で `UNUserNotificationCenterDelegate` の帰属先を書き忘れかけた)
4. **要望を縮小した設計を出さない。** 達成可能な軸を全部列挙してから、諦める軸を 1 つに絞る。両立不能は数値で証明してエスカレーションに書く (sessions/2026-06-02, 2026-07-16)
5. **並列 N 設計ではスコープ境界 (どのファイル・ディレクトリがどちら専属か) を各 doc の冒頭に明記する** (sessions/2026-06-11)
6. **ブリーフ・Researcher の実測/数値/件数/ファイル名/理由づけは、自分の設計条件で解き直す。** 実測は「その条件で実走した」でしかない (`.git` の有無・linker・TZ で反転する)。「壊れるテスト N 件」は仮想設計への予測で設計判断で減らせる。数値は「測った」のか「割った」のか。結論が正しくても理由が偽なら理由を立て直す (2026-07-16〜30)。**ブリーフの「契機 X は現行どおり」は、その契機の呼び出し元を grep して実発火頻度を数えてから受ける** — bloom E2E Phase A で「drain 後 flush (現行どおり)」を残すと、drain が TrackEvent ごと (≈3 秒) に走っていて「5 分バッチ」の要件と矛盾していた (2026-10-03)。**ブリーフの「複数ヒットしたら」型の異常系は、先に unique index / 制約を schema で grep する** — wasawasa の「build_number が複数ヒット」は部分 unique index で起き得ず、本当に曖昧になるのは制約の無い server_commit 接頭辞の方だった。**既存 API が返さない出力 (`changes` 等) を MCP に足す要望は、既存サービス関数の戻り値型を確認し、tx 本体の切り出しを設計に書く** (二重実装の回避。2026-10-05)。**ライブラリの「冪等」「無損失」は研究のサンプルでなく手元の実コーパス (Muraki の md 数百本) で回してから正典の前提にする** — Tiptap の md 往復は研究の 2 本では冪等、実文書 9 本中 3 本で回すたびに壊れ続けた。ブリーフの上限値 (1 MB) も最悪形で測ると 2 乗の parse で数十秒になった (2026-10-05, wasawasa 3b)。**「往復する」の実測は、どの経路 (ブラウザの DOM あり / サーバーの DOM なし) で測ったかを確かめ、正典の書き込み経路で測り直す** — 表のセルの `<br>` は研究 (ブラウザ) で往復したが、サーバーの正規化はエスケープして保存しており、既存の本番バグだった (2026-10-07, wasawasa (4))。**目印を足す符号化 (区切り行のハイフン数 = 列幅) は、既定の出力が偶然その目印を満たす率を実コーパスで数えてから判定を決める** (合計 100 だけだと 1534 表中 12 を誤読)
7. **検証を設計に入れたら「この検証が緑で、かつ本番が落ちる状態はあり得るか」を自問し、「壊せば赤くなる」と書いたらその壊し方を自分で 1 回実行して赤を確認する。** プローブは成功/失敗で返り値が違うか、経路上の中間 proxy が応答を書き換えないか、危険側・無害側の両方で実走する (2026-07-16, omatase・nwasabi-hp)。**「設定行を外す → 赤」型の負のコントロールは、その設定の既定値を先に確かめる** — mermaid の `securityLevel` は既定が `strict` で、ブリーフどおり「外す」と緑のまま (負のコントロールが成立しない)。壊し方は「危険側の値にする」(`'loose'`) で書いた (2026-10-05, wasawasa コードブロック)。**拡張・プラグインの並びを変える設計は、出力 (正規形) の比較だけでなく入力 (キー操作の優先順) も実走する** — 正規形はコーパス 669 本で不変だったが、Tab の行き先が位置で変わっていた
8. **IA (ホーム構造・タブ・画面分割) は挙動仕様と別物として先に裁定を取る。** 企画書の節順を主従と読んで地図主役の R0、参照アプリ名 (「Zenly のような UI」) を質感でなく骨格の指定と読んで 1 画面地図ホームの R1 を書き、2 回連続で全面組み直しになった (骨格が違っても挙動仕様の中身はほぼ生き残る = IA だけ先に安く確定できた)。参照アプリの言及は「質感 (部品・遊び)」か「構造 (画面構成)」かを切り分けて確認し、IA は ASCII 4 画面級のラフ 2 案で本人に選ばせてから挙動仕様を書く (2026-08-19/20, bloom)。**承認済みモックでも「表示に使っている識別子」と「色 token のコントラスト」は正典で検算する** — wasawasa m1 は Release を client 版で名乗っていたが PRODUCT の例表では名前 ≠ 版 (`2.1` = client 2.0.2) で、名前列を足す逸脱が要った。入力枠・pill の色は 4 つが WCAG 未達で、実測で置換した (2026-10-02)
9. **「相手側の設定で回避する案」より「自分側を仕様に頑健にする案」を採り、前者は賭けている前提つきで不採用案に残す。** base image が docroot に置いている物も数える — `COPY` は既存ファイルを消さない (2026-07-16, omatase)
10. **削除リストはワイルドカードのまま書き写さず、1 ファイルずつ import 元を grep して確定リストに展開する。** 孤児化するファイルは、原因が自分の設計なら報告項目に (プロダクト判断)、既に下りている裁定なら実行として設計で決める (2026-07-16/29, atender)
11. **変更対象は file でなくキー文字列で grep し、宣言サイトの数と実効値 (外側が勝つ modifier / 同一キーの重複宣言) を確定してから書く。** 「N 行だけ」「変更は N つだけ」という数え上げの断言は、重複・節またぎの被りで即座に嘘になる — doc 完成時に「触る行」の側から引き直す (2026-07-17, atender)。**UX doc の閾値をサーバー側 doc の擬似コード/SQL が再掲している構成 (phase0/phase1 のような分冊) では grep を両方の doc に必ず及ぼす** — 片方だけ直すと挙動仕様と実装契約が乖離し、Reviewer もどちらが正か判定できなくなる (2026-08-21, bloom: P1(a) の人数閾値が phase0 §10-4 と phase1 SV5 擬似コードの 2 箇所に重複していた)
12. **自前部品→標準部品の置換では、「自前が明示的に渡していた属性 × 標準が暗黙に引く供給元 (asset catalog / build setting / system default)」の表を作り、供給元の実値を実測する。** 死に資産は消費者ゼロだから腐ったまま生き延び、標準化がその最初の消費者になる。先に「この自前部品が満たしている制約は何か」を言語化してから置換する (2026-07-17, atender)
13. **フェーズ表は節単位で割らない。削除対象は「最後の本番参照が消えるフェーズ」でしか消せず、その参照は別フェーズの節にいる。** シェル (nav/tab bar/余白) を変える設計では、着手前に「全画面が持つはずの構造」を grep で数え、例外の 1 画面を先に見つける (2026-07-17, atender)
14. **「additive」はフィールド追加と enum 値追加で別問題。** enum 追加は旧クライアントの未知値フォールバック経路に落ちて表示退行になる — 旧クライアントの扱いを実装で確認してから additive を名乗る。代表値の種類を増やすのでなく、潰す前の内訳を additive に足して既存値は据え置く (2026-07-29, atender)
15. **時刻依存の挙動仕様は #番号ごとに危険窓の標本時刻を書く。** 日付だけの標本を残すと Reviewer が無害な正午を選び、最も危険な窓が唯一の無検出窓になる。1 箇所で言語化した危険は同類型の全項目に伝播させる (2026-07-17, atender)
16. **「スコープ外」と切った既存コンポーネントに自分の設計の出力が流れ込むなら、そのパイプラインの暦・単位・丸め規則は自分の仕様の一部 (in-scope に昇格)。** スコープ表に「例外的に触る」の行で明示する (2026-07-29, atender)
17. **競合の緩和策 (猶予窓・リトライ・冪等キー) を採る前に、最悪インターリーブを 1 本書き下して収束を確かめる。** 「窓を N 秒開ける」類は多くの場合、競合を遅らせるだけで消さない上に安全性 (replay 耐性等) を下げる — 競合を生む構造 (書き込み経路が複数ある) を先に潰せば緩和策自体が不要になる (2026-09-08, bloom: refresh ローテーション猶予窓を設計に入れかけ、A/B の 5 手トレースで「どちらのトークンでもない状態」に落ちると判明して撤回)。**不変条件を書いたら、それを成立させる state / action / スコープが契約表に載っているか自己確認する。** 「持ち越す」「壊すな」はどのスコープで成り立つか、識別子が変わったとき誰が捨てるかまで書く — 判定材料が揃っている場所 (state 遷移関数) に置く。載っていない不変条件は実装不能で Reviewer は黙って落とす。**終了・ガード条件 (「N 以下なら閉じる」等) は、初期状態がその条件を満たして即発火しないかを状態機械の全遷移入口で自問する** — 「承諾者 ≤1 で自動終了」が作成直後 (発起人 1 人) にも真で、即時 active ビーコンが最初の tick で閉じる仕様バグを書いた (2026-07-30 omatase / 2026-08-20 bloom SV4(d))。**楽観ロック (revision) のリソースに画面の書き込み経路を足す時は、同じリソースを開いて自動保存しているクライアントの revision を誰が進めるかを書く** — wasawasa (2) でツリーからの「名前を変更」を GET + PATCH で書きかけ、開いているエディタの次の保存が偽の 409 になると気付いた。開いているページはエディタの保存経路に渡す窓口 (context) を設計に入れた (2026-10-05)。**ローテーションする秘密 (refresh token 等) を別の場所へ写す設計では、写す前に「新しい rotation を止める → 進行中の rotation が保存まで終わるのを待つ」を書き、写した後の照合と状態の確定は同じ直列ジョブに置く。写し先の上書き・削除は操作 ID 条件付きにし、世代を見ない無条件書き込みを作らない** — bloom の login-as 退避で、通信中の refresh と退避が競合して退避 token が失効する穴を Codex に High で指摘された (2026-10-07)。**一覧の「再取得」と自分の送信・削除の応答が交差する設計は、id の upsert・tombstone・mutation 世代で合流規則を書き、到着順 3 通り (WS 先着 / 応答先着 / 変更前 GET の後着) を挙動仕様に並べる**。debounce は連続イベントで飢餓になるので、間引きは固定期限 (最小間隔) で書く
18. **外部ストアへの差分同期では「等しいかの判定関数」を独立した挙動仕様にする** (write→read で bit 一致しない表現は正規化規則を表で)。**空配列は「本当に 0 件」と「まだ分からない」を型で区別する** — 区別しないと掃除ロジックが全消しする (2026-07-29, atender)。**外部ストアの「書き込み時オプション」(iOS Keychain の `kSecAttrAccessible` 等) を変える設計では、そのオプションがライブラリの読み取りクエリの一致条件にも入っていないかを実装 (pub-cache の Swift/Kotlin まで) を開いて確認する** — 入っている場合、オプション変更は既存データの不可視化であり、「旧で読む→削除→新で書く」移行を書かないと全ユーザーのデータが消えたのと同じになる (2026-09-08, bloom: `flutter_secure_storage` の `baseQuery` が read/containsKey にも accessible を積んでいた)。**端末→サーバー同期の識別子は「別端末・再インストール・別アカウントでも一意か」「公開値から総当たりできないか」の 2 問を通す** — 端末ローカル AUTOINCREMENT を全端末共通 ID にし、鍵なしハッシュで blob_id を作って Codex に NO-GO を食らった。鍵だけユーザー別にしても端末共通 DB の元データはアカウントをまたぐ (2026-10-03, bloom E2E Phase A R1)
19. **「A を止める」ガードは、その振る舞いが通る経路 (保存 / 中継 / 新規接続 / クライアント自主停止) を全部数え、主張を達成できる範囲まで縮めて残る窓と閉じる主体を明記する。** best-effort write の失敗時挙動は書き手の重要度でなく「失敗したまま応答したら読む側が誤解するか」で決める (2026-07-30, omatase)
20. **裁定・正典の語 (「gap で分ける」等) は参照された正典の実物を開いて語義を確定してから実装語に翻訳する。** 字面の実装が、裁定が消せと言ったものを別名で再導入していないか自問する。「現状」に依存する記述は doc 完成時点の main で再確認する — リポジトリは設計中も動く (2026-07-17/30, atender)。**裁定の UI 規則は既存の既定値と合成してから受ける** — bloom outbox で「位置が未解決なら場所行を出さず投稿後に付く」を字面どおり書くと、場所トグルの既定 OFF (V4) と合わさって本人が ON にできず「投稿後に付く」が空文になった。解決を速い段 (fix) と遅い段 (逆ジオ) に割って両立させた。要望の文言 (通知の絵文字等) も DESIGN.md の禁止事項を grep して、衝突すれば正典側の例外追記を置換リストに入れる (2026-10-08)
21. **UX 側で「サーバーが既に持っている値を画面に出す」だけに見える要望でも、その値が現行 API レスポンスの DTO に含まれているかを grep で確認する。** 含まれていなければ「表示だけの変更」ではなく DTO 拡張が要る — 既存の共通型 (例: `Member`) を膨らませず、その文脈だけの派生型 (例: `AcceptedMember = Member & {arrived_at}`) を切って他の利用箇所を汚さない。値の更新をリアルタイムで見せたい場合、新しい配信経路を作る前に既存の汎用イベント (「変わったから REST 再取得しろ」の合図) で足りないか先に確認する (2026-08-21, bloom: 集合モードの承諾者ピン強調 + 残距離で `Beacon.accepted` に `arrived_at` が無いことに気付き、既存 `event{beacon_update}` を再利用した)
22. **外部リンク・URL を開く/送る系の新規 UI (共有ボタン等) を設計する前に、doc 内で「OS 連携はどこに寄せる方針か」を grep する。** 一見「軽い util パッケージ (`url_launcher` 等) を 1 個足すだけ」に見える実装でも、既存方針 (例: 「OS 連携はネイティブブリッジ 1 箇所に集約、util パッケージは入れない」) と矛盾する提案を無自覚に書きかけた — grep 1 発で既存の禁止事項に気付き、ブリッジに新 method を足す代替に直した。参照デザイン (他社アプリのスクショ) に引きずられて実装手段まで真似しない — 真似るのは見た目、実装は自プロジェクトの既存方針に従わせる (2026-08-21, bloom: S13 の「LINE で送る」で `url_launcher` を書きかけ、`SystemBridge.openURL()` に差し替えた)。**「パッケージか自前ブリッジか」を engine の非公開クラス (`FlutterSceneDelegate` 等) が該当メソッドを実装しているかで決めるときは、ヘッダーに無くても `nm -U Flutter.framework/Flutter | grep '\[Class method:\]'` で実装の有無を確定してから `override` を書く** — Codex はコンパイルできないので「override が通るか」を doc 側で潰す (2026-09-22, bloom: Universal Link を app_links でなく SceneDelegate override に置いた)
23. **「既存の読み取り経路に自動で乗る」と Researcher が言ったら、(a) 読み取りが行から導出している値 (例: `periodIndex = meeting.start + offset`) が新しい行でも正しいか、(b) クライアント側で「パターン展開」している画面 (occurrence を読まずに週パターンから描く月カレンダー等) が無いか、を経路ごとに 1 行ずつ表にしてから書く。** 「date 範囲フィルタだけ」は行が結果集合に入る条件でしかなく、値の正しさと、そもそも occurrence を読まない画面の存在は別問題。atender build 18 では 8 経路のうち 2 経路 (`periodIndex` 導出 2 箇所 / 個人カレンダーの `MeetingExpansion`) が自動反映されず、表を作らなければ「自動反映」と書いて出荷していた (2026-09-08, atender)
24. **「○○表示中だけ動く」を規定する前に、その画面の可視性がコード上どこで決まるかを grep する (`IndexedStack` / `StatefulShellRoute.indexedStack` / `Offstage`)。** タブ画面は mount され続けるので、既存コードの `initState`/`dispose` = 表示中、という前提は既に嘘になっていることがある (bloom M-S9 の 5 秒ポーリングは「S3 表示中のみ」と書かれていたが、一度地図タブを開くと他タブでも回り続けていた)。可視性の供給源 (shell の index / route) を契約に書き、電池・GPS に効く「表示中だけ」は Swift 側のライフサイクルフックにもバックストップを置く (2026-09-19, bloom M3)。**別系統の一次入力 (Doppler の speed/course 等) を持つ実機を、入力が無いモックの式 (位置差分) で写経しない** — モックの式は「その入力しか無い環境」の近似で、実機では精度で負ける (1 Hz・12 m 誤差の差分は 8.5 m/s の誤差)
25. **2 つの操作を 1 つに統合する設計では、統合前に「別々だったから取れていた順序」を開発フロー表で洗い出し、統合後も取れるか確認する。** wasawasa で「反映 (バージョン切替)」と「サーバーデプロイ」を 1 ボタンに統合したとき、ストア審査の前にサーバーだけ先に上げる (切替は公開時) 順序が統合で消えかけ、`server_only` モードを足した。統合した操作の片方が外部で失敗しうるなら、内部の確定 (台帳の切替) は外部の成功時に回し、失敗の不変条件を「何も変わらない」にする (2026-10-03, wasawasa Phase 2)
26. **「実行時に接続先 / テナントを切り替える」設計では、container (DI のルート) を作り直す前に、プロセスに 1 つしか無いもの (`GlobalKey`・MethodChannel / EventChannel のハンドラ・static コールバック・保存名) を grep で全数挙げ、旧ツリーのアンマウント → 1 フレーム待ち → 新ツリーのマウントの順を状態機械に書く。** 新旧が同じフレームに共存すると `GlobalKey` は旧 Element を新 Navigator に付け替え、EventChannel は旧の cancel で新の購読を殺し、旧 `dispose` の `onLink = null` が新のハンドラを消す。保存名 (DB ファイル・Keychain キー) は「既定の接続先は既存名のまま (移行 0 行)、新しい接続先だけ改名可能でない識別子 (host) 由来の名前」にすると本番の読み取り経路に触れずに済む (2026-10-04, bloom env-picker)
27. **番号・ID の「系列」を増やす設計 (外部サービスの採番を受ける等) では、一意制約だけでなく「その番号の大小で導出していたもの」(最新の選定・一覧の並び・下限による締め出し・カウンタの自動繰り上げ) を grep で全数表にしてから書く。** 一意制約を分けるだけだと「今入れるビルド = 番号最大」が系列をまたいで新旧逆転し、手動登録の「n ≥ next なら next = n + 1」でカウンタが外部の帯に引っ張られる。衝突が DB でなく外部 (配布先が同じ版 + 番号を上書き) で起きることもあるので、外部側の同一性の規則も表に入れる (2026-10-05, wasawasa 3a)
29. **「既定 / 選択 ID を別の実体に切り替える」設計 (既定学期の付け替え等) では、その ID を完了判定・ゲートに使っている箇所 (`isSetupComplete` / `setupGuard` / `RootView` の分岐) を grep し、新しい実体が判定を満たすかを書く前に確かめる。** atender build 19 で既定学期を「時間割未作成の新学期」に切り替える設計を書く途中、`isSetupComplete` が時間割の有無を見ていれば次回起動でセットアップ画面に強制送還される構造だった (実際は見ていなかったが、確認せずに書けば実装者も気付かない)。**UI テストで「永続化した却下」を無効化する手段は、UserDefaults の引数ドメイン上書きでなく既存の DEBUG env フック (起動時に消す) に寄せる** — 引数ドメインは読み取りを恒久的に上書きするので「却下した後は同プロセス内で再表示しない」が検証不能になる (2026-10-07)
28. **標準部品の「オプション A + 効果 B」を組み合わせる設計は、A を指定したときに B が framework 内で黙って無効化されないかを、その getter (`delegatedTransition` / `canTransitionFrom` 等) を開いて確かめる。** API と引数が実在することは組み合わせが成立することを意味しない — bloom で `CupertinoSheetRoute(topGap: 0.5)` の「半高 + 背面縮小」を書き、SDK は `topGap` 指定時に背面縮小を `null` にしていた (Codex に NO-GO、2026-10-06)。テストは「表示された」でなく効果そのもの (背面の描画幅) を測る仕様にする。**便利関数 (`showX(...)`) の引数は、関数が中で作る route / widget にその引数を渡しているかまで開く** — `showCupertinoSheet(showDragHandle:)` は受け取って捨てており、route 側の掴み手は `CupertinoDynamicColor` を resolve せず常時ダークで見えなかった (2026-10-07、gotcha/flutter-cupertino-sheet-drag-handle-dropped-and-invisible-dark.md)。**overlay を「どの画面の上でも」出す設計では、既存の builder Stack に Navigator の外の全面 overlay (ゲート等) が無いかを先に読む** — root Navigator に積んだシートはそれより下に隠れる。builder のさらに外に dev 専用の入れ子 Navigator を置いて解いた (2026-10-07, bloom dev メニュー)。**ブリーフが指定したパッケージの版は、その版の pubspec の依存と 1 つ前の版との `lib/` diff を見てから採る** — `smooth_sheets` 1.3.0 は差分が import 行だけで、中身は `material_ui` (Material の独立コピー) を引き込むだけだった。ロジック同一の 1.2.1 に pin した。tarball は `curl https://pub.dev/api/archives/<pkg>-<ver>.tar.gz` で scratchpad に落とせ、使い捨ての `flutter test` で設計の数値 (detent の上端等) を実走できる (2026-10-08, bloom シート detent)
