# Architect の職業的習慣ノート

召集されたら最初に読む。**過去の自分 (歴代 Architect) が実際に踏んだ穴**であり、予防的な網羅ルールではない。新しく踏んだら自分で追記・置換する (INDEX 対象外、再生成不要)。

- **横断的変更 (母数・型・命名規約の変更) では、影響を受ける既存テストを grep で機械的に洗い出してから移行リストを書く。** 目視列挙で rule-scope.test.ts が漏れ、developer 初回実装が 14 件全滅した実績 (sessions/2026-06-11)
- **導出値の手計算を doc に書かない。生成規則だけを書く。** 規則と手計算が矛盾したら規則が規範になり doc は errata になる — 最初から手計算を書かなければ起きない (gotcha/design-doc-derived-counts-vs-generative-rule.md)
- **描画テスト対象のコンポーネントは公開 prop 契約 (フィールド名・形・コールバック引数) を明記する。** 欠落すると Reviewer が prop 形を推測して偽陰性 YELLOW (gotcha/design-must-specify-component-prop-contract-for-render-tests.md)
- **型付き言語 (Swift 等) は挙動仕様だけでなく DTO の Optional 性・enum・VM の public API・init まで書く** (gotcha/design-doc-must-specify-swift-type-signatures.md)
- **データ源が要望に足りなく見えても、要望を縮小した設計を出さない。** 要望文言の含意 (件数・動作) から必要データ量を逆算し、既存ユーティリティで埋められないか先に当たる。縮小初稿を Leader に差し戻された実績 (sessions/2026-06-02)
- **並列 2 設計のときはスコープ境界 (どのファイル・ディレクトリがどちら専属か) を両 doc の冒頭に明記する。** マージがコンフリクトゼロになった成功例 (sessions/2026-06-11)
- **Researcher の実測を「本番と同じ条件での実測」と読み替えない。設計の土台になる実測は、設計する条件で自分で再現する。** omatase Coolify 設計で、Researcher は `next build` を実走して standalone レイアウトを報告したが (a) `.npmrc` の `node-linker=hoisted` を見ておらず node_modules の形の記述が誤り、(b) **`.git` のある作業ツリーで実行したため、Docker context (`.git` 無し) で `package.json#prepare` の `lefthook install` が install を exit 1 させる致命傷を検出できていなかった** (2026-07-16)。Researcher の実測条件と設計対象の条件の差分 (`.git` の有無 / linker / OS / Node 版) を明示的に洗い、差分があるところだけ再現する。「Researcher が実走した」は「その条件で実走した」でしかない
- **インフラ設計では、実測できなかった点を「不確定」と書くだけで終わらせず、それを潰す検証を設計成果物の中に入れる。** ローカルに docker daemon が無く Docker 上のレイアウトを検証できなかったので、CI に「イメージを焼いて起動して /healthz を叩く」job を設計へ組み込んだ (omatase 2026-07-16)。doc の注記は実行されないが CI job は実行される
- **★ ただし「検証を設計に入れた」で安心しない。その検証が本番と同じ経路を通るかを 1 段掘る。** 上の CI job は `docker run -p` + **ホストから** curl する設計だった。本番の Coolify healthcheck は **コンテナ内から localhost** を叩く。`ENV HOSTNAME=0.0.0.0` の Node は IPv4 のみ bind するので**ホスト経路は 200 / コンテナ内 localhost 経路は Connection refused** — つまり **CI 緑のまま初回デプロイだけ確実に落ちる**設計を書いていた (omatase 2026-07-16、Reviewer RED)。検証ステップを書いたら「この検証が緑で、かつ本番が落ちる状態はあり得るか?」を自問する。ポート公開プローブは in-container healthcheck の代理にならない (gotcha/coolify-healthcheck-localhost-ipv6-vs-node-bind.md)
- **同じ役割の設定が 2 コンポーネントで片方だけ通るとき、それは「片方が正しい」でなく「非対称がある」。** Go は `:8080` が dual-stack、Node は `0.0.0.0` が IPv4 のみ。同じ `health_check_host:"localhost"` で Go は通り web だけ落ちた。この非対称は原因の誤帰属 (イメージや wget を疑う) を生むので、**設計段階で bind/挙動を揃えにいく**こと自体に価値がある
- **「相手側の設定で回避する案」と「自分側を仕様に頑健にする案」が並んだら後者を採り、前者を不採用案に理由付きで残す。** omatase で B案 (`health_check_host:"127.0.0.1"`) は実測で通ったが「Coolify が host をそのまま URL に埋める」という**実機未確認の前提**に依存していた。A案 (`ENV HOSTNAME=::`) はコンテナが dual-stack になるので相手が何を使っても成立する。**実測で通ること ≠ 前提が確かめられていること** — 何に賭けているかを不採用案に書く
- **`set -euo pipefail` 下で `resp=$(cmd --fail-with-body)` と書いたら、body は「ログに出る」ではなく「出ない」。** 出力を変数に捕らえた時点で、非 2xx の exit で `echo "$resp"` の前にスクリプトが死ぬ。挙動仕様に「body がログに出る」と書くなら `|| rc=$?` で退避してから echo して明示 exit する形まで doc に書く (omatase D2、Reviewer が fake API で実測)。**「step が失敗する」と「原因がログに残る」は別の要件**であり、後者はテストで別途アサートさせる
- **リーダーから渡された「削除してよいファイル一覧」をワイルドカードのまま設計に書き写さない。1 ファイルずつ import 元を grep して確定リストに展開する。** atender Phase E で指示の削除対象 `components/today/*` に、ホームの出欠 CTA が現役 import している `MainTabView` 依存の `MainAttendanceCTA.tsx` が混ざっていた (2026-07-16)。字面で実行させれば本番機能が壊れていた。Leader の「importer ゼロを確認済」は**ディレクトリ単位でなくファイル単位で**再確認する
- **削除で新たに孤児化するファイルは、設計で勝手に消さず「孤児化した事実」を報告項目にする。** 消すか残すかは「作った UI を捨てるか」というプロダクト判断で Architect の裁量でない (Phase E の Spotify 歌詞風 UI 3 ファイル)
  - **★ ただし「その UI を捨てる」裁定が既に下りていて、その結果 caller が 0 になった残骸は別**。それを消すのは新しいプロダクト判断でなく**既存裁定の実行**なので設計で決めてよい (atender の `DayAgendaPanel`/`CalendarWeek`/`CalendarDay`/`CalendarSegmented` は build 11 の「日/週表示とアジェンダを廃止」裁定の結果 caller 0 になった、2026-07-29)。**判断基準は「孤児化の原因が誰の決定か」** — 自分の設計が原因なら報告、既に下りている裁定が原因なら実行。汎用 util (`CalendarLane` 等) はテストが乗っているので残す方を採り、事実だけ報告する
- **ブリーフに「不明」と書かれた事実でも、調べる先が違うだけのことがある。設計判断が丸ごとそれに乗るなら、諦める前に一次ソースを別ルートで当たる。** researcher が「Google Sans のライセンス不明 (`google/fonts` repo に無い)」とし、Leader も緊張関係として上げてきたが、**フォント本体の name table ID 13 / 公式 download manifest の OFL.txt / `/metadata/fonts/<Family>` の 3 系統**で SIL OFL 1.1 と確定でき、「(a)ブランド完璧だが不統一 vs (b)統一だが規約逸脱」の二択自体が消滅した (2026-07-16)。コレクション repo に無い ≠ ライセンス不明。**一覧 API の license フィールドが全件 null のような「証拠に見えるノイズ」に飛びつかず、必ず裏を取る** (実際 1 回引っかかって、個別エンドポイントで否定した)
- **ベンダー規約は「文言」だけでなく「公式アートワークの実測」まで当たる。規約の自己申告が事実と食い違うことがある。** Google の規約は *"The SVG format also makes it possible for you to edit the ... text to the language of your app"* と書くが、**現行 SVG のテキストはアウトライン化パスで編集不可** (`<text>` 0 個を実測)。これに気付かず「公式アセットをそのまま使えば安全」と設計すると、日本語アプリで Google だけ英語という不統一が完成する。逆に公式 SVG の実測 (`x="16" width="20"` 等) は spec 画像より信頼できる寸法根拠になる
- **「A と B の規約を両方守れ」の要望では、両立可能かをまず数値で検算する。両立不能なら、それを証明して不採用案でなくエスカレーションに書く。** Apple の 43% と Google の 14/20 は同一ボタン高で両立せず (Apple title ≈ Google title × 1.36 が比率で固定)、Touri の「フォント統一」要望は規約順守下では**原理的に達成不可能**だった。ここを曖昧にすると Developer が勝手に片方を破る
- **要望の主目的 (Touri が言った「統一」) が原理的に一部達成不能でも、達成可能な軸を全部列挙してから諦める軸を1つに絞る。** 塗り/stroke/高さ/角丸/ロゴ枠/ロゴ左端/ラベル左端/日本語グリフのフォントは全部揃えられ、揃わないのは Latin ラベルの pt だけ、と切り分けられた。「規約が厳しいので統一は無理です」で返すのは調査不足
- **★ 切り分けプローブを設計に書いたら「成功時と失敗時で*返り値が違う*か」を必ず自問する。同じ値が両方で返るプローブは情報量ゼロ。** nwasabi-hp の apex 配線で「`curl -H "Host: n-wasabi.org" http://localhost/` → **404 なら Traefik まで到達 = 期待値**、その他なら server_name が効いていない」という判定表を書いたが、**敷設前も・成功時も・失敗時も 404** だった (Leader が実機実測、2026-07-16)。Nginx vhost に `proxy_intercept_errors on;` + `error_page 404` があり、**上流 (Traefik) の 404 を横取りして `default_server` と同じカスタム 404 ページに差し替える** — 2 つの 404 がバイト単位で同一 (`Content-Length: 1020`)。**「期待値」を書くときは、その値が返る経路を全部数える** (今回は 2 経路あって区別不能だった)。判定不能なら**「判定する方法は無い」と書き、代わりに何で担保するかを書く** (今回は `nginx -T` での config 確定 + Traefik 直叩き `127.0.0.1:8880` での迂回 + 段 3 後の 200)。★ **200 は `error_page` の対象外なので横取りされない — 「成功の証拠」は 404 でなく 200 に置く**
- **★ 上と同根: プローブが通る経路上の中間 proxy が応答を書き換えないかを確認する。書き換えるなら、それは挙動仕様にも波及する。** 同じ `proxy_intercept_errors` は「HP コンテナが返す 404 body が本番ではユーザーに届かない」も意味しており、(a) スモークの 404 アサートは **status のみ**にする必要 (CI はローカルコンテナ = 横取り無しなので body が違い、body を見ると CI 緑・本番赤)、(b) **カスタム 404 ページを作っても表示されない** という不採用理由の変化、まで波及した。**プローブの穴を直すときは、その事実が仕様に与える影響を洗い直す** — プローブだけ直して終わると仕様側に嘘が残る
- **★ 「壊せば赤くなる」と設計に書いたら、その壊し方を自分で 1 回実行して赤くなるか確かめる。破壊テストの*ミューテーション*自体が的外れなことがある。** nwasabi-hp で「`COPY site/ dst/` を **`COPY . .`** に広げれば CI が赤くなる」と 4 箇所に書いたが、**Dockerfile に `WORKDIR` が無く base image の `WorkingDir` が `/` だったので、ファイルは docroot の外 (`/README.md`) に落ちて配信されず、smoke は緑のまま**だった (Developer/Leader が実測)。**安全網は壊れていなかった — 壊れていたのは「この変更をすると漏れる」という私の事実認識**。★ **「危険な変更」と「検出される変更」が一致しているかを、危険側・無害側の両方を実走して確かめる** (今回: `COPY . dst/` は漏れて赤、`COPY . .` は漏れず緑 = 一致していた)。字面 (`COPY . .` は危険) で覚えず **COPY 先が docroot を向いているか**で判断する — 同じ文字列でも Coolify の `static` は `WORKDIR /usr/share/nginx/html/` を先に吐くので**危険度が反転する**
- **★ ベースイメージが docroot に置いている物を数える。`COPY` は既存ファイルを消さない。** 同じ設計で `nginx:alpine` 既定の `/usr/share/nginx/html` へ COPY したため、**base image 同梱の `50x.html` が生き残って配信され** (`GET /50x.html` → 200)、「配信範囲 = `site/` の中身」という**設計の中心的な主張が偽**になった。実害はゼロ (公開ボイラープレート) だが、**主張が偽になること自体が却下理由になる** — 真の配信範囲が「`site/` ∪ base image の置き土産」になり、それは *`static` の `base_directory` を「定義がリポジトリの外にある」と批判したのと構造が同じ*。しかも moving tag (patch 自動追従) を選んでいると**コミット無しに中身が変わり得る**。対処は `rm` (減算的・追いかけっこになる) でなく **docroot を自分が所有するディレクトリに移す** (構造的・base image が何を置いても不変)。**「相手側の中身に依存せず自分側を頑健にする」の再適用**
- **★ ブリーフが「未修正のバグ」「現状こうなっている」と書く項目は、doc を書き終える直前に git log と実ファイルで再確認する。ブリーフも自分の初回 Read も、セッション開始時点のスナップショットでしかない。** atender 版数管理で、リーダーは「手順書のバグ (CLAUDE.md が Info.plist の手編集を指示) を設計に含めるか判断してほしい」と渡してきたが、**書いている最中に main の `6c80bec` で修正済みになっていた** (2026-07-17)。私の初回 Read は修正前の内容を返しており、それを信じたまま書けば**既に直っているものを「直す」設計**を出していた。リポジトリは設計中も動く。「現状」に依存する記述は、doc 完成時点の現状で書く
- **「〜をベースに/コピーして」型の要望では、fidelity (元実装への忠実) と curation (設計原則による選別) のどちらが契約かを設計前に確定する。** dandan-app で原則準拠の選別設計 (画面絞り込み・ツール統合・policy 不採用推奨) が Touri 裁定「不採用判断いらんからコピーして」で全面書き直しになった (2026-07-07)。コピー契約なら doc の本丸は「忠実度テーブル (全構成要素に コピー / 機械変換+必然理由 / additive を割り、捨てる行ゼロ)」であり、改善提案は「やらない変換」として不採用案に隔離する
- **★ 「データは既にある。不足は表示ロジックだけ」を信じない。新機能の入力 (時計・日付・ID・単位) は、存在ではなく*正しさ*を、1 点でなく境界の両側で実測する。** atender UI 刷新で Researcher は「『次の授業』のデータは `OccurrenceDto` に既にあり、不足は表示ロジックだけ = 最大の勝ち筋」と報告し、Leader もそれを最優先タスクとして渡してきた。**データはあったが時計が壊れていた** — `CalendarRange.todayString()` が UTC 暦で、API は `APP_TZ = "Asia/Tokyo"` 固定。**毎日 00:00〜08:59 JST の 9 時間だけクライアントが前日を指す** (2026-07-17 実測)。信じて建てれば「教室移動しながら次の授業を見る」= まさにその時間帯に 1 日ズレた列を光らせる機能が出荷されていた。ついでに既存バグも見つかった (月曜 9 時前はルームの時間割が先週を読む)。**日中しか再現しないズレは開発者が絶対に踏まない**ので、レビューでも目視でも出てこない。**「N 時間ズレる」は 1 点測っても見えない — 境界の両側 (08:00 と 09:00) で挟む** (gotcha/client-today-must-use-server-timezone.md)
- **★ 「標準部品に回帰せよ」を字面で実行しない。その自前部品が*なぜ*作られたかを grep してから置換する。** 同設計で findings は「`EmptyState` → `ContentUnavailableView`、`AuthProviderButton` → `SignInWithAppleButton`」を一律の目標に挙げていたが、**`EmptyState` は `Image("mascot-hello")` を描いていた** (Touri が生成させたキャラクター資産)。字面で置換すればマスコットが消える = 作った UI を捨てるプロダクト判断を Architect が黙って下すことになる。正解は「標準部品を使わない」でも「マスコットを捨てる」でもなく、**`ContentUnavailableView(label:)` の icon に `Image("mascot-hello")` を渡す** (型検査で確認済) — HIG 準拠の余白を得たまま資産が残る。一方 `SignInWithAppleButton` は**不採用**にした: 現行ボタンは Apple と Google の両ブランド規約を寸法まで実測して満たした資産で、標準部品に替えると Google 側との統一が崩れる。**「標準部品だから正しい」が成り立たない場所が実在する。** 置換前に「この自前部品が満たしている制約は何か」を 1 個ずつ言語化する
- **★ ブリーフの「壊れるテスト N 件」は事実でなく、*ある仮想の設計*に対する予測。自分の設計で数え直す。しかも件数は設計で減らせる。** 同設計でブリーフは「意図的に壊れる 9 件」と名指ししてきたが、実際に壊れたのは **3 本 + 削除 1 本**。差は 2 つとも**設計判断で消せた**: (a) `HomeChipsTests` 3 本 → 既存関数 `HomeChips.items(rooms:)` に条件を混ぜず、可視判定を**新関数** `isVisible(rooms:)` として足したので契約が保たれた (b) `NavigationTests` → HIG は tab bar に filled symbol を推すが **`calendar.fill` は SF Symbols に存在しない** (実測) ので fill 統一が原理的に不可能 → symbol 名を変えない判断になり緑のまま。**「壊れる件数」を引き継ぐと、壊さずに済む設計を探さなくなる。** 壊すのは減らせないものだけにして、減らせた理由を doc に書く (Reviewer が「なぜ緑のままなのか」を疑わずに済む)
- **★ フェーズ表を「§N 全部を P1」の粒度で書かない。削除対象は「最後の本番参照が消えるフェーズ」でしか消せず、その参照はたいてい別フェーズの節にある。** atender UI 刷新で §10 に「§3 全部を P1」と書いたが、§3.5 の `Space` 整理は**実行不能**だった: `selfTtChrome` の最後の参照は §5.3 (P3)、`tabBarHeight` の 9 参照のうち 2 つは §5.4/§5.3 (P3)、`tabBarContent` は §4.1 (P2)。**P1 で実際に消せたのは「最初から本番参照 0 だった 4 つ」だけ** (2026-07-17)。節番号は**トピックの単位**であって**実行の単位ではない** — 節ごとフェーズに割ると、節の中の各項目が持つ依存関係が消える。トークン/ファイルを消す設計では **1 個ずつ「最後の参照は誰か → そいつは何フェーズか」**を表に書く。ついでに §9.2「壊れるテスト」の**壊れるフェーズ**も同じ依存で決まる (`DesignTokenTests` は P1 で壊れると書いたが、実際に壊れるのは P3)
