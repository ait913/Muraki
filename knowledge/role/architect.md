# Architect の職業的習慣ノート

召集されたら最初に読む。**過去の自分 (歴代 Architect) が実際に踏んだ穴**から蒸留した現役の習慣 (20 本以内を維持)。新しく踏んだら自分で追記・置換し、古びたら捨てる (INDEX 対象外、再生成不要)。2026-07-31 に Opus 5 移行で全面圧縮 (原本: ai-audit/archive/20260731-muraki/role/architect.md)。

1. **横断的変更 (母数・型・命名規約) では、影響を受ける既存テストを grep で機械的に洗い出してから移行リストを書く。** 目視列挙の漏れが初回実装 14 件全滅を生んだ (sessions/2026-06-11)。**一覧に項目を足す変更 (slash の項目・`EVENT_KINDS`・MCP ツール) では、件数だけでなく「絞り込みの文字」「末尾 N 件 (`slice(-N)`)」で照合しているテストも grep する** — wasawasa 3c で slash に「データベース」を足すと「タ」→ task だけ、のテストが「タ」を含むラベルで割れ、`EVENT_KINDS.slice(-8)` と MCP の `tools.slice(-9)` は末尾に足した瞬間に別物を指す (2026-10-07)。**出力の既定形式を変える変更 (通知本文を文字 → Block Kit 等) は、機能のテストファイルでなく「既定経路の出力文字列」で grep する** — wasawasa の既定文面 (`[デプロイ完了]` 等) の完全一致は p2-notify だけでなく smoke・gate-fixes-alt・p3a・E2E に散っていた。カスタム経路を使うテスト (変わらない) も「変えない」行として根拠つきで表に載せる (2026-10-07)
2. **導出値の手計算を doc に書かず、生成規則だけを書く。ただし「機械的に取れる規則」は対象全件で走らせてから書く** — 1 例で効く規則は 1 例の規則。規則が実在しないなら設計が与える定数の列に置き、Developer に再導出させない (gotcha/design-doc-derived-counts-vs-generative-rule.md, 2026-07-30)。**Reviewer 用に具体値 (色 hex・座標列) を doc に書くよう求められたら、規則を scratchpad のスクリプトで実走して得た値だけを書く** — 色相の手計算で 130.5° と書きかけ、実走で 134.9° だった (2026-09-18, bloom M2)。**実走も測り方で嘘になる**: 画像から色を採るとき領域全体の平均・円平均・ヒストグラム最頻は肌や小物が混ざる (ネイビーのケープが「hue 6°」と出た)。対象部位のパッチ中央値を狙って採り、値を書く前に元画像でその部位を目視する (2026-09-24, bloom キャラ v2)。**試作スクリプトはビルドのエラーを捨てない** (`dart compile ... >/dev/null 2>&1` で構文エラーが消え、古いバイナリの出力を新しい規則の結果として 2 回見比べた — 形が変わらないことに気付いて発覚。2026-10-11, bloom 地図テクスチャ)
3. **契約を明記する: コンポーネントの公開 prop 契約、型付き言語では DTO の Optional 性・enum・public API・init まで。** 欠落すると Reviewer が推測して偽陰性になる (gotcha/design-must-specify-component-prop-contract-for-render-tests.md, gotcha/design-doc-must-specify-swift-type-signatures.md)。**既存の 1 クラスから機能を切り出して別クラスに分離する設計では、切り出す機能が OS 側で「1 プロセスに 1 個しか持てない」役割 (delegate 登録・シングルトン) を伴っていないか確認し、伴うなら元クラスの型宣言 (conformance) からも明示的に外し、新クラスの登録箇所 (`AppDelegate` 起動時の 1 行等) まで書く** — 型シグネチャの削り忘れは 2 クラスが同じ delegate を取り合う実装不能な契約になる (2026-08-21, bloom: LocationBridge→NotifBridge 分離で `UNUserNotificationCenterDelegate` の帰属先を書き忘れかけた)。**Dart の abstract interface にメソッドを足す設計は、先に `grep -rln "implements <Interface>" test` で fake の数を数える** — bloom の `LocationBridge` は fake 11 ファイルで、足すと全赤。前例 (`system_bridge.dart` のトップレベル関数) に寄せた (2026-10-08)。**既存のキュー / 表に「種別」を足す設計 (動画だけの outbox に写真) は、列や引数を足す前に `schemaVersion` を固定しているテスト・interface の fake を数え、既存の値から一意に導けるなら導出で済ませる** — bloom の写真は `source_path` の拡張子 (`.jpg`) で決まり、drift 列 (schemaVersion 固定テスト 3 本) も `PostMediaProcessor` の引数 (fake 2 本) も要らなかった。前処理を interface の手前 (submit 前) に寄せると interface は不変で済む (2026-10-10)**「OS 資源を理由の集合で共有管理している」層に新しい理由を足す設計は、その理由の出し入れ口を 1 関数に絞り、既存の除去箇所 (`removeReason`/filter) を全部表にして巻き込まれないことを確かめ、さらに理由を持つだけで走る既存の分岐 (fix を SLC として記録する末尾の else 等) が誤作動しないかを `didUpdate` の全分岐で追う**
4. **要望を縮小した設計を出さない。** 達成可能な軸を全部列挙してから、諦める軸を 1 つに絞る。両立不能は数値で証明してエスカレーションに書く (sessions/2026-06-02, 2026-07-16)。**裁定の文言 (「帰宅を検知して『vlog できたよ』と通知」) は、OS の実行制約と突き合わせてから受ける** — bloom 0.2.2 で背景の relaunch 中に vlog を作り切る前提で書きかけたが、iOS は背景の Metal を止めるので地図 snapshot も動画合成も前景でしか走らない。文言を事実に合わせた案を推奨にして残論点へ上げた (2026-10-11、pattern/ios-background-detect-foreground-render.md)。**私的な位置を含む成果物を外へ出せる設計 (共有シート) では、カメラの中心・最初のテロップ・軌跡の端が家を指していないかを 1 フレームずつ問う** — 冒頭を家の cell10 中心に置くと zoom 8 でも 1 pt ≈ 250 m で家が割れる。**判別規則の裁定 (「線路なら電車、それ以外は車」) は、具体的な場所 3 つ (地下・高架・並走道路) に当てて破綻しないか確かめる** — N02 は地下鉄も地表投影で持つので、地下鉄の真上の幹線道路 (銀座通り・国道 246) を走る車が電車になる。裁定を捨てずに「止まった場所 (駅か信号か)」を足して両立させた (2026-10-15, bloom B 軌跡)。**ライブラリの版を上げるかの判断を求められたら、CHANGELOG の修正項目が今の版で自分の PJ に起きる経路かを pub cache の実装で確かめる** — maplibre_gl 0.26.2 は custom headers 未使用でも全 http(s) を横取りしており、「custom headers 由来のクラッシュ」は bloom にも当たっていた
5. **並列 N 設計ではスコープ境界 (どのファイル・ディレクトリがどちら専属か) を各 doc の冒頭に明記する** (sessions/2026-06-11)
6. **ブリーフ・Researcher の実測/数値/件数/ファイル名/理由づけは、自分の設計条件で解き直す。** 実測は「その条件で実走した」でしかない (`.git` の有無・linker・TZ で反転する)。「壊れるテスト N 件」は仮想設計への予測で設計判断で減らせる。数値は「測った」のか「割った」のか。結論が正しくても理由が偽なら理由を立て直す (2026-07-16〜30)。**ブリーフの「契機 X は現行どおり」は、その契機の呼び出し元を grep して実発火頻度を数えてから受ける** — bloom E2E Phase A で「drain 後 flush (現行どおり)」を残すと、drain が TrackEvent ごと (≈3 秒) に走っていて「5 分バッチ」の要件と矛盾していた (2026-10-03)。**ブリーフの「旧クライアントは版ゲート (`MIN_CLIENT_BUILD` 等) で締め出す」は、クライアントが実際に送っているヘッダ値を定義元まで grep してから受ける** — bloom は全ビルドが `kClientBuild = 1` 固定で、ビルド番号で引き上げると新版ごと全員締め出す設計になるところだった。互換レベル定数 (1 → 2) に読み替えた (2026-10-10)。**ブリーフの「審査通過後にサーバー反映」型のリリース順序は、審査員の端末がどのサーバーに繋がるかを確かめる** — 審査中は prod の旧サーバー相手に新機能が動き、失敗するとリジェクト要因になる。**ブリーフの「失敗したら N 単位に分割して再送」型の再試行は、その経路の限流値 (burst / 毎分) で最悪リクエスト数を数えてから分割方式を決める** — bloom footprints で「日単位に分割」は 31 日 chunk で 31 リクエスト、burst 4 を超えるため二分割再帰に直した (2026-10-08)。**「firstSeenVersion N で出た」バグの原因コードが N 新規とは限らない — `git log -p --follow` で原因行の初出 commit を引き、N で広がった誘因 (起動時 write migration の追加・bg engine 起動契機の増加等) と区別してから「原因」「回帰か新規か」を doc に書く** — bloom の bg drift open は P2a からあったが 0.2.0 で競合窓が広がり常時クラッシュ化。これを掴めば「前景 ingest への回帰は good baseline への復帰で新規退行でない」と framing できる (2026-10-09)。**検証を「塊ごと拒否」から「行ごと捨てる」へ緩める設計は、(a) 旧クライアントが 200 を受けて何を確定扱いにするか (uploaded=true で再送が止まる) と (b) 検証に無い上限 (int32 溢れ → 500) を先に洗う。****ブリーフの「複数ヒットしたら」型の異常系は、先に unique index / 制約を schema で grep する** — wasawasa の「build_number が複数ヒット」は部分 unique index で起き得ず、本当に曖昧になるのは制約の無い server_commit 接頭辞の方だった。**既存 API が返さない出力 (`changes` 等) を MCP に足す要望は、既存サービス関数の戻り値型を確認し、tx 本体の切り出しを設計に書く** (二重実装の回避。2026-10-05)。**ライブラリの「冪等」「無損失」は研究のサンプルでなく手元の実コーパス (Muraki の md 数百本) で回してから正典の前提にする** — Tiptap の md 往復は研究の 2 本では冪等、実文書 9 本中 3 本で回すたびに壊れ続けた。ブリーフの上限値 (1 MB) も最悪形で測ると 2 乗の parse で数十秒になった (2026-10-05, wasawasa 3b)。**「往復する」の実測は、どの経路 (ブラウザの DOM あり / サーバーの DOM なし) で測ったかを確かめ、正典の書き込み経路で測り直す** — 表のセルの `<br>` は研究 (ブラウザ) で往復したが、サーバーの正規化はエスケープして保存しており、既存の本番バグだった (2026-10-07, wasawasa (4))。**目印を足す符号化 (区切り行のハイフン数 = 列幅) は、既定の出力が偶然その目印を満たす率を実コーパスで数えてから判定を決める** (合計 100 だけだと 1534 表中 12 を誤読)。**ブリーフの「現状は X を一切していない」も grep で確かめる** — bloom で「アプリは版を送っていない」と渡されたが、実際は定数 `X-Client-Build: 1` を送っており、426 ゲートがそれを読んでいた。実値化すると既存ゲートの意味が変わるので互換の 1 行が要った (2026-10-10)。**ブリーフの「変化したら即送信」は、その経路のサーバー限流が「429 を返す」か「黙って捨てる」かを確かめてから受ける** — bloom の WS `pos` は 1 回 / 5 秒 / user を超えると無音で drop し、テストでも緩和されない。移動手段の変化を即送りすると直前の送信から 5 秒以内の分が消えるので、壁時計で 6 秒空ける遅延送信 (最新値で 1 通に畳む) にした (2026-10-11)。**執筆中に方針変更が続けて来たら (同日 3 回)、置換のたびに旧方針の語 (「15 分」「丸め」「bucket」等) を grep して全節から消し、挙動仕様の標本と不採用案の理由まで追う**。**ブリーフの「全メソッドで所有者 ID を必須に」は、その ID を持たない呼び出し側 (閲覧者 ≠ 所有者の配信経路、nginx alias 直読み) を利用側リポジトリで grep してから受ける** — nexom 1.2.0 で aisaba の user icon 配信が所有者 pid を持たず、参照系は `pid: str | None` を既定値なしの必須引数にして `None` 明示で capability 読みを許す形に直した。同じ回: 「既知 xfail の理由」(`format_psc_contents_id` 欠落) は `--runxfail` で実走すると別原因 (`PsFileTypesError()` の TypeError) だった — xfail の reason 文を信じず 1 回走らせる (2026-10-21)
7. **検証を設計に入れたら「この検証が緑で、かつ本番が落ちる状態はあり得るか」を自問し、「壊せば赤くなる」と書いたらその壊し方を自分で 1 回実行して赤を確認する。** プローブは成功/失敗で返り値が違うか、経路上の中間 proxy が応答を書き換えないか、危険側・無害側の両方で実走する (2026-07-16, omatase・nwasabi-hp)。**「設定行を外す → 赤」型の負のコントロールは、その設定の既定値を先に確かめる** — mermaid の `securityLevel` は既定が `strict` で、ブリーフどおり「外す」と緑のまま (負のコントロールが成立しない)。壊し方は「危険側の値にする」(`'loose'`) で書いた (2026-10-05, wasawasa コードブロック)。**拡張・プラグインの並びを変える設計は、出力 (正規形) の比較だけでなく入力 (キー操作の優先順) も実走する** — 正規形はコーパス 669 本で不変だったが、Tab の行き先が位置で変わっていた
8. **IA (ホーム構造・タブ・画面分割) は挙動仕様と別物として先に裁定を取る。** 企画書の節順を主従と読んで地図主役の R0、参照アプリ名 (「Zenly のような UI」) を質感でなく骨格の指定と読んで 1 画面地図ホームの R1 を書き、2 回連続で全面組み直しになった (骨格が違っても挙動仕様の中身はほぼ生き残る = IA だけ先に安く確定できた)。参照アプリの言及は「質感 (部品・遊び)」か「構造 (画面構成)」かを切り分けて確認し、IA は ASCII 4 画面級のラフ 2 案で本人に選ばせてから挙動仕様を書く (2026-08-19/20, bloom)。**承認済みモックでも「表示に使っている識別子」と「色 token のコントラスト」は正典で検算する** — wasawasa m1 は Release を client 版で名乗っていたが PRODUCT の例表では名前 ≠ 版 (`2.1` = client 2.0.2) で、名前列を足す逸脱が要った。入力枠・pill の色は 4 つが WCAG 未達で、実測で置換した (2026-10-02)
9. **「相手側の設定で回避する案」より「自分側を仕様に頑健にする案」を採り、前者は賭けている前提つきで不採用案に残す。** base image が docroot に置いている物も数える — `COPY` は既存ファイルを消さない (2026-07-16, omatase)
10. **削除リストはワイルドカードのまま書き写さず、1 ファイルずつ import 元を grep して確定リストに展開する。** 孤児化するファイルは、原因が自分の設計なら報告項目に (プロダクト判断)、既に下りている裁定なら実行として設計で決める (2026-07-16/29, atender)
11. **変更対象は file でなくキー文字列で grep し、宣言サイトの数と実効値 (外側が勝つ modifier / 同一キーの重複宣言) を確定してから書く。** 「N 行だけ」「変更は N つだけ」という数え上げの断言は、重複・節またぎの被りで即座に嘘になる — doc 完成時に「触る行」の側から引き直す (2026-07-17, atender)。**UX doc の閾値をサーバー側 doc の擬似コード/SQL が再掲している構成 (phase0/phase1 のような分冊) では grep を両方の doc に必ず及ぼす** — 片方だけ直すと挙動仕様と実装契約が乖離し、Reviewer もどちらが正か判定できなくなる (2026-08-21, bloom: P1(a) の人数閾値が phase0 §10-4 と phase1 SV5 擬似コードの 2 箇所に重複していた)
12. **自前部品→標準部品の置換では、「自前が明示的に渡していた属性 × 標準が暗黙に引く供給元 (asset catalog / build setting / system default)」の表を作り、供給元の実値を実測する。** 死に資産は消費者ゼロだから腐ったまま生き延び、標準化がその最初の消費者になる。先に「この自前部品が満たしている制約は何か」を言語化してから置換する (2026-07-17, atender)
13. **フェーズ表は節単位で割らない。削除対象は「最後の本番参照が消えるフェーズ」でしか消せず、その参照は別フェーズの節にいる。** シェル (nav/tab bar/余白) を変える設計では、着手前に「全画面が持つはずの構造」を grep で数え、例外の 1 画面を先に見つける (2026-07-17, atender)
14. **「additive」はフィールド追加と enum 値追加で別問題。** enum 追加は旧クライアントの未知値フォールバック経路に落ちて表示退行になる — 旧クライアントの扱いを実装で確認してから additive を名乗る。代表値の種類を増やすのでなく、潰す前の内訳を additive に足して既存値は据え置く (2026-07-29, atender)。**DB 列の nullable 化も同じ罠 = API の Optional 化**。旧 iOS の `Codable` が非 Optional なら null で decode が落ちて画面ごと壊れる — DB は NULL、DTO は番兵 (`""`) で型契約を据え置く。**onDelete を SetNull にする列は、私的データの「写し」の行 (`source = PERSONAL` 等) が匿名で残らないか `source` 別に確かめ、写しは tx で明示削除する** (2026-10-09, atender build 20 退会)
15. **時刻依存の挙動仕様は #番号ごとに危険窓の標本時刻を書く。** 日付だけの標本を残すと Reviewer が無害な正午を選び、最も危険な窓が唯一の無検出窓になる。1 箇所で言語化した危険は同類型の全項目に伝播させる (2026-07-17, atender)
16. **「スコープ外」と切った既存コンポーネントに自分の設計の出力が流れ込むなら、そのパイプラインの暦・単位・丸め規則は自分の仕様の一部 (in-scope に昇格)。** スコープ表に「例外的に触る」の行で明示する (2026-07-29, atender)

31. **「ログが消えた」「○時から始まっている」型のブリーフは、その時刻を deployments の `finished_at` と突き合わせてから原因を書く** — bloom で「01:00 JST の日次再起動でログが消える」と渡されたが、Coolify logs API を `lines=all` で引くと先頭はデプロイのコンテナ作成時刻で、Touri が見た 01:02 JST は前夜のデプロイ完了 (01:03 JST) だった。原因が「再起動」なら docker 側の設定で済むが「デプロイのコンテナ再作成」なら永続ボリュームか外部転送しか残らず、設計の置き場が変わる (2026-10-13)。**外側 middleware で `r.PathValue` を読む設計は、mux の手前で `r.WithContext` するものが無いか grep してから書く** (gotcha/go-servemux-pathvalue-invisible-to-outer-middleware.md)。**設計中にブランチ再編が来たら、doc の file:line を新ブランチで引き直すだけでなく、旧ブランチにしか無いテスト (label 集合の固定等) を移行表から外し、旧ブランチ側の責務 (番号付け替え・privacy の当て直し) を「誰のメモか」まで書く**
32. **「有効なら新しい列が非 NULL」の CHECK を足す設計は、drizzle の生成物にその CHECK が入ると既存の有効な行で migration が落ちる。生成物から CHECK を外し、データ migration (割当) の末尾で張る順序を doc に書く** — wasawasa 連携アカウントで、dev1 / dev2 がアプリアップロード有効のまま 0015 で新 CHECK を張る形を書きかけた。秘密の移行は先に封緘の AAD を読み、行キーを含まないなら SQL で複製する (pattern/singleton-secret-to-named-accounts-migration.md、2026-10-14)。**執筆中にスコープが足された時 (環境ページ・slug)、既存の UI の入口 (`env-edit` 等) を E2E で grep して件数と移行先を移行表に載せてから書く**
30. **並行レーンで migration 番号を分け合う設計では、「欠番を許容する」と「後から小さい番号を適用できる」を混同しない。** golang-migrate は今の版より大きい番号しか当てないので、大きい番号を先に dev に載せると小さい番号は永久に当たらない。番号を書いたら「どの番号が先に着地していなければならないか」を順序制約として doc の冒頭とリリース手順の両方に書く — bloom スタンプ攻撃で「欠番 OK なので 0018 より先に 0019 を流せる」と書きかけ、同 worktree の別 doc (track-3d) の順序制約で誤りに気付いた (2026-10-11)。**migration を足す設計は、ブリーフが指すブランチでなく全リモートブランチの最大番号 (`for b in $(git branch -r); do git ls-tree --name-only $b server/migrations/; done`) と各環境の DB の版 (session 記録のデプロイ履歴) を先に確かめ、対象ブランチをそこから決める** — bloom admin の最終アクセスで「master の次番号」を受けかけたが、dev1 は既に 0.2.2 (版 21) で、master に 0022 を入れて prod に先に流すと 0.2.2 の 0018〜0021 が永久に当たらなくなる。この順序制約を設計 doc に書いて報告したところ、Touri 裁定で「既存データからその場で引く (sessions.created_at の最大)」に置換され、migration 自体が不要になった。**表示のための書き込みを足す前に、既存の表 (sessions・元表の最大値) で要望を満たせないかを先に出す** (2026-10-12)。**以前の設計で「不採用」と書いた機能を Touri が要望したら、その不採用を固定している既存テスト (禁止語・禁止キーの列挙) を grep して移行表に載せる** — admin の詳細ページに「最終アクセス」が出ないことを assert するテストがあった。**同じ規則は正典 (PRODUCT.md) にも効く: 新しい裁定が正典の既存裁定 (「CI 化しない」等) を反転するなら、該当節を全部 grep して置換文案を doc の申し送りに書く** (wasawasa パイプライン、§4・§8・§9-9 の 3 か所、2026-10-14)。**上流 doc の「削除する」を「残す」に反転する設計 (bloom 0.2.3 の平文投稿) では、`count(*) = 0` を固定しているテストだけでなく、「平文が残ってよい表」の集合 (`retainedPlainTables`)・手順書の文字列と順序を固定しているテスト (`TestC_Runbook_OrderAndRules`)・CLI の出力行を正規表現で固定しているテストまで grep する。残す期間中に走る既存の掃除 (DB 参照あり 21 時 sweep / DB 非参照の切替 purge) を両方表にし、どちらが残した行のファイルを消し得るかを書く** (2026-10-16)。**drizzle の migrator も journal の `when` が最後に当てたものより新しい migration しか当てない** — 並行レーン (承認ゲート付きの Phase D 等) と番号を取り合う時は「後で生成した方を後でマージ」を順序制約に書く。**「次の番号」を別 doc が文書上で予約していたら (`0017` = Phase D)、`grep -rn "0017"` で予約している文書を全部拾い、先に着地する方が番号を取って予約側の文書を置換表に載せる** — 予約を避けて欠番 (0018) にすると、後から小さい番号を当てられない制約と衝突する (wasawasa 審査中、2026-10-19)。**enum に値を足す設計は、その値で色 token を引く表 (`STATUS_TONE`)・一覧フィルタ・`it.each(ST)` の網羅配列・description の完全一致テスト (`toBe`) を grep して移行表に載せる** — `release_update` の description は MC29 が `toBe` で固定していた

34. **サーバーが中身を読めなくなる設計 (E2E) では、サーバーが今やっている集計・判定・通知文面・seed / デモデータ・admin export を grep で全部表にし、「端末へ移す / 鍵付きトークンに置き換える / 平文で残す (理由)」に 1 行ずつ分類してから書く。** 暗号文は平文より大きいので、経路の上限 (WS の `SetReadLimit`・body cap) も grep する — bloom の WS は 1024 byte で、4 グループ分の RT 暗号文が入らなかった。dev / 審査用の seed はサーバーが暗号文を作れないので「dev だけサーバーが鍵を持つ seed グループ」を設計に入れないと、塗りの無い地図でしか実機確認できない。並列 doc が触る UI 層には「型を変えない境界 (provider / model)」を先に切り、中身だけを後の単位で差し替える (2026-10-15, bloom C)
33. **外部の管理ツール (wasawasa 等) に環境・資源を「登録する」設計は、選ぶ種別 (tier / kind) が駆動する副作用を grep してから種別を決める。** 名前が似ていても意味が違う — bloom 審査用環境で Coolify 側が production 環境 (mem-tiers の保護) だから wasawasa も `tier=production` と書きかけたが、wasawasa は production tier へのデプロイでリリースを `released` に遷移させる (`statusChangesOnReflect`)。審査に出しただけで「リリース済み」になるので development にした。**インフラの手順を書く前に、対象の実物を API の GET で 1 回見る** (`custom_labels` の全文・env のキー・storages・betaGroups の `hasAccessToAllBuilds`)。TestFlight の内部グループが全 build を自動配布していると気付かなければ、審査版が日常端末に入って別 DB のアカウントになる穴を書き落としていた (2026-10-15)
34. **「定義だけで書き込み側が無い」表・列に書き込みを足す設計は、先に読み出し側を全部 grep し、起動する副作用 (外部送信) を塞いでから書く。** bloom 0.2.3 の `UsualPlaces` は空のまま `isUsualCell10` が presence の `at_usual` に流れており、場所の登録を足した瞬間に「いま家にいる」がサーバーへ出る休眠経路だった (読み出しは 1 箇所だけで、置換して関数ごと削除した)。同じ回で踏んだ 2 点: (a) **背景で動く機能の判定者を決める前に、背景 engine が DB を開けるかを現行 doc で確かめる** (bg engine は DB 不可 → 候補検出は前景限定、通知は「見つけた候補の思い出し」に縮むと要望の縮小として申告した)。(b) **interface に引数を足す前に fake の数を数える** (`PresenceSink` = 3 ファイル、`LocationBridge` = 13 ファイル → 後者は触らずトップレベル関数に逃がした) (2026-10-15)
36. **「DB を見ない掃除 CLI に DB 参照の keep を足す」設計は、その CLI が unlink する経路を全部 (ディレクトリ走査・保留 manifest の参照先・tmp・bundle 無しの uploads) 表にして keep を各経路に当て、さらに「同じ CLI を後の時点 (公開後・期限後) にも回す」手順が稼働中の作業ファイル (`tmp/upload-complete-*`) を数えているか見る** — bloom 0.2.3 平文投稿 R0 で走査側だけ keep を付け、保留 manifest ループが投稿済み媒体を unlink する穴と、期限後 purge が稼働中の tmp を消す穴を Codex に BLOCKER 2 件で指摘された。**「env X が設定済み = 公開済み」型のガードは、手順書で X を設定する手順番号と Release の手順番号を見比べてから書く** (X は Release の 5 手前だった)。公開日時は人が渡す引数でなく機械的な出どころ (App Store lookup の `currentVersionReleaseDate`、鍵不要) を curl で実走してから採る。**upload 機構を共有する新 endpoint は、再開の一致条件 (`:315`) と active 枠の数え方 (`ownerUsage`: chunk 0 の未完 manifest も active) を開き、中断 N 回で枠が詰まる経路をトレースする** (2026-10-16)
37. **「平文を消さず別置きにする」設計で、DB を見ない掃除 (purge) と DB を見る掃除 (sweep) の両方が走る環境では、鍵が要らない「退避」段を切替直後に置き、purge が走査しないディレクトリへ rename する。rename は mtime を保つので、sweep の mtime 猶予は退避の窓を守らない — 参照集合を退避先の twin で閉包する** (bloom 0.2.3 平文投稿 R2、2026-10-16)。同じ回: **Leader の判断に「掃除は完了まで回さない」型があったら、その掃除の仕事 (旧クライアントの仕掛かりの削除) が「流入前にしか安全にできない」ものでないかを前回のレビュー指摘 (Codex B2) と突き合わせてから受ける** — 期限なしの変換は Release 後に跨るので両立せず、退避段を足して反論した
38. **「ファイルを作ってから tx で行を CAS」型の変換 CLI は、ファイル生成が tx の外にある時点で行ロック・共有 advisory lock (`_shared` は共有同士を排他しない) では同時実行を守れない — プロセス単位の排他 (`pg_try_advisory_lock` の session lock、2 本目は `refused`) を取り、tmp 名に run id を入れて残骸の帰属を分ける** (bloom 0.2.3 平文投稿 R2、Codex BLOCKER、2026-10-16)。同じ回の 3 点: (a) **「最新 N 件から条件に合う 1 件を探す」検証は「条件で絞ってから N 件」に書き換える** — 条件 (key_id) が封筒の固定 offset にあるなら SQL の `substring` で絞れる。(b) **「未検証でも処理して後で人が確認」は、処理の生成物が次の検証の候補になるなら自己検証ループ** — 未検証は処理しない、落ちた印は削除して ask に戻す、端末側は拒否された鍵の id を記録して再送しない、まで 1 組で書く。(c) **`-group` 等の絞り込み引数を持つ CLI の最終行は、各カウンタが「対象範囲」か「全体」かを 1 つずつ明記し、終了判定 (seed 撤去等) に使う値は全体に固定する** — 絞って回した run の 0 を全体の完了と読む手順書を書いていた
35. **先に書いた下流 doc の境界案は、上流が着地したら『書いた案』でなく『着地したコード』を grep して残りを出し直す。** bloom D2 U2 は C の設計前に書いた presence `usual` トークン方式のまま残っていたが、C U3 が `place_tokens` / `SamePlaceKindNear` / `SuppressProximity` / `sync` を実装済みで、残りは `at_usual` の計算・既定配線・呼び出し元・wipe の取りこぼしだけだった。上流の制約が下流の上限とぶつかっていないかも同時に見る (C の主キー `(user, group, kind)` は D2 の「各 3 件」と衝突 → 要求全体 422)。上流のテストが hook を自前で渡している間は、本番では誰も配線していない — 既定配線の置き場を決めてからテストの作法を書く (2026-10-15)
39. **「検証に落ちたら二度と送らない」型の端末側ガードは、落ちた原因が端末の値でなく「サーバー側の判定材料」(候補集合) にもあり得ないかを問い、材料の世代 (候補 id の指紋) を応答に載せて世代が変われば解除する形で書く** — bloom 0.2.3 平文移行 R3 で key_id だけを拒否記録にし、メンバーが混ぜた偽暗号文 1 件で正しい鍵が全端末から永久に再送されない穴を Codex に MAJOR で指摘された (2026-10-16)。同じ回の 2 点: (a) **「読んで検証してから UPDATE」の CAS の版は、新しい列 (`rev` / `updated_at`) を足す前に、行に既にあるランダム値 (sealed box の `sealed` 等) で足りないかを見る** — 連番は DELETE → INSERT で 0 に戻り、`updated_at` は同一 ms で衝突する。(b) **同じ URL で中身の表現が変わる設計 (平文 → 暗号文) は ETag でなく URL に表現世代 (`?v=<内容由来の hash>`) を載せる** — `max-age` の鮮度キャッシュは同じ URL に再検証しない。世代の値は「戻して作り直す」経路でも変わるもの (`media_id` は再変換で同じ `pid`、`dek_wrap` の hash は毎回違う) を選ぶ。先に `thumb_url` 等を完全一致で固定している既存テストを grep して置換表に載せる (E2E bundle のテスト 3 本)。**「平文 / E2E どちらの投稿を作るテストか」は helper 名で決めず中身を開く** — `uploadPost` は名前と裏腹に `e2ePostFixture` を呼んでおり、AF2 を「平文なので不変」と書いて Developer に直された (R5)。(c) **ファイル欠損を「行単位で済んだ扱い」にする規則 (`stash_missing`) を書いたら、入力の親 (DATA_DIR) ごと無い場合に全行が同じ経路に落ちて後段の破壊的処理 (purge) の前提を満たしてしまわないかを問い、入口のガード (`data_dir_missing`) を分けて書く** (Reviewer 指摘、2026-10-16)
40. **「N 箇所が全部 rebuild / 全部 watch している」型のブリーフは、N の行を grep で全数の表にし、各行に処置 (select / ヘルパ / 変更なし) と理由を付ける。** `ref.watch(p).field` は select ではない (全体を watch している) ので、ブリーフが「select 済み」と見なしている行を疑う。Researcher の「invalidate で unmount する」は riverpod の `core/element.dart` を開いて refresh と reload を分ける — `invalidate` は refresh で `when` が既定で loading を飛ばし、壊すのは依存 (`ref.watch(x.future)`) の再計算だった。既存の防御 (`pathBetween` の迂回ガード等) が既にあるかも同時に確かめる (2026-10-19, bloom 0.2.4。pattern/riverpod3-live-path-isolation-and-hold-previous-value.md)。**ブリーフが指す修正 (新 ImageProvider 等) は先に `grep -rln <型> test` で波及を数え、規模次第の項目は 0.x+1 送りを理由付きで書く**
42. **移行ガイドの「利用側」grep は、ローカルの PJ ディレクトリが実体かを `ls -la` で確かめてから信じる。** nexom 1.2.0 の移行表を書くのに `Developments/aisaba_platform` を grep したら 0 件だったが、中身は存在しないパスへの dangling symlink (iCloud 退避の跡) だった。0 件は「利用箇所なし」でなく「ディレクトリが空」。GitHub を scratchpad に `gh repo clone <repo> -- --depth 1` して grep し直し、利用側の実体 (`AuthService(AUTH_DB, AUTH_LOG)` の位置引数呼び出し) が判って互換性マトリクスと upgrade 順序 (アプリ先・auth 後) が書けた。**互換を切る引数変更では、新サーバー×旧クライアント / 旧サーバー×新クライアントの 2 マスを必ず埋め、どちらが先に上がるべきかを移行節の冒頭に書く** (2026-10-21)
44. **デプロイ手順を書くときの 4 つの grep / head** (aisaba 1.2.0 で Codex に 9 MUST を食らった束): (a) venv を rename で切り替える前に `head -1 <venv>/bin/gunicorn` — shebang が絶対パスなら rename 方式は全サービス起動不能 (最終名で作って symlink)。(b) 共有 nginx include を触る前に `grep -l <include名> gateway/*.conf` — 対象外の vhost (Coolify / appily) が 4 本使っていた。(c) テスト fixture で FW の DB 層を別スレッドから叩く前に `grep check_same_thread <db層>` — 無ければサブプロセス。(d) 「ロールバック = バックアップ復元」と書く前に「書き込みが再開した後の新規行はどうなるか」を問う — 書き込みを閉じた検証窓 + コミット点を切り、以後は前進修正と明記する。加えて root の `sudo python` で取ったバックアップは root 所有になる (サービスユーザーで取る)、追跡化したディレクトリの復元は `git checkout 旧` の **後**。第 2 パスでさらに 2 件: (e) nginx の include を足す前に `grep include /etc/nginx/nginx.conf` で **glob の文脈** を見る — `gateway/*.conf` が http 文脈で読まれていると、vhost 用に置いた `if` 入りファイルが glob にも拾われて `nginx -t` が落ちる (サブディレクトリに逃がす)。(f) 切替中に書き換える状態 (保守 ON/OFF) を追跡ファイルに持たせない — 未コミット変更になって `git checkout` が双方向で拒否される (リポジトリ外 + 0 件一致可の wildcard include) (2026-10-22、pattern/shared-venv-breaking-upgrade-cutover.md)

56. **「network を分けたので到達不能」を保証として書かない。** ホストの Docker が `iptables: false` だとブリッジ間隔離も `internal: true` も無効で、Phase 0 の実測 (他 network のコンテナから TCP が通る) で初めて分かった。保証に使えるのは `network_mode: none` のように interface 自体が無いものだけ。それ以外は「到達されても拒否される層」(pg_hba のサブネット限定、内部 API の送信元 IP 検査、edge 認証) に置き、受入は「到達不能」でなく「拒否の文言 (`no pg_hba.conf entry`、404)」と、同じ操作を許可側から行うと別の文言になる負のコントロールで測る。同じ回: **自分が書いた healthcheck と peer uid 検査のような「自己検査が自分の防御に弾かれる」矛盾は、コンテナ内で誰の uid で何が接続するかを全員分表にして洗う** (signer の HEALTHCHECK は 10003 で自分の socket に入る)。**volume の初期所有者は root** なので、`user:` を非 root にする service は Dockerfile で所有者付きのディレクトリを用意する (2026-10-26, ais-pass go-rewrite R1)
58. **設定ファイルを symlink で差し込む / 移す設計の前に、`grep -rn "__file__" <config 群>` で自分の位置からパスを導出している config を探す。** aisaba の compose 化で config を image に symlink で焼く案を書きかけ、`applications/calender/config.py` の `Path(__file__).resolve().parent` が symlink 先 (`/etc/...`) に化けて TEMPLATES_DIR が壊れると気付いた (ファイル単位の bind mount に変更)。同じ回: **ブリーフの理由を解き直して「並走でよい」と逆張りするときは、その安全性が本番に書き込んだ後でしか確かめられない形になっていないかを問う** — 「同じファイルの SQLite を複数プロセスが書くのは既存の複数 worker と同じ」と書いて旧 / 新の並走を推したが、ファイルログの RotatingFileHandler の rename 競合を見落とし、判定も事後になるので Codex に退けられた。停止が数分で許容済みなら、ビルドを停止前に終わらせる「保留起動」(env で app を起動しない) で停止の幅を詰める方が筋だった。**「loopback + allow 127.0.0.1」で守られていた到達制限は、共有 reverse proxy の背後に移した瞬間に崩れる** — 移植表に「その制限の代替」の行を必ず作る (2026-10-29、pattern/host-service-to-compose-shared-bind-cutover.md)
60. **点列の補正規則 (外れ値・平滑化) は、doc に書く前に scratchpad へアプリをコピーして規則を差し込み、既存の補正テスト一式を回す。** 手書きの合成例が全部期待どおりでも、既存の「基準の一日」fixture で壊れる規則は多い — bloom 0.2.5 の時間外挿 Hampel は徒歩 → 電車の角と 40 秒停車を消し、RP-1/RP-2 を赤にした (合成の直角・飛び点では無害だった)。片側ずつ外挿する形に変えて基準日 0 点・赤は意図した 3 本だけになった。さらに「片側 3 点」で判定させた短い列では、飛び点 1 つで Theil–Sen が崩れて**正しい隣の点**が消えた — 頑健推定の破綻点 (何点中何点まで汚れてよいか) を窓の最小点数に反映する。doc の例の数値は実走した値だけを書き、実走していない例 (「規則からこうなるはず」) は実走してから書く (4 行中 2 行が外れていた) (2026-10-29)
57. **管理画面のホストに Access (edge 認証) を付ける設計は、そのホストを「人以外」が叩いていないかを先に全アプリの env で grep する (`*_API_BASE` / `*_URL` の値のホスト部だけを抽出し、値そのものは出さない)。** aiserver2 で coolify.aisaba.net に Access を付けかけ、wasawasa の `COOLIFY_API_BASE` と Muraki の appily SKILL が公開経由で `/api/*` を叩いていると気付いた。付けた瞬間にデプロイ基盤が止まるところだった。path ごとの app (暫定 Bypass → 呼び出し側のヘッダ対応 → Service Auth) に段階を割った。**webhook の送信元 (GitHub) は任意のヘッダを付けられないので、Service Auth は使えない** — path を限った Bypass + WAF の送信元 IP 制限 + アプリ側の HMAC で組む。同じ回: clone で uuid が変わる移行は、その uuid を自分の env (`COOLIFY_SELF_APP_UUID`) や他システムの DB (wasawasa の登録) に持っている者を数えてから手順を書く (2026-10-29)
59. **「上限 N → M」の要望は、`> N` の検証を grep するだけでなく「N 件に比例して膨らむもの」を全部数える: 本文上限 (`bodyCap`)・WS の read limit と 1 メッセージの件数・`scrollable: false` のシート・折り返し上限の無い行。** bloom の所属上限 4 → 10 で、Researcher の報告 (定数 1 + ハードコード 2) の外に WS `pos2` の「items ≤ 4」(サーバー) と「4 件で打ち切り」(端末)、read limit 4096 (アプリの実寸で 10 件が 4.5 KB)、非スクロールの投稿先シート (11 行 × 52pt で SE のシートを超える) があった。サイズは scratchpad で最大形と実寸の両方を JSON にして測る。**「N+1 件 → 422」のテストは本文上限の内側に収まっているか** (外なら 413 になって検証まで届かない) も同時に見る。同じ回: Riverpod の再試行回数は成功でも戻らず `asReload: true` / 依存の変化でしか戻らない (`library/riverpod-3-retry-and-selectasync-semantics.md` What 5) — 復帰の invalidate は `asReload: true`。Researcher の「uuid X はデプロイ uuid」は、同日のインフラ移行 (clone で uuid が変わる) と突き合わせると「旧 app uuid」だった — 理由が違うと置換の範囲 (prod だけか全環境か) が変わる (2026-10-29)
60. **「端末内だけに残す」と書く前に、そのログ API が遠隔へ流す枝 (breadcrumb / remoteSink) を持っていないかを定義まで開く。** bloom の `DebugLog.note` は `remoteBreadcrumb` を呼び、dev ビルドではその文が無加工で Crashlytics に出る。座標入りの例外文を「端末内だけ」のつもりで流す設計を Codex に BLOCKER で止められた — ローカル専用の API (`noteLocalOnly`) を足して経路を分け、テストは非致命と breadcrumb の両方を捕まえて座標・ID が無いことを見る。同じ回: **「失敗したら N 回まで修復」は、回数を戻す条件を「検証つきの成功」に置き、修復を起こさない失敗 (付随レイヤ) を分ける** — 構築直後の付随更新が毎回失敗すると、構築成功で回数が 0 に戻って無限に回る。ユーザーの観測 (「N マス」と出るのに塗りが無い) は provider 層と描画層のどちらが原因かを一発で分けるので、Researcher の仮説の確度順より先に「その観測で真になる層」を引く (2026-10-29)
61. **「機能 X を消す」設計では、X が自分の外 (OS のストア・サーバー・他ユーザーの画面) に書いた状態を全部表にし、「消す経路が残るか」を 1 行ずつ確かめる。** atender build 21 で個人予定の書き出しを剥がすと、planner は `prunableKinds` に入らない kind を消さないので、build 20 が Atender カレンダーに書いた個人予定が永久に残るところだった (kind を掃除用に残し、一度きりの移行で ±730 日を一掃)。サーバー側のミラー (EventKit 読み込み) とルームへの共有も「iOS から OFF にできない」まま残るので、データ削除として Touri 判断に上げた。同じ回: **Researcher の「UI は存在しない」も grep で確かめる** — 削除済みの画面とは別に、設定シートの中に「押すと必ず 409 になって `try?` で成功表示する」取り込みボタンが生きていた。**Swift の DTO に Optional を足すときは `var x: T? = nil`** (`let x: T?` は memberwise init で省略できず、既存の呼び出しとテストが全部コンパイルエラーになる) (2026-10-29)
62. **「背景で記録が途切れる」型の dump は、空白の原因を推す前にバーストの始まりごとに「起こした行」(slc / visit の行) があるかを見る。** 起点の行が無いバーストは前景復帰 (アプリを開いた) が起点で、OS のサスペンドとも停止条件とも別の現象になる。bloom 0.2.5 で「visit 到着停止 / サスペンド / 2 fix 停止」の 3 候補を渡されたが、行を読むと 3 つとも効いていた (departure で理由が付いたのに 258 秒 fix が来ない = 背景で始めた測位が続かない)。1 つに絞れない時は全部を 1 回で直し、**どれが効いたかを分ける観測 (開始・停止の理由ログ) を同じ設計に入れて段 2 の判断基準を数値で書く**。その観測は背景で Dart が止まっていても残る置き場 (Swift が書く端末内ファイル) にする — `DebugLog` はメモリ上で、背景で消える。同じ回: OS の「新 API」(CLBackgroundActivitySession) の挙動は SDK の header (`Platforms/iPhoneOS.platform/.../CoreLocation.framework/Headers/*.h`) と `.swiftinterface` を読むと、Researcher が拾えなかった規則 (前景でしか有効にならない・背景起動では即作り直せば再開) が書いてある。**ヒアドキュメントに `&&` を含むコード (Dart / Swift) を入れると Bash の && 禁止フックに止められる** — 試作のファイルは Write で書く (2026-10-30)
63. **外部 URL の「200」を、リンク先のファイルが実在する根拠にしない。** SPA の nginx (`try_files $uri $uri.html /index.html`) は未知パスも 200 で index を返す — atender.appily.run の `/support.html` 等は `public/` の実ファイルを `ls` して初めて言える。同じ回 (atender LP): **画像の「縮尺に合わせた値」(影・線幅) を表に書くときは、倍率の分母 (原寸幅) を素材ごとに列にしてから割る** — hero と直立端末で原寸が 2096 / 1070 / 517 と違うのに 1 つの倍率で書きかけた。**nginx の設定を doc に載せる前に、本番と同じ `docker run` オプション (`--read-only --tmpfs /tmp --cap-drop ALL`) で scratchpad の image を起動し、挙動仕様の全パスを curl する** (5 分で済み、`try_files $uri/` が 403 を返す類の差がその場で分かる) (2026-10-30)
63. **外部 API の「成功の値」(202 の status 列挙等) は knowledge やブリーフでなく相手のコードの型 union (`AttemptResult['status']`) で確かめる** — AIS Mail は 202 で `failed` (二度と送られない) も返し、Researcher の列挙にもブリーフにも無かった。字面どおり「202 は成功」と書くと握りつぶしを別の形で再導入する。同じ回: **失敗を「500 で表に出す」と決めたら、ライブラリがその例外を何の body で返すかを実走し、配布済みクライアントのデコード経路 (iOS `ErrorResponse`) まで追う** — better-auth のコールバックで素の Error を投げると body 空の 500 で iOS は「HTTP 500」しか出せず、`APIError` に API の封筒を詰めると無改修で日本語が出た (pattern/better-auth-send-callback-fail-loud-with-envelope.md)。**相手が同期で N 秒待つ API にタイムアウト N 秒を付けるブリーフは、相手の待ち時間をコードで引いてから受ける** (2026-10-30)
