# Developer の職業的習慣ノート

召集されたら最初に読む。**過去の自分 (歴代 Developer) が実際に踏んだ穴**であり、予防的な網羅ルールではない。新しく踏んだら自分で追記・置換する (INDEX 対象外、再生成不要)。

- **Codex は同期実行のみ。バックグラウンド委譲・「監視タスクを設置した」報告で終了は禁止。** subagent が終了すると Codex プロセスは孤児化し実装が途中で止まる。完了まで待ってから報告する (再発4回: sessions/2026-06-02 ×2, 2026-06-08, 2026-06-11)
- **`codex exec` をパイプ/リダイレクト付きで走らせる時は `< /dev/null` 必須。** stdin 待ちで 30 分ハングした実績 (tool-quirk/codex-exec-background-needs-dev-null-stdin.md)
- **完了報告の前に worktree 内で typecheck / build を自分で走らせて pass を確認する。** 「Codex が完了と言った」は完了ではない。NodeNext 50+ エラーを Leader の pre-flight で初めて発覚させた実績 (sessions/2026-05-26)
- **researcher の version 列挙を無検証で package.json に転記しない。** install が通ることまでが自分の仕事。架空 version で `npm install` 全滅の実績 (sessions/2026-05-26)
- **`codex` が PATH に無いことがある (cask 実体が消える)。** `which codex` 失敗時は `/Applications/Codex.app/Contents/Resources/codex` を直接叩く。Caskroom の version dir が空でも app bundle 内に本体がいる (2026-07-04)
- **Go の自己検証は `go -C <worktree> build -o /dev/null ./... ; go -C <worktree> vet ./...` で。** Bash tool は呼び出しごとに cwd をリセットするので、worktree 外から `go build ./...` すると "directory prefix . does not contain main module" で誤って fail に見える。`cd` は permission prompt を招くので `-C` フラグを使う (2026-07-04)。**`-o /dev/null` を省くと main package のバイナリが worktree に落ちて `git status` に untracked で現れる** — `git add -A` する人が commit に混ぜる事故になる。検証後に `git status` を見て自分の生成物 (バイナリ / `.next` / `node_modules`) が残っていないか確認してから commit する (2026-07-16, omatase coolify-deploy で `apps/backend/omatase` が出た)
- **並走 slice で依存ファイル未存在のままフルビルド不能な時は、scratchpad に worktree をコピーし「仮定した契約」のスタブ (別ファイル名) を足して `go -C build/vet` で typecheck する。** worktree 本体にスタブを置くとマージ時に衝突するので絶対に置かない。「gofmt が通った」だけで報告しない (2026-07-05, dandan-app Slice2)
- **`go build`/`go vet` green は SQL の実行時エラーを一切捕まえない。** pgx で `$n - interval '...'` と書くと Postgres が `$n` を interval に型推論して 42883 (operator does not exist) になる — `$n::timestamptz` の明示キャストが要る。しかもエラーを `_ =` で握りつぶす best-effort 系 (last_used_at touch 等) だと本番でも沈黙する。DB を触る Slice は、実 PG が手元にあるなら 1 回スモークしてから報告する。Reviewer の「呼んでいない」診断も実際は「呼んでいるが SQL が死んでいた」だった — 帰属は計測 (エラーを一時的に stderr へ) で確定してから直す (2026-07-05)
- **codex sandbox はネットワーク不可 = localhost の DB 接続も `httptest` の listen も落ちる。** `go test` が `connect: operation not permitted` / `bind: operation not permitted` で fail しても実装バグではない。DB 依存テスト・ローカル起動確認は Codex に任せず Developer が worktree 外で自分で回す。同理由で vendored 資産 (htmx 等) の DL も召集前に済ませる (2026-07-05)
- **Codex をバックグラウンドで走らせても turn を「待機中」で終えない。poll で待ち切って報告まで出す** (2026-07-05, 07-08 に2回発生)
- **goose の SQL migration で `DO $$ ... END $$;` ブロックは `-- +goose StatementBegin` / `-- +goose StatementEnd` で囲まないと "unterminated dollar-quoted string" で実行時死する。** go build/vet では捕まらない。migration を書いた Slice は goose CLI (`go install github.com/pressly/goose/v3/cmd/goose@latest`) + 実 PG で Up/Down/Up を回してから報告する。Down も「新スキーマで合法になったデータ (unique 撤去後の重複行等) が旧制約の再作成を 23505 で壊さないか」まで見る (2026-07-08, dandan-app Slice1)
- **Codex は「可能な範囲でテスト移植」を「移植ゼロ + 理由書き」に倒しがち。また「不変」契約の additive ツールでも文言を勝手に簡略化する。** テスト移植は配置先・流用ハーネス・skip 条件まで指定した専用ラウンドに分け、「不変」資産は完了後に旧実装と文言レベルで diff 突合する (2026-07-08, dandan-app Slice2: check_repo のメッセージ書き換えと天野テスト移植スキップを round 2 で回収)
- **headless Chrome の `--dump-dom` + `--virtual-time-budget` は、ページが timer や fetch を回し続けると Chrome が終了せず `cmd.Output()` が永久ハングする** (go test 600s タイムアウトで発覚)。UI スモークは「ページ側から fetch で Go 側の /report にログを POST → テストは poll して成立で `exec.CommandContext` を cancel (kill)」の report-back 方式にする。Chrome の自然終了に依存しない (2026-07-08, dandan-app Slice3 uihost)
- **worktree が iCloud(`~/Documents` 配下)にあると、そこへの rsync が offloaded(dataless placeholder)ファイルを黙って取りこぼす。** `__init__.py` や `migrations/*.sql` が copy 先から欠け、Python が package を namespace 扱い(`agenthub.__file__ is None`)して `ModuleNotFoundError: No module named 'agenthub.app'` になる。しかも1回目の rsync は exit 1 で部分成功。対策: コピー後に `find <orig> -name '*.py' | wc -l` と copy 側を突合し、欠けたら rsync を再実行してから検証する。検証 venv は必ず iCloud 外(scratchpad = /private/tmp)のローカルディスクに置き、editable install も local copy を指す(Documents 直 install は import が間欠ハング)(2026-07-09, agent-hub RED 修正検証)
- **DB を触る Slice の実 PG スモークは、既存の test コンテナを先に探す。** `docker ps | grep pg` で Leader/Reviewer が立てた `*-test-pg`(例 port 55433, POSTGRES_PASSWORD/DB は `docker inspect ... .Config.Env` で取得)が生きていることが多い。ローカルに psql/postgres が無くても docker 越しに `TEST_DATABASE_URL` を組めば pytest も直スモークも回せる。SQL 型バグ(`$n::timestamptz` 欠落等)は静的検査で捕まらないので、middleware が毎リクエスト呼ぶ経路(touch 系)は実 PG で認証済みリクエストを1回通して 500 が出ないことまで見る(2026-07-09, agent-hub Bug A: touch_session が全認証500だった)
- **`xcodegen generate` は `project.yml` `info.properties` に無いキーを、生成される `Info.plist` から黙って落とす。** commit で Info.plist に手足しされた `ITSAppUsesNonExemptEncryption=false` (TestFlight 暗号化質問スキップ用) が xcodegen 実行で消えた。ビルド検証で xcodegen を回すと working tree にこの regression が乗る。対策: xcodegen 後に `git diff -- Info.plist` を見て、手足しキーの脱落を確認する。落ちていたら (a) 自分の scope 内なら restore、(b) 恒久対策 (project.yml へ移設) は scope 外なら Leader へ上申。Info.plist に静的に置いたキーは次の誰かの xcodegen でまた死ぬ (2026-07-14, atender login-auth-revamp)
- **「daemon が無い」「環境が無い」は決めつけず 1 コマンドで確認してから CI に委ねる。** `docker info --format '{{.ServerVersion}}'` は 1 秒。前回「ローカルに docker daemon が無い」と決めて検証を CI に委ねた結果、`ENV HOSTNAME=0.0.0.0` (Node が IPv4 のみ bind → Coolify の in-container healthcheck が `localhost`→`::1` で Connection refused → 初回デプロイ確実死) を素通しし、Reviewer RED → 設計差し戻しまで往復した。実際は daemon は動いていた (`open -a Docker` で起動もできる)。設計 doc 逐語コピーで逸脱ゼロでも、**設計が実測で否定される前提を含んでいたら実装は死ぬ** — 手元で回せる検証を回すことは Reviewer の仕事の先取りではなく Developer の責務 (2026-07-16, omatase coolify-deploy)
- **コンテナの疎通検証は「ホストから `-p` 越しに叩く」で済ませない。ホスト側プローブは bind stack のバグに対して常に緑になる。** 実測: 同一イメージで `HOSTNAME=0.0.0.0` → `netstat` が `0.0.0.0:3000` (IPv4 のみ)、in-container healthcheck **exit 1**、しかしホストからの `curl` は **200**。`HOSTNAME=::` → `:::3000`、healthcheck **exit 0**、ホスト **200**。つまりホストプローブは両者を区別できない。本番の healthcheck がコンテナ内実行なら、検証も `docker exec` でコンテナ内から**本番と同じコマンドを逐語**で回す (host を `127.0.0.1` に「直して」はいけない。落ちる経路がそこ)。**加えて負のコントロールを取る** — `-e` で旧値に戻して fail することまで見て初めて「検証に歯がある」と言える。緑を確認しただけでは vacuous pass と区別がつかない (2026-07-16, omatase coolify-deploy)
- **worktree でなく main の作業ツリーで召集された時、Codex の完了報告に出る `M <file>` 一覧は「Codex が触ったファイル」ではなく `git status` の丸写し。** Leader が同じツリーを並行編集していると、触るなと言われたファイル (`CLAUDE.md`) が Codex の報告に modified として現れる。ここで「Codex が禁止ファイルを触った」と早合点して revert すると **Leader の作業を破壊する**。帰属は報告文でなく実体で判定する: (a) `ls -lT` の mtime を codex 実行窓と突合、(b) `git diff -- <file>` の内容が Codex への指示範囲か Leader の文脈か (Muraki knowledge パス参照・PJ 運用記述は Leader)。Codex 自身も「git status 上は modified ですが今回こちらでは触っていません」と正しく自己申告してきたので、報告文の読み方を誤らなければ事故らない (2026-07-16, omatase n-wasabi.org 追従)
- **設計doc に実装すべきコードブロックが逐語で載っている時は、`diff` で機械的に一致を確認する。** 目視で「同じっぽい」は確認ではない。設計doc (job 直下 4-space) と実ファイル (6-space) で indent が違うだけなら、共通 indent を剥がして正規化してから diff すれば逐語一致を exit 0 で示せる。「設計どおり実装した」を主観でなく検証結果として報告できる (2026-07-16, omatase n-wasabi.org 追従)
- **worktree は untracked ファイルを引き継がない → 「未追跡の死にファイルを削除する」設計タスクは worktree で実行不能。** 設計が Leader/Architect の**本チェックアウトの working tree** を見て書かれていると、削除対象 (`git status` で `??`) が worktree に存在せず、素直に従うと「無いファイルを消そうとする」→ Codex が**忖度して同名ファイルを新規作成してから消す**ような破滅的解釈をしうる。着手前に対象を 1 つずつ `git ls-files --error-unmatch <path>` で tracked 判定し、untracked なら「本 worktree では no-op」と確定させて Codex の指示に明記 + Leader へ上申する。同型で `rm -rf "Atender 2.xcodeproj"` (untracked な複製の物理削除) も worktree では no-op。**削除リストはワイルドカードで判断せず 1 ファイルずつ照合**する — 同ディレクトリに現役ファイルが混在する (atender の `components/today/` は 6 個中 4 個が tracked 現役、`MainAttendanceCTA.tsx` を消すとホーム CTA が壊れる) (2026-07-16, atender phase-e-p1)
- **負のコントロールのために一時的に HEAD へ戻す時、`git checkout HEAD -- <file>` は未コミットの実装を無警告で破棄する。** 「E0-5 を外して fail することを見る」ために `git checkout HEAD -- project.yml Info.plist` した結果、Codex が書いた実装ごと消え、設計 doc から手で再実装する羽目になった (幸い設計に逐語仕様があり復元できた)。退避は必ず **scratchpad へ `cp` してから** (`git stash` も worktree/ignore 状態が絡むと事故る)。検証で木を弄る時は「戻し方を先に用意してから壊す」。復元後は blob hash (`git diff` の index 行) で元と一致することまで確認する (2026-07-16, atender phase-e-p1)
- **`find <DerivedData> -name Atender.app | head -1` は平気で数か月前の stale bundle を掴む。** 「UIAppFonts が入っていない」と誤診しかけた (実際は Jul 9 の別 DerivedData を見ていた)。正しい dir は `xcodebuild -showBuildSettings | grep BUILD_DIR` で引く。ビルド生成物を検査する時は必ず mtime を印字して当日のものか確認する (2026-07-16, atender phase-e-p1)
- **`UIAppFonts` の値は「バンドル資源ルートからの相対パス」= 実質ファイル名のみ。`Resources/Fonts/X.ttf` と書くと黙って未登録になる。** xcodegen の `sources: - Atender` は .ttf を個別 resource として Copy Bundle Resources に入れるので、**ディレクトリ構造は保持されず .app 直下にフラットに落ちる**。設計doc が `Resources/Fonts/GoogleSans-Medium-Latin.ttf` と指定していたが、これは実測で誤り。未登録フォントは SwiftUI が**例外も警告も出さずシステムフォントにフォールバック**するので、ビルド緑・実行緑のまま「フォントだけ効かない」で通過する (atender の Inter が全画面で効いていなかった既存バグと同じ機序)。確認法: `xcodebuild build` 後に `ls <DerivedData>/.../Atender.app/ | grep ttf` で**実際の配置**を見てから plist 値を決める。`find $APP -ipath '*Fonts*'` が空なら階層は存在しない (2026-07-16, atender login-unify)
- **iOS Simulator は全エージェント共有のグローバル状態。並走 feature の agent が同じ sim に自分の .app を install で上書きしてくる。** 実測: 自分の build を install → 2分後にスクショしたら**別ブランチの UI** が写り、`Info.plist` の `UIAppFonts` も自分の 7 件でなく相手の 6 件だった (= 並走 P1 の build)。「実装が反映されない」と誤診して自分のコードを疑う事故になる。対策: **feature 専用 sim を `xcrun simctl create "<feature>-dev" "iPhone 16" <runtime>` で作って使い、終わったら delete**。検証前に `get_app_container` → `PlistBuddy -c "Print :UIAppFonts"` 等で**今 install されているのが自分の build か**を1回確認してからスクショを撮る (2026-07-16, atender login-unify)
- **`hdiutil attach` がハングする環境でも `hdiutil convert siwa.dmg -format UDTO -o raw.img` は通る。** ハングするのは kernel の attach/DiskArbitration 経路だけで、変換はユーザー空間で完結する。変換後の raw イメージ (`.cdr`) は mount せずに **PNG シグネチャ (`\x89PNG`) / `<svg` / `%PDF` を正規表現で走査して carve** すれば中身を取り出せる (PNG は IHDR から w/h、IEND までで切る)。Apple の `Logo-Sign-in-with-Apple.dmg` はこれで全 25 PNG + 8 SVG を抽出でき、SVG の `<title>` に `Left Black Logo Medium` 等の**正式名が入っている**ので size 選定の一次情報になる。Architect/Leader が「mount できない = 寸法未検証」で止めた項目を Developer が確定できる。**mount 固執で時間を溶かす前に convert を試す** (2026-07-16, atender login-unify)
- **SwiftUI で `.foregroundStyle()` を `Text` にだけ付けると、同じ HStack の SF Symbol は既定色 (黒) のまま残る。** bitmap 資産 (`Image("...")`) は foregroundStyle の影響を受けないので、Apple/Google のようなロゴ画像ボタンでは露見せず、**SF Symbol を使う 1 つのボタンだけが黒いまま**という形で出る。ビルドもテストも緑。**SF Symbol を 20x20 の枠に収めたいなら `.font(.system(size:18))` ではなく `.resizable().scaledToFit().frame(width:20,height:20)`** — font 指定だと envelope.fill は実測 21.67pt 幅になり枠からはみ出して中央寄せされ、左端が他ボタンのロゴと 1.33pt ずれる。**スクショのピクセル実測 (3x なら 1pt=3px) でしか捕まらない** (2026-07-16, atender login-unify)
- **`codex exec` の既定 sandbox は read-only。書き込みは `-s workspace-write` を付けないと全部拒否される。** しかも Codex は**エラーで落ちず exit 0 のまま「実装しました」に近い体裁の説明文を返す** (実際は `patch rejected: writing is blocked by read-only sandbox`)。出力の tail だけ見て完了扱いすると**ファイルがゼロなのに完了報告**になる。召集後は必ず `git status` / `find` で**実体の存在**を確認してから次へ進む (2026-07-16, nwasabi-hp scaffold)
- **zsh に `PIPESTATUS` は無い (zsh は `$pipestatus`、小文字)。** Bash tool の shell は zsh なので、`cmd | tail; echo "exit=${PIPESTATUS[0]}"` は**空文字**を吐く。「exit=」とだけ出たのを緑と読むと、検証したつもりで exit code を一度も見ていない報告になる。**exit code を報告に載せる検証はパイプを使わず** `cmd > log 2>&1; echo "exit=$?"` で取る (2026-07-16, nwasabi-hp scaffold)
- **設計docの「破壊テスト」手順は、そのまま実行しても破壊にならないことがある — 実行前に「それは本当に赤くなるか」を考える。そして予測色は docroot の所有者が変わると反転するので、旧設計での実測を新設計に持ち越さない。** nwasabi-hp の設計は S12 表で `COPY . .`、Reviewer 注記で `COPY . /usr/share/nginx/html/` と**同じテストを 2 通りに書いていた**。前者は nginx イメージの WORKDIR が `/` なのでファイルは `/README.md` に落ち、docroot の外 → 漏れない。★ **ただし「漏れない」と「smoke が緑」は別物**。docroot を自前ディレクトリ (`/var/www/site`) に移設した後は、`COPY site/ /var/www/site/` を `COPY . .` に**置換**すると docroot **ごと消える** (`ls: /var/www/site/: No such file or directory`) ので `/` → 404 で **smoke は赤 (exit 1)**。設計docは「緑のまま」と書いていたが実測で偽だった。緑になるのは `COPY . .` を**追加**した場合 (`COPY site/` を残す) だけで、**「置換」と「追加」は別のミューテーション**。設計の「書き換えて」を字義通り実行して予測と食い違ったら、両方の変種を実走して**どちらの読みで予測が成立するかまで切り分けてから**上申する — 「設計が間違い」より「設計の語が曖昧」の方が正確な報告になることが多い。負のコントロールは「守りを外したら**実際に赤くなった**」まで見て初めて意味を持つ。設計に手順が 2 通りあったら**赤くなる方を採り、不備として上申**する (2026-07-16, nwasabi-hp scaffold / docroot 移設)
- **Leader から渡される「肯定的」前提 (「API は健全」「原因はクライアント側」) も、否定的主張と同じ強度で独立検証する。** CLAUDE.md が明示するのは「否定的主張を検証なしで受理するな」だが、**肯定的前提の誤りは調査方向をまるごと誤らせる**ぶん害が大きい。atender の web ログアウト不能は「API は 204 を返し Set-Cookie も正しい = API は健全、原因は client」という前提で召集されたが、実際は API の手書き sign-out が原因だった。**Leader の probe は「セッション無しの curl」で、返ってきた `Set-Cookie` の cookie 名を本物の cookie 名と照合していなかった** (本物は `__Secure-` prefix + `Domain=` 付き)。**「認証系エンドポイントが cookie の有無に関わらず同じ応答を返す」は健全さの証拠ではなく、そのハンドラが何もしていない徴候**として読む。触るなと言われた領域が原因だと実測で判明したら、勝手に直さず実測根拠を添えて上申する (認証・セッション削除は CLAUDE.md のエスカレーション対象) (2026-07-16, atender fix/web-logout)
