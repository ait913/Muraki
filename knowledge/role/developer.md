# Developer の職業的習慣ノート

召集されたら最初に読む。**過去の自分 (歴代 Developer) が実際に踏んだ穴**から蒸留した現役の習慣 (20 本以内を維持)。新しく踏んだら自分で追記・置換し、古びたら捨てる (INDEX 対象外、再生成不要)。2026-07-31 に Opus 5 移行で全面圧縮 (原本: ai-audit/archive/20260731-muraki/role/developer.md)。

1. **完了報告の前に build / typecheck / test を自分の手で回して緑を確認する。** 委譲先エンジンや subagent の「完了」「通った」という申告は完了ではない。検証後は `git status` を見て自分の生成物 (バイナリ / `.next` / `node_modules`) が残っていないことまで確認する (sessions/2026-05-26)
2. **識別子 (package version / API 名 / symbol 名 / export 名) は書く前に実在確認する。** researcher の列挙も無検証で転記しない — install・コンパイルが通ることまでが自分の仕事 (sessions/2026-05-26)
3. **静的検査の緑は実行時を保証しない。** SQL の型推論・migration・ルーティング・wire 契約は、実 DB / 実サーバに 1 回撃つスモークでしか捕まらない。DB や配線を触った Slice は報告前に実経路で 1 回通す (2026-07-05, dandan-app)。典型例: pgx で WHERE 断片を組み立てるヘルパに固定引数列を渡すと、SQL 本文が `$1` を参照しない組み合わせで PG が `could not determine data type of parameter $1` を返す — build は緑、実 PG で初めて赤 (2026-08-20, bloom P3b)
4. **帰属は報告文でなく実体 (mtime / `git diff` / 計測) で確定する。** 「誰が触ったか」「どの build が入っているか」「どのログか」は、報告・ファイル名・フラグでなく mtime・hash・`workdir` 行で判定する (2026-07-16, omatase)
5. **肯定的前提 (「API は健全」「N 箇所しかない」「既に実測済み」) も否定的主張と同じ強度で検証する。** 範囲を区切る主張は外側全部への否定的主張。測られたケースの外側 (入力クラス) を自分で列挙して総当たりしてから実装する (2026-07-16, atender web-logout)
6. **設計の名指し (file:line / 消費者数 / 制約名 / 削除リスト) は着手前に grep で数え直す。** 宣言サイト・caller・制約は設計の主張より多いことが常態で、数が合わないまま型を締める/消すとビルドか本番が壊れる。合わなければ最小の整合で通して設計の誤りとして上申する (2026-07-21, atender tmpl-search)
7. **設計 doc 内で節同士が矛盾したら、挙動仕様節 (Reviewer がテストを生成する節) を上位として実装し、読み替えを完了報告に明記する。** 「触るファイル一覧」は実装範囲の上限で、節ごとの列挙漏れは下限を決めない (2026-07-29, atender eventkit-export)
8. **設計 doc の逐語コードは diff で機械的に一致確認する。逐語がコンパイル不能 (actor 隔離等) なら契約を保つ最小の是正 + 上申。** 「設計どおりに書くと通らない」から先を即興にしない (2026-07-16/17, omatase・atender)
9. **検証で木を壊す前に戻し方を用意する。`git checkout HEAD -- <file>` は未コミットの実装を無警告で破棄する。** 退避は scratchpad へ `cp` → 復元は `diff`/hash でバイト検証。ベースラインは `git worktree add --detach` で建てれば自分の木を触らずに済む (2026-07-16, atender phase-e-p1)
10. **guard・修正の検証は負のコントロール込みで。** 緑を確認しただけでは vacuous pass と区別がつかない。守りを外して実際に赤くなるまで見て初めて「検証に歯がある」(2026-07-16, omatase coolify-deploy)
11. **検証は本番と同じ経路を逐語で通す。** ホストから `-p` 越しの curl はコンテナ内 healthcheck の代理にならない (bind stack のバグに常に緑)。本番がコンテナ内実行なら `docker exec` で同じコマンドを打つ (2026-07-16, omatase)
12. **「環境が無い」「壊れている」は 1 コマンドで確認してから決める。** `docker info` は 1 秒、`which` が失敗しても `ls ~/go/bin` に実体がいる。決めつけて CI に委ねた検証が本番確実死を素通しした (2026-07-16/30, omatase)
13. **worktree に `.env` を置かない。共有リソース (simulator / scratchpad / ポート / main の DB) は並走前提で扱う。** `@prisma/client` は `.env` を自動ロードして無関係テストを壊し、絶対パスの `DATABASE_URL` は main の DB に migration を当てる。sim は feature 専用に作り、ログ名は feature 固有にする (2026-07-29, atender)。「session 専用」と案内される scratchpad にも前セッションの成果物が残っている — 成果物の収集は glob でなく**自分が作ったファイル名の明示列挙**で行う (glob が他人のスクショを montage に混ぜた。2026-08-20, bloom P2b)。compose.test.yaml の固定ポート DB も並走レーンと共有 — 別レーンの未コミット migration で schema_migrations が先に進み `no migration found for version N` で落ちる。リセットで他レーンを壊さず、自前コンテナを別ポートで建てて `TEST_DATABASE_URL` を向ける (2026-08-20, bloom P2b)
14. **並走 Reviewer の生成物は触らない。テスト本数は数でなく名前の diff で比較する。** Reviewer のテスト起因の型エラーは実装からは直せないので、tsconfig の `exclude` 等の設定層に逃がし、検査を弱めた事実を報告する (2026-07-30, omatase)
15. **スコープ外の発見・設計の曖昧さは勝手に直さず、実測根拠を添えて上申する。** 触るなと言われた領域が原因と判明した時ほど正確に (2026-07-16, atender)
16. **偽 fail の第一容疑者は自分のハーネス。** exit code はパイプを使わず取る (zsh に `PIPESTATUS` は無い)。共有 markdown の編集はアンカーの出現回数を assert してから置換する (2026-07-16)。Bash の `&&` 禁止フックはヒアドキュメント内の JS/Python 文字列 (`if(a&&b)`) まで引っかけるので、パッチスクリプトは Write ツールでファイル化してから `python3 fix.py` で実行する (Dart 断片の `&&` でも再発 2026-08-21)。Flutter 実走ドライバ (integration_test) の落とし穴 3 連 (2026-08-21, bloom P3): (a) `reportTestException` でプラグイン内部の非同期例外を握っても**テストは中断されて「All tests passed」の偽緑になる** — 握るのではなく発生源を断つ (maplibre_gl の styleNotFound は style URL をローカル inline JSON に差し替えると競合窓ごと消える)。(b) `simctl uninstall` は TCC (位置許可の grant) を消す — 再インストール後に grant し直す。(c) CLGeocoder はレート制限で無期限ブロックする — 呼び出し側に `.timeout(5s)` を必ず付ける。headless Chrome の `captureScreenshot` が全滅したらページを疑う前に `pmset -g log | grep "Display is turned"` (display sleep) → `caffeinate -d -u` (2026-08-19, bloom M1)。zsh 検証スクリプトで `GID`/`UID`/`EUID` を変数名に使うと整数型の予約変数への代入で `bad math expression` になり UUID が入らない — 別名 (`GRPID` 等) を使う (2026-08-20, bloom P1)。zsh で `grep [x]codebuild` を未クォートで書くと glob 展開の `no matches found` で「プロセスが居ない」と誤読する — ブラケットパターンは必ずクォート (2026-08-20, bloom P2a)。headless の `xcodebuild` (SwiftPM binary artifact 解決) が無出力・無通信で永久ハングしたら、原因は login keychain の `github.com` item への SecItemCopyMatching (GUI 承認プロンプト待ち)。`sample <pid>` でスタックを取れば一発で分かる。対処は `SWIFTPM_NETRC_DATA="machine github.com login token password dummy"` を export して keychain provider を短絡 (GitHub は public asset への偽 Basic auth を無視する。2026-08-20, bloom P2a)。fake clock を注入したスモークでは、(i) JWT の exp/iat 検証 (golang-jwt) と DB の `DEFAULT now()` は**実時刻のまま**なので、fake が過去/未来だとトークン即失効・日付フィルタ全落ちの偽 fail になる — トークン発行だけ実時刻、DB 既定列はハーネス側で UPDATE して揃える。(ii) WS 送信→サーバー内処理は別 goroutine なので、直後に engine tick を叩くと「pos 未到達 = stale」で状態が巻き戻る — tick 前に数百 ms 待つ (2026-08-21, bloom P3c)。`await Navigator.push(...)` / `await showModalBottomSheet(...)` (= `showBloomSheet`) は **pop されるまで解決しない Future** — その pop 呼び出しを続くコードで書いた瞬間、実行順序的に「pop の前で待つ」デッドロックになる (2026-08-21, bloom P4)。症状は「特定の網羅的操作のあとで無音停止」で、WS/Docker/simulator ネットワークの障害と見分けがつかず誤診しやすい (今回 Docker Desktop 再起動・simulator erase・timeout 追加など無関係な対処に数十分溶かした) — 切り分けは (1) 各 await の直後に `debugPrint` を刺して**どの行で止まるかを行単位で特定**する、(2) サーバーの access log のタイムスタンプ間隔を見て「サーバーは応答している=クライアント側の待ちが原因」と確定する。両方を同時に使うと数分で原因に到達できる。修正は該当 push/showModalBottomSheet を `unawaited(...)` にする (pop は別ステップで呼ぶ)。**Docker Desktop (ローカル dev、Coolify 本番とは別) が長時間ビルド後に無応答になったら** `osascript -e 'quit app "Docker Desktop"'` → `com.docker.backend` 系 PID を `kill -9` → `open -a Docker` で復旧できるが、**古い container 定義が消えることがある** (named volume は残るのでデータは無事、他レーンの container は再作成が必要になり得る — 復旧後は自分の container だけでなく他プロジェクトの `docker ps -a` も確認し、消えていたら Touri/該当セッションに一言残す)。Riverpod の `Notifier` に `Timer.periodic` を持たせる時 2 点 (2026-08-21, bloom P5/build4): (a) 停止呼び出しを `ConsumerState.dispose()` 内の `ref.read(provider.notifier)` に頼ると `Using "ref" when a widget is about to or has been unmounted is unsafe` で死ぬ — `initState` で `late final` フィールドに notifier を退避し、`dispose` はそのフィールド経由で呼ぶ。(b) widget test (`router.go` で画面遷移するだけで最後まで unmount しないテスト) では periodic Timer が残留し `A Timer is still pending even after the widget tree was disposed` で無関係テストまで壊す — `WidgetsBinding.instance.lifecycleState == AppLifecycleState.resumed` の時だけ実 Timer を張る設計にすると、widget test は lifecycle イベントを送らない (既定 `null`) ため自動的に無効化されて安全になり、かつ「前景の間のみ動く」という設計要求も同時に満たせる (一石二鳥、後付けの回避策にしない)
17. **UI の「直った」は box とインク・要素とピクセルを区別して実測する。** スクショの画素実測・a11y ツリー・実タップまで見ないと出ないバグの層がある (フォント silent fallback / tint の暗黙供給元 / overlay の取り付け先)。自動検証が届かない境界は正直に「手動」と報告する (2026-07-16, atender)
18. **subagent が API エラーで死んでも、SendMessage で再開して報告だけ回収できる。** その際「ファイルを変更するな」を明示する (回収のつもりの再開で作業を再開させない)
19. **subagent が異常終了したら、報告を読む前に `git diff` を確認する。** 変異注入や中途半端な変更が作業ツリーに残っていることがある (後片付けコードは異常終了時に走らない)
20. **長時間ジョブが harness の 10 分 cap で SIGTERM されても「失敗」と決めつけない。** 成果物はディスクに残っていることが多い。log の到達点と実体 (`git status` / `find`) で完了度を判定して回収する (2026-07-23, omatase)

21. **`flutter test integration_test/... -d <sim-udid>` は毎回アプリを再インストールし、コンテナ UUID が入れ替わる。** drift/sqlite (Application Support 配下) は新コンテナで空になるが、Keychain (flutter_secure_storage) は実機同様プロセス/コンテナを跨いで残る。2 回の別プロセス起動で「サインイン → cold start 確認」を再現しようとすると db 側だけ消えて session が復元できず誤検知する — 同一 `flutter test` 呼び出し内で `BloomDb.open()`→`db.close()`→再 `BloomDb.open()` する形で「同じインストールのまま再起動」を模す (2026-08-21, bloom 緊急修正)。siwamock を使う場合、API サーバー側の `SIWA_JWKS_URL` を siwamock の `/keys` に向けないと (既定は実 Apple JWKS) `INVALID_APPLE_TOKEN` で全滅する。ローカル配布は `flutter build ipa --export-options-plist=...` の `signingStyle: automatic` エクスポートが GUI Apple ID セッション前提で headless だと `Failed to Use Accounts` で落ちる — `xcodebuild -exportArchive` に `-authenticationKeyPath/-authenticationKeyID/-authenticationKeyIssuerID` (ASC API key) を渡せば GUI 不要。ASC API key はチームスコープなので同じ Apple Developer アカウント内の他 PJ (atender 等) の鍵を bloom にも使い回せる。
22. **前任がネットワーク断で死んだ worktree を引き継ぐ時、`flutter build ios ...` が「disk I/O error (build.db)」で毎回落ちても、ディスク障害と決めつけない。** 前任が起動した `flutter build ios --simulator --debug` (または同種の xcodebuild) が親プロセス kill 後も孤児化 (`PPID=1`) して同じ `DerivedData/Runner-<hash>` を掴んだまま生き残っていることがある — `ps aux | grep -iE "xcodebuild|flutter_tools.snapshot"` で確認し、`pkill -9 -f "<worktree>/app/build/ios"` で一掃してから `rm -rf DerivedData/Runner-<hash>` → 再ビルドすると一発で緑になる (2026-08-21, bloom B9)。qr_flutter の `eyeShape/dataModuleShape: circle` (丸ドット QR) は `cv2.QRCodeDetector` / `zbar` の標準デコーダでは検出できない (finder パターンが円で 1:1:3:1:1 の輪郭認識に失敗) — 検証には `pip install zxing-cpp` (`zxingcpp.read_barcodes(cv2 画像)`) を使う。

23. **`flutter analyze` の `no_leading_underscores_for_local_identifiers` を Reviewer 生成テストで直す時、`_group` のような local を安易に `group` へ改名すると `flutter_test` の top-level `group()` 関数と衝突し、`referenced_before_declaration`/`missing_required_argument` の連鎖エラーになる。** 衝突しない名前 (`buildGroup` 等) を選ぶ。`xcodebuild -exportArchive` の ExportOptions.plist で `destination: upload` を使うと成功時 (`Upload succeeded.` / `EXPORT SUCCEEDED`) でもローカルに `.ipa` が残らない — 完了確認とハッシュ記録は xcdistributionlogs のログ文言か archive 自体 (`Runner.xcarchive`) の hash で行う (2026-08-21, bloom build 8)。

24. **`dayjs.tz(dateString, "YYYY-MM-DD", APP_TZ).startOf("day").toDate()` (JST 0時の instant) と、fixture の `new Date("YYYY-MM-DDT00:00:00.000Z")` (UTC 0時) は 9 時間ズレた別の instant。** 読み取り側が `gte/lte` の日範囲クエリなら両方同じ「日」バケツに入るので気付かないが、**完全一致 (`where: { date: exactValue }`) の書き込み/クエリ**にどちらか一方を混在させると常に 0 件になる (atender build18 の `existing` conflict 検出が沈黙する形で壊れていた)。生 DB を完全一致で検証する Reviewer テストは、API 生成行 (JST 0時) と fixture 直挿入行 (UTC 0時) を同一視できないことがあるので、疑わしい失敗は先に `node -e` で実際の instant を出して比較する。直す場所は「読み取り/書き込みの exact-match をやめて day-range に揃える」(発見時点で他の全サービスが既にそうしている規約に寄せる) が筋で、日付表現そのものを変えない (2026-09-08, atender build18 P2)。
25. **setupGuard (403 SETUP_REQUIRED) がルートに掛かっているとき、「他人のリソース → 404」を検証する fixture はその「他人」もセットアップ完了させる。** `createTestUser` (未完了) だと 404 に到達する前に 403 で止まり、テストの意図と違う理由で失敗する。同ファイル内に正しい先例 (`setupCompleteUser` を使う既存テスト) がないか探すと、どちらが実装バグでどちらがテストの fixture 選択ミスかの判定材料になる (2026-09-08, atender build18 P2)。
26. **XCUITest の `app.buttons.containing(NSPredicate(format: "label CONTAINS %@", "…"))` は画面外・シートの裏に隠れた要素 (タブバーの残骸等) にも一致し、`exists==true / isHittable==false` で沈黙して skip/fail する。** 曖昧な部分一致 predicate は自分が意図した要素以外を拾っていないか、accessibility hierarchy dump (テスト失敗時に自動添付される) か `accessibilityIdentifier` 追加で確定させる。設計docに identifier の規定が無い要素は実装側に追加してよい (Reviewer のテストコメント自身が「識別子が無いための既知の穴」と明示している場合は尚更、追加後にテストの predicate も identifier 優先に直してよい) (2026-09-08, atender build18 P2)。
27. **better-auth の social provider に `getUserInfo` を自前で渡すと `mapProfileToUser` は呼ばれない** (github provider が `options.getUserInfo` を先に return する)。追加列 (`githubLogin` 等) は getUserInfo の戻り `user` に直接入れる。`user.id` は型が `never` で渡せず、アカウント主体 ID は provider の `accountSubject` (GitHub は profile.id) が決める — 設計 doc が `user.id` を書いていても型に従う。Bash の `&&` 禁止フックは heredoc 本文のどこかに `&&` が紛れただけでコマンドごと拒否する (何も実行されない) ので、ソース一括生成は Write ツールか Python 生成スクリプト (Write で作る) で。ESM の top-level await を使う使い捨てスクリプトは package.json に `"type":"module"` が無いと `.ts` では cjs 変換で落ちる — `.mts` にする (2026-10-02, wasawasa)。

34. **Bash の `&&` 禁止フックは heredoc 内の `a && b` (TS/JS 断片) も拒否する。** TS/TSX は最初から Write ツール。cmdk の `loop` は ↓ を端で折り返す (↓ N 回で N 番目とは限らない)。使い捨ての目視 E2E は `tests/e2e/zz-*.spec.ts` + `fs.appendFileSync` でログ (vitest が console.log を握る)、終わったら消す (2026-10-05, wasawasa pages-ui)。

42. **bloom の `UploadBridge.swift` は `import background_downloader` していて、その `Task` 型が Swift Concurrency の `Task` を隠す。** 症状は `Task { ... }` が「Trailing closure passed to parameter of type 'DispatchWorkItem'」/ `Task.detached` が「Type 'Task' has no member 'detached'」という的外れなエラー。`_Concurrency.Task` と明示する。Flutter / Xcode を回せる環境でも、Swift の追加は `flutter build ios --simulator` を 1 回通すまで完了扱いにしない (2026-10-10, bloom post-media-batch)。
