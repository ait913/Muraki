# Reviewer の職業的習慣ノート

召集されたら最初に読む。**過去の自分 (歴代 Reviewer) が実際に踏んだ穴**であり、予防的な網羅ルールではない。新しく踏んだら自分で追記・置換する (INDEX 対象外、再生成不要)。

- **validation エラーの assert は status 中心 (400) にする。`error.code` 等の strict assert は zValidator が生 ZodError を返す構成で偽陰性になる。** gotcha 化済みなのに 2 回踏み直した (sessions/2026-06-02)
- **jsdom + Vitest は localStorage / matchMedia 未提供。**先に polyfill (gotcha/jsdom-no-localstorage-in-vitest.md)
- **バグ修正系のレビューは negative control を標準にする**: 修正前コードに戻してテストが落ちることを確認してから GREEN を出す。「テストが実装に迎合していないか」をこれだけが証明できる (sessions/2026-06-11 で有効)
- **偽 RED / テスト全滅の疑いは、実装コードでなく本番経路の直接プローブで切り分ける。** bulk API 全滅に見えた失敗を fixture の日付規約ミスと特定した実績 (sessions/2026-06-11)。fixture の日付は本番の正規化規約 (JST midnight) に合わせる (gotcha/api-test-date-fixtures-must-match-production-normalization.md)
- **Codex へのテスト生成依頼も同期実行・`< /dev/null`** (Developer と同じ穴)
- **既存の失敗テストを「ベースライン」と報告する前に、PJ の known-failures 台帳と照合する。台帳にない失敗は「未分類」と明記して返す** (「ベースライン」の山が本番バグを隠した実績: sessions/2026-06-11)
- **MCP ツールレベルのテスト (go-sdk) は Codex の「設計doc単独生成」では作れない。** ツールは ctx 経由で identity 注入され、ハンドラは unexported。既存の package-internal 統合テスト (例 dandan-app `internal/auth/mcp_integration_test.go`) の `issueAccess`/`testLogin`/`bearerRT`/`StreamableClientTransport` 往復パターンを流用し、Reviewer が同パッケージ内 (`package auth`) で自作する。`mcp.NewServer(Deps{GitHub: 実Client with WithApp+WithAPIBaseURL(fake)})` を auth 保護 `/mcp` の背後に配線 → アクセストークン発行 → `session.CallTool` で往復。IsError メッセージは `res.Content` の `*TextContent`、成功値は `res.StructuredContent` を json 経由で decode。フィールド名は設計doc の戻り値記述から取り、具体値 assert が通れば wire 契約一致の証明になる (sessions/2026-07-04 dandan Slice2)
- **Bash heredoc は中身に `&&` が 1 箇所でもあるとグローバル `block-bash-amp` フックに当たる。** Go コード (→ネスト if に分解、`||` は当たらない) だけでなく、Codex への指示文の散文や「このノート自体の更新」でも発火する (2026-07-08 に 2 回踏み直し)。heredoc を書く前に中身から `&&` を排除する。どうしても文字列が要るときは Python 側で `'AND'*2` 的に結合して生成する (sessions/2026-07-04)
- **`codex` の実体は `~/.local/bin/codex`** (2026-07-16 実測。`/Applications/Codex.app/...` は**存在しない** — 旧記載は陳腐化していた。Codex アプリは `/Applications/ChatGPT.app/Contents/Resources/codex` に同梱もされている)。`command not found` で止まらず `which codex` で引く
- **Codex の sandbox は localhost DB 接続を拒否する** (workspace-write でも network 不可)。Postgres 前提テストは Codex にはコンパイル確認までしかさせられない。実行は Reviewer が自分で回す (TEST_DATABASE_URL + docker postgres を自前起動)
- **設計docは wire/DB 状態を規定するが store API の意味論 (戻り値・入力 struct のどのフィールドを永続化するか) は規定しない。** ブラインド生成テストが store の戻り値や `CreateX(struct{RevokedAt:...})` の永続化を仮定すると偽陽性 fail になる (dandan Slice1 で 2 件: RotateRefreshToken の戻り値 = 更新前スナップショット / CreateMCPToken が RevokedAt を無視)。fixture は直接 SQL UPDATE、assert は DB 直読に倒す。切り分けは probe テスト 1 本 (Create → SELECT) で 1 分
- **redirect の query 値は URL エンコードされて返る** (`rd=/dashboard` → `rd=%2Fdashboard`)。設計docの文字面と Location 文字列を直接比較しない。`url.Parse` → `Query().Get()` で比較
- **「write が起きない」系の失敗で「未配線」と断定しない。** ブラックボックスでは「未配線」と「配線済みだが best-effort `_ =` がエラー握りつぶし」を区別できない (dandan Slice1 で後者を前者と誤帰属しかけた。真因は SQLSTATE 42883 の無音化 → gotcha/best-effort-write-swallows-sqlstate-errors.md)。帰属は観測レベルで書く
- **typed AddTool の入力 schema は非ポインタ全フィールドが required になる (jsonschema-go)。設計docの入力表で `?` が付かないフィールドは required とみなし、ブラインドテストでも常に全フィールドを渡す** (空配列含む)。dandan Slice2 で submit_plan の acceptance_criteria/tags/insights/relations と apply_assignments の reason を省略して 7 テストが偽 fail、1 ラウンド浪費 (2026-07-05)
- **空状態契約 (空配列で返す) の検証は「キー存在 + 値が nil でない + len==0」の 3 点セット。** Go の nil slice は wire で null になり、典型的な系統的違反 (gotcha/go-nil-slice-null-breaks-mcp-empty-state-contract.md)。契約違反は Fatalf でなく Errorf + 空 slice 返しで続行すると、null の裏の挙動 (イベント記録・ガード等) まで同ランで検証できる (2026-07-05)
- **共有 TEST_DATABASE_URL で `go test ./...` するとパッケージ並列 (デフォルト -p) で TRUNCATE 同士が deadlock する (SQLSTATE 40P01)。** 実装バグと誤帰属しない: 単独パッケージ実行 → 全 green なら環境依存。判定用の全体回帰は `go test -p 1 ./...` で取る (dandan 2026-07-05)
- **Codex 生成テストの偽 fail は、まず fixture の合成データ論理を手で追う。** 剰余条件で seed を分岐させるループ (`i%2` で reassign、`i%5` で unassign 上書き等) は、Codex 自身が上書き条件を忘れた assert を書く (dandan Slice3: i=55 は %5 上書きで from=m1 なのに「m1 非関与」と誤 assert。件数 assert は DB 突合で pass しており実装は正しかった)。負系の文字列 assert は「その行が条件に該当しないこと」を seed 式から再計算してから直す (2026-07-05)
- **seed ヘルパの UpsertUser は OAuth ログイン済み user の github_login / github_token_enc を上書きする。** ログイン後に同 user_id で seed すると sealed token が壊れ GitHub 系表示が縮退し、login 文字列 assert も外れる。表示の login assert は固定文字列でなく DB 直読 (`SELECT github_login FROM users WHERE id=$1`) と突合する (2026-07-05)
- **コピー契約 (fidelity 優先) の PJ では、設計docの検証条項がコピー元原文と衝突したらコピー元が勝つ。** dandan Slice2 で 2 件: §9.5-2「存在しない grep 0 件」は天野原文 description「存在しない ID はスキップ」に誤ヒット (意図は policy/open_* の先回り文言のみ)、0 件応答の空配列契約は天野が nil slice (wire null) を返すため null が正。判断前に許可されたコピー元比較で原文を突合してから assert を絞る (2026-07-08)
- **ダッシュボード HTML の負系 grep (「この名前が出ないはず」) はフィルタ UI の select 選択肢に誤ヒットする。** フィルタの正しさは data-testid 行数一致で取る (dandan 2026-07-08)
- **MCP Apps UI ハーネス (report-back 方式) の駆動は「hostLog にリクエストが載った」で先へ進まない。** hostLog は送信記録で応答適用を保証しない → 応答適用後にしか変化しない DOM マーカーを待つ。ui/message の text は `params.content[0].text` (`params.text` は常に undefined)。dark 検証は `--force-dark-mode` + 実際に色の付く要素の dark palette 値。詳細 gotcha/mcp-apps-ui-harness-testing.md (2026-07-08 Slice3 で 6 シナリオ偽 fail)
- **設計docの「friendlyError 契約」等の UI 横断記述は、コピー契約 PJ では画面ごとに実装有無を原文で確認してから assert する。** 天野 friendlyError は workspace.html のみ (insights.html は JSON.stringify で Error→"{}" 表示)。note の「コピー元が勝つ」原則の画面単位 instance (2026-07-08)
- **dev の `.env` が Vitest に漏れて `.env.test` を上書きする (app が import 時に dotenv で `.env` を読む構成)。2026-07-14 と 2026-07-17 で 2 回踏んだ。** 漏れるのは 1 変数でなく **3 変数 / 計 5 件** (`BETTER_AUTH_COOKIE_DOMAIN` → `auth [§8 #7]` / `PUBLIC_WEB_URL` → `cors-cookie [§8 #70]` / `BETTER_AUTH_TRUSTED_ORIGINS` → `ios-api §8.4` 3 件)。**~~「.env を正しい値に直すと全 pass」~~ は誤った処方だったので撤回する**: dev の `localhost` / `localhost:5173` は **dev としては正しい値**で、直すとローカル開発が壊れる。真の欠陥は値でなく**漏れること自体**。**切り分け**: 失敗テスト内で `console.log(process.env.THAT_VAR)`。**検証で書き換えたら `cp` バックアップ → `diff` でバイト単位復元する** (dev 値は正しいので直した状態で放置しない)。env 由来の一括失敗は「CORS が壊れた」「認証が壊れた」の顔で現れ、**新 feature の regression と誤帰属しやすい** — 帰属は negative control (feature を消した状態で同じテストを回す) で決める。詳細 gotcha/dev-dotenv-leaks-into-vitest-overriding-env-test.md (2026-07-17)
- **~~prisma CLI がこの環境で無言ハングする~~ → 解消済み (2026-07-17 実測)。** 真因は iCloud evict (memory `env_icloud_evict_hangs` 参照) で、`prisma --version` / `prisma generate` とも正常動作する。**シムで差し替える回避策はもう要らない。** ただし `pnpm install` 後は `pnpm exec prisma generate` が必須 (postinstall フック無し)。忘れると `@prisma/client does not provide an export named 'PrismaClient'` — コードのバグに見えるが未生成なだけ。**なお macOS に `timeout` は無い** → `perl -e 'alarm N; exec @ARGV'` を使う
- **同一 sqlite tmp を共有する Vitest を 2 プロセス並行起動するとロックでハングする** (singleFork + 共有 DATABASE_URL)。ハング時はまず `pkill -f vitest` して 1 本ずつ回す。harness が長時間コマンドを勝手に background 化するので、前の run が生きたまま次を撃たない (2026-07-14)
- **env 由来の分岐 (provider config, trustedOrigins 等) は「プロセス起動前に env を投入」して検証する。** `env.ts` が import 時に一度パースして固定する構成では、実行時 `process.env.X=... → resetAuth()` は届かない。設定側の検証は APPLE_* を export した状態で 1 本だけ回す boot-probe に回し、未設定側 (404) だけ in-process で見る。詳細 gotcha/env-module-import-time-parse-defeats-runtime-env-swap.md (2026-07-14)
- **better-auth 1.6.11 は magic-link の verification.identifier を平文 email でなく不透明ランダムトークンで保存し、verify 失敗を 302 リダイレクト (JSON 400 でない)、送信失敗を 5xx に伝播しない。** 旧 auth.test.ts の `identifier contains email` / verify 400 / resend 失敗 500 期待は陳腐化。send 自体 (200 + verification 1 行 + resend 1 回) は正常。バージョン更新後の「既存が赤い」は挙動変化をまず疑い、probe で実挙動を採取してから陳腐化と断ずる (2026-07-14)
- **インフラ設計 (Dockerfile/workflow) のレビューは「ユニットテストが無いから回せない」で終わらせない。** 設計docが「docker daemon が無い」と書いていても**自分で `docker version` を確認する**。omatase では Docker Desktop が `open -a Docker` で起動でき、K1-K8/H4/H5 を全て実走できた (Architect 環境の不在をそのまま引き継がない)。CI job の shell も yaml から `yaml.safe_load` で `run` を抜き出せば**手元で実行できる**: fake API サーバ (python http.server) を立てて `COOLIFY_API_BASE` を向ければ D1-D8 のような「本番でしか出ない」分岐が全部踏める。ポーリングの長い timeout は**コピーを sed で短縮** (`seq 1 180`→`seq 1 3`) して経路だけ確認する (2026-07-16)
- **healthcheck の検証をホスト側のポート公開プローブで代用しない。** `docker run -p 18080:3000` + `curl 127.0.0.1:18080` は 0.0.0.0 bind なら通るが、Coolify の healthcheck は**コンテナ内から localhost** を叩く。Node の `HOSTNAME=0.0.0.0` は IPv4 のみ bind し、busybox wget は localhost を ::1 で引くため落ちる (Go は dual-stack なので通り、非対称が誤帰属を生む)。`docker exec` で実 CMD-SHELL を実行して初めて検出できた。詳細 gotcha/coolify-healthcheck-localhost-ipv6-vs-node-bind.md (2026-07-16)
- **「実装が設計に忠実」と「本番で動く」は別。** 設計docのシェル片をそのままコピーした実装は diff 上は完璧でも、設計自体の欠陥 (D2 の `resp=$(curl --fail-with-body ...)` は set -e で body を echo する前に落ちて**ログに body が出ない**) をそのまま継承する。失敗の帰属先は「実装 or 設計」であって、実装が設計通りでも**設計の不備なら報告する** (2026-07-16)
- **自分のテストハーネスのバグを実装のせいにしない。** 2026-07-16 に 3 回踏んだ: (1) fake サーバの readiness を待たず `sleep 2` で撃って偽 fail、(2) readiness 判定に `[ "$c" != "000" ]` を使い、curl の `000` + `|| echo 000` で `000000` になって即 break、(3) fake API のルーティングで `/api/v1/deployments/x` が `startswith("/api/v1/deploy")` に誤ヒットし全 status が null。**偽 fail の第一容疑者は自分のハーネス**。「全シナリオが同じ異常値」を見たらルーティング/起動を疑う
- **負のコントロールは「自分で手打ちしたコマンド」でなく `yaml.safe_load` で ci.yml から抜いた実 step を bugged 対象に当てる。** 手打ちだと「設計通りのコマンドは検出できる」しか言えず、**実装された step が検出するか**は未証明のまま。omatase では step の `run` を抽出 → `${{ matrix.* }}` を置換 → `docker exec probe` が要るので同名コンテナを bugged (`-e HOSTNAME=0.0.0.0`) で立てて実行 → exit 1 を確認、で「CI が実際にバグを捕まえる」を証明できた (2026-07-16)
- **「この matrix entry でも検出できるか」を対象アプリの都合で諦めない。** Go は IPv4-only bind を強制する env が無く backend の検出能力を直接示せなかったが、**別イメージ (web) を `-e PORT=8080 -e HOSTNAME=0.0.0.0` で立てて backend 用 step を当てる**と「localhost:8080 の IPv4-only listener を step が exit 1 で捕まえる」が直接示せた。検出能力の証明に必要なのは「その port でその症状が出ている listener」であって、本物のアプリではない (2026-07-16)
- **`git show <base>:<file>` で修正前の実装を取り出して当てるのが、修正系レビューで最も安い negative control。** omatase D2 は旧 step (775c08d) を fake API に当てて「body が消える」を再現し、新 step との差を 1 コマンドで示せた。worktree を汚さずに済む (2026-07-16)
- **`curl ... || echo 000` は `-w '%{http_code}'` の `000` と重なって `000000` になる。** 自分のハーネスでこれを踏んだ (note 済) だけでなく、**レビュー対象のシェル片にも同じ形が現れる**。`= "200"` 比較なら無害なので「バグ」と報告しない。`!= "000"` 比較をしている箇所だけが本当の欠陥 (2026-07-16)
- **フォント/画像など「フォールバックが親切な API」の検証に、そのフォールバックする API 自身を使わない。** `Font.custom` は解決失敗を無言でフォールバックするので登録漏れを検出できない (atender は全画面 SF Pro のまま TestFlight に出ていた)。`UIFont(name:)` は nil を返す → こちらで assert。詳細 gotcha/swiftui-font-custom-silent-fallback-hides-missing-uiappfonts.md (2026-07-16)
- **ベースライン件数の台帳は「測った日 + 測ったコミット + failure 数」まで書かせないと failure を隠す。** atender の「iOS 157 GREEN」は実測 172 テスト / 2 RED で二重に誤りだった。件数だけの台帳を信じると「総数が合ってる」で RED を素通りする。**台帳と実測が食い違ったら、台帳でなく実測を正とし、その場で台帳を置換する** (2026-07-16)
- **`pnpm exec tsx` で API を起動する系は、この Bash-tool 環境では無言で起動しない** (プロセスは alive だが listen せずログもゼロ。`( … & )` / `nohup` / サンドボックス無効 いずれも不可)。**前景 `perl -e 'alarm N; exec @ARGV'` でも出力ゼロ**なので原因を追う手がかりが無い。prisma を直接叩く seed スクリプトは動く。**API 前提の E2E/sim 検証は撃たずに Leader へ「未検証」と返す方が安い**。撃つと停止できない tsx プロセスが溜まる (`pkill` は permission denied で掃除もできない) (2026-07-16)
- **「純粋ロジックはテストできるが View の `.task` 配線はテストできない」を GREEN で誤魔化さない。** `HomeChips.items` が全 pass でも「温キャッシュ時に rooms が読まれるか」は 1 ミリも証明していない。純粋関数の GREEN が配線の GREEN に見える構造なので、**カバーできていない挙動は判定に明示的に書く** (2026-07-16)
- **`DecodingError.keyNotFound` の localizedDescription は "The data couldn't be read because it is missing." で、**空データの decode と同じ文面**。** `APIError.decoding(...)` のように localizedDescription だけを包む型だと、どのキーが無いか消える。この文面を見て「body が空 = スタブが効いていない」と誤診し 1 ラウンド浪費した (2026-07-17 atender)。切り分けは**同じ経路を最小 JSON で叩くプローブ 1 本** (通れば配線は生きており、犯人は fixture のキー漏れ)。**そもそもスタブ JSON を手打ちしない** — 稼働中の実 API から curl で採取して fixture 化すれば起きない
- **リーダーから渡る「契約仕様」の型名・シグネチャは実在確認してから使う。** atender で「`RoomWeekRepository.roomWeek(id:weekStart:force:)`」と渡されたが実在せず (実体は `RoomRepository.roomWeek`)、`cannot find in scope` で足止め。**実装を読まずに名前だけ引く手段: ビルド済 `.swiftmodule` を `strings` して型名/メソッド名を拾う** (`strings Atender.swiftmodule/arm64-*.swiftmodule | grep -oE "[A-Za-z]+Repository"`)。ロジックは見えず、呼び出しに必要な名前だけが得られる。init のアリティは**コンパイルエラーに教えさせる** (`has no member 'members'` → `roomMembers` と判明)。これで「実装コードを読まない」を守ったまま blind test を書ける (2026-07-17)
- **Vitest の in-process テストは CJS/ESM interop バグを原理的に検出できない。** Vite の transform は Node native ESM より寛容な interop shim を挟むので、`import * as ical from "node-ical"` が **Vitest では動き `tsx`/`node dist/` では `parseICS is not a function`** になる。atender の ICS インポートは**この穴に落ちて「一度も動いたことがない機能」が出荷されていた**。ブラインド生成した 5 本は**修正前コードでも 5/5 GREEN** (負のコントロールで発覚)。→ CJS パッケージ (`node-ical`/`rrule`/`jschardet`/`iconv-lite` 等) の interop は **`execFileSync(node_modules/.bin/tsx, [probeFixture])` の子プロセス probe テスト**でしか担保できない。詳細 gotcha/vite-cjs-esm-interop-hides-node-esm-failures.md (2026-07-17)
