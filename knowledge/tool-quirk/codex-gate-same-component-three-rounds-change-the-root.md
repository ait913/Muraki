## Context

wasawasa の行ページ (DB の行を Notion 風のページとして開き、プロパティ欄とタグ欄を持つ) で、Claude Reviewer は GREEN (設計 doc からのテスト 103 本 + 負のコントロール 9 変異) だったのに、Codex の静的レビューが**クライアントの楽観ロック**に関する HIGH を 7 パス連続で出し続けた。毎パス「前回の HIGH は塞がったが、その直し方が新しい HIGH を生んだ」の形 (時刻だけ更新 → 409 自動再送 → 版チェーン `adv` → ...)。

## What

- Claude Reviewer のテストは設計 doc の挙動仕様から生成されるので、設計 doc に書かれていない**並行編集の競合** (他者が同じ行を変えた / 応答の逆転 / キュー待ち中の版のずれ) は原理的に検出できない。Codex の静的追跡はそこを突く。これは「見解が割れた」のではなく、検出できる欠陥の種類が違う
- 第 1〜6 パスは「指摘箇所を直す」で対応し、毎回 HIGH が 1〜2 件残った。第 7 パスで**根**を 2 つ変えたら収束した:
  1. **サーバーの契約**: `updateRow` が「変更なし」を版検査より先に 200 で返していた → no-op PATCH が他者の版を持ち帰る経路 (版検査を早期 return より前へ)
  2. **クライアントの構造**: 「複数 in-flight の版チェーン + 値スナップショット」をやめ、「job は作成時の版 (`chainAt ?? 操作時点`) だけを送る / 実行時の最新行の版は決して送らない / 409 で行のキュー全破棄 + 再読込 / 選択系は差分 (add / remove / create) を実行時に基底へ適用」に単純化
- 第 8 パスで GO。合計 8 パス、修正 7 ラウンド、約 4 時間

## Why

楽観ロックの正しさは「送る `expected` が、ユーザーが見て操作した版 か 自分の成功応答の版 のどちらかである」という 1 つの不変条件に尽きる。パッチで個別経路を塞いでも、その不変条件を破る新しい経路 (GET で入った他者の版を `cur` から拾う、no-op 応答の版を採る) が別の場所に残る。契約 (サーバー) と構造 (クライアントの状態の持ち方) を不変条件に合わせて作り直す方が、パッチ 3 回分より安い。

## How to apply

- Codex ゲートで**同じ部品**が 3 パス連続 NO-GO になったら、第 4 パスを回す前に Leader が止まる。「指摘を直す」でなく「どの不変条件が守れていないか」を 1 文で書き、サーバー契約とクライアント構造の両方をその不変条件に合わせて書き直す指示を出す (sessions/2026-10-09-9f2cb1ff 第 7 ラウンドの形)
- 楽観ロックのクライアントを設計 doc に書く時は、Architect が「`expected_updated_at` に入れてよい版は何か」を不変条件として明記する。サーバー側は「版検査 → 変更なし 200」の順を契約に書く (3c §6-8)
- Codex の指摘はコード行付きで具体的なので、Developer に「根拠をコードで確認してから直す、誤認なら修正不要と報告」を毎回付ける。今回 8 パス × 平均 3 件で誤認は 0 件だった (静的レビューの精度は高い)。ただし「塞がった」の判定も Codex に書かせ、再現手順を実装で追い直させる (第 8 パス)
