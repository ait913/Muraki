## 課題点

- **開発 repo が iCloud 同期下にある**: 何が課題か = `~/Documents` 配下の venv/git が間欠 import・checkout stall し、reviewer のテスト実行と main マージが両方詰まった(素の starlette が既知良好 venv でハング、通常 merge が2分タイムアウト)。いつ起こるか = ファイルがオフロード状態 + 負荷が重なった時、間欠的に。次どうするか = repo/worktree/venv を iCloud 対象外へ移す(恒久)。当座は検証をローカルディスク venv、マージは `git update-ref` で working-tree I/O 回避([[gotcha/icloud-synced-venv-git-stall]])。
- **Reviewer が API エラーで途中終了**: 何が課題か = reviewer subagent が「接続断」で最終判定を出す前に死に、生成テストと2バグ報告だけ残った。いつ起こるか = 長時間走る subagent が terminal API error を踏んだ時。次どうするか = 今回は Leader が生成テストを独立実行して RED を確定できた(テストが成果物として残っていたので復旧可能)。subagent の途中終了は「生成物がディスクに残っているか」を先に確認してから再召集 or Leader 代行を判断する。
- **設計 §6 スコープ境界が UI 忠実度を削った**: 何が課題か = `store/product.py` を改変許可リストから外した結果、developer が roster avatar を機能縮退させ、fix ラウンドでスコープ拡大して復元する二度手間になった。いつ起こるか = 表示に必要なデータ列が既存 read 関数に無く、その store が改変スコープ外の時。次どうするか = Architect が「表示に要る列 ↔ 触る store」を設計時に突合し、read の列追加は最初からスコープに含める。

## いい点

- **subagent の否定的主張を独立検証してから受理した**: 何が良かったか = reviewer(途中終了)の「2バグ」と developer の「設計不備2点」を鵜呑みにせず、Leader が生成テストを自分で走らせて RED を確定・原因を正確な SQL エラー/route decl まで帰属した。いつ効いたか = RED 差し戻しで developer に「どこを・なぜ」を具体指示でき、1ラウンドで GREEN。どう続けるか = CLAUDE.md エスカレーション規約(独立検証)を今後も機械的に踏む。
- **環境要因をコード欠陥と誤認しなかった**: 何が良かったか = import ハングを「実装バグ」と早合点せず、素のサードパーティ import を既知良好 venv で試して環境要因を切り分けた。いつ効いたか = developer に無駄な「コード修正」を投げずに済んだ。どう続けるか = import/build の異常はまず素の依存 import で切り分け(knowledge 化済)。
- **承認ゲート + プロダクト判断を確実に Touri へ上げた**: 何が良かったか = 閲覧粒度(思想で決まる)と設計 doc 承認・scope 逸脱を要点提示で確認し、勝手に決めなかった。どう続けるか = 「正解が仕様でなく思想で決まる」判断はシグナルベースで必ず上げる。
- **iCloud stall 下でも ref 操作でマージを完遂した**: 何が良かったか = 通常 merge がタイムアウトした時、fast-forward を `git update-ref` に逃がして working-tree I/O ゼロでマージ成立。どう続けるか = working-tree 一括 I/O が詰まる環境では ref 操作に逃がす(knowledge 化済)。
