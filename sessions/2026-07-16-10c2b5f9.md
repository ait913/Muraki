## 課題点

- ★ **手順を機械的に適用して重くしすぎた** (Touri から明示的に指摘された)
  - **何が課題か**: 497 個の静的ファイルを `site/` に置くために、設計doc を 659 行書き換え、Architect と Developer を何往復もさせた。coming soon の 1 枚ものに対して過剰。Touri から「**何に時間かかってるの? HTML/CSS だよね触ってるのは**」と指摘されて初めて Reviewer を飛ばした
  - **いつ起こるか**: Muraki の workflow を「事故る余地の大小」で調整せず全部に適用したとき。特に**素材が既に完成していて、こちらは配置するだけ**の作業
  - **次どうするか**: workflow は**事故を防ぐためのもの**であって儀式ではない。着手前に「**この作業で事故る余地はどこか**」を 1 行で言えるか自問する。言えないなら軽くする。今回で言えば「バンドルをほどく」は事故る余地が大きく (実際 Leader が欠陥を入れた)、「ファイルを配置する」は小さかった。**同じ機能追加でも工程ごとに重さを変える**

- ★ **「検証したつもり」が 4 件出た。全て実行した人だけが見つけた**
  - **何が課題か**: (1) omatase の healthcheck をホストから叩いて緑 (2) 404 を配線 OK の証拠にする (3) 破壊テストが破壊にならない (4) `grep unpkg` が 0 なら成功 (実際は文字列は残り、消えるのはリクエスト)。**全部「検証コードは書いたが何も検証していない」形**
  - **いつ起こるか**: 検証を設計に組み込んだ瞬間に安心したとき。設計docを読んだだけでは絶対に出てこない
  - **次どうするか**: **検証を書いたら「この検証が緑で本番が落ちる状態はあり得るか」を必ず自問する**。加えて **負のコントロールを取る** (壊して赤くなることを確認してから緑を信じる)。判別に使う信号は**変化することを確認してから使う** (敷設前も後も 404 なら情報量ゼロ)

- **Leader が展開作業で外部依存を新設した**

  - **次どうするか**: **変換作業は「変換前後で観測可能な振る舞いが一致するか」で検証する** (今回なら「外部リクエスト数」)。内部表現のチェックリスト (UUID の解決) は完了の証明にならない

  - **何が課題か**: knowledge/SKILL は「新規 app は作成直後に `is_force_https_enabled:false` を PATCH する」を標準手順として書いており、**これで防げる**と読める。しかし今回それを初回デプロイ前に済ませた上で **新規 app 2/2 でループした**。再 PATCH + force redeploy でも直らず、fqdn ダンスが必須だった。既存 knowledge の Why (「stale label が残る」) は**新規 app には当てはまらない** (古い label が存在しない) ので、根本原因は未説明のまま
  - **いつ起こるか**: Cloudflare 配下で新規 Coolify app を立てるたび。今回は 2/2
  - **次どうするか**: gotcha と SKILL を「PATCH は必要だが十分でない / fqdn ダンスは復旧手順でなく**新規作成フローの一部**」に置換済。次に新規 app を立てるときは最初から fqdn ダンスを見込む。根本原因は未特定なので、頻発するなら Coolify issue を追う

- **設計docに書いた検証が、本番で落ちる経路を通っていなかった**
  - **何が課題か**: Architect が `docker-build` job を設計に組み込んだこと自体は良かったが、その job は**ホストから** `curl 127.0.0.1:18080` するだけで、Coolify が実際に叩く**コンテナ内**経路を通っていなかった。0.0.0.0 bind でも 200 が返るので緑になる。「検証を設計に入れた」ことで安心してしまう構造
  - **いつ起こるか**: 検証コードを設計する時全般。特に「本番の実行環境と検証の実行環境が違う」場合
  - **次どうするか**: 検証を設計に入れたら「**この検証が緑で本番が落ちる状態はあり得るか**」を必ず自問する。Architect の role note に追記済

- **Researcher の実測条件と、設計対象の実行条件がズレていた**
  - **何が課題か**: Researcher は `.git` のある作業ツリーで `pnpm install` を測ったため、`.git` の無い Docker context で `prepare: lefthook install` が落ちる罠を検出できなかった。また `.npmrc` の `node-linker=hoisted` を見落として node_modules の形を誤記述した
  - **いつ起こるか**: リサーチの実測環境と、設計が動く環境が異なる時 (ローカル vs Docker、macOS vs linux/musl)
  - **次どうするか**: Architect が Researcher の実測を**再現する時に条件差分を洗う**。今回は実際にそれで 2 件潰せた。role note に追記済

  - **いつ効いたか**: 特に actionlint と in-container healthcheck step。どちらも vacuous pass になりやすい形だった

- **本番を触る前に「切り分けプローブ」を先に打ったこと** (※ただし下記の通り**根拠は間違っていた**)
  - **何が良かったか**: 多層構成 (CF → tunnel → Nginx → Traefik → container) で、Coolify を触る前に層を1つずつ潰しにいった姿勢そのものは正しかった。403/521/526 が返っていれば実際に切り分けられていた
  - **いつ効いたか**: fqdn 削除 → 404 確認で「Cloudflare 無罪」を確定させたのも同じ型。**こちらは 302 → 404 の遷移**を見ているので推論として成立している
  - ★ **後から判明した誤り**: 「404 = Traefik まで到達 = 配線 OK」という判定は**嘘だった** (後半の HP 作業で実測により発覚)。`gateway/*.conf` の `proxy_intercept_errors on` が **Traefik の 404 を横取りして共通のカスタム 404 に差し替える**ため、「Traefik まで届いた 404」と「vhost が無く default_server が拾った 404」が **`Content-Length: 1020` までバイト単位で同一**になる。結論 (配線は通っていた) は正しかったが**根拠が成立していなかった** = まぐれ当たり
  - **どう続ける**: 「期待する失敗」を先に観測する型は維持する。ただし ★ **成功の証拠は 404 でなく 200 に置く** (200 は `error_page` の対象外で横取りされない)。**エラーコードは途中の層に書き換えられうる**ので、「特定のエラーが返った = そこまで到達した」と推論する前に**書き換える経路が無いか**を確認する。判別に使う信号は、**変化すること**を確認してから使う (敷設前も後も 404 なら情報量ゼロ)

- **予測が外れたことを外れたと記録したこと**

  - **どう続ける**: 予測と結果が食い違ったら、**推論で辻褄を合わせずに観測を並べる**。n を明示する
