## 課題点

- **Leader が表面的な信号 (`tsc`/`curl 200`/`204`) で OK 判定し、実物を見なかった事故が本日3回**
  - **何が課題か**: (1) Web ログイン画面を `tsc`+200 で OK にしスクショを撮らず、白箱とフォントバラつきを見逃した (2) sign-out を「204 + それらしい Set-Cookie」で健全と断言し、cookie 名不一致を照合しなかった (3) フォント統一を「ジオメトリを揃えれば出る」と推測でベンダー準拠を推奨。全て Touri か subagent に覆された
  - **いつ起こるか**: 検証を「返り値のステータス」で済ませ、描画結果や payload 中身を見ないとき
  - **次どうするか**: **UI は必ず chrome-devtools MCP でスクショを撮って目視** (CLAUDE.md 明記済みなのに未実行だった)。**API は status でなく payload/ヘッダの中身を照合**。「200 だから OK」を禁止する
- **Leader がスコープを勝手に縮小した (P2/P3 を落とす・Web デプロイを P2 待ちにする)**
  - **何が課題か**: Touri の却下済み提案どおりに進めていた。Web デプロイを iOS の P2 完了まで理由なく待たせた
  - **いつ起こるか**: 複数タスクを1つの流れに束ねるとき、独立性を検証せず惰性で直列化する
  - **次どうするか**: 束ねる前に「これは本当に依存しているか」を1つずつ問う。独立なら即出す
- **レビューのたびにビルドする構造 (1機能4ビルド) + `head` でログを切って失敗を見落とす**
  - **何が課題か**: Developer と Reviewer が別々にビルドし2トラック並列で4回。かつ grep を `head -25` で切り TEST FAILED の中身を2回取り逃した
  - **いつ起こるか**: 軽量レビューを「Reviewer もビルド」で組む / ビルドログを部分表示する
  - **次どうするか**: **マージしてから1回だけビルド**。ログは丸ごとファイルに落としてから grep する。[[feedback_phase_consolidation_review_loop]] に反映済み
- **マージ時の YAML 重複キー事故 (`UIAppFonts` が2つ)**
  - **何が課題か**: 衝突対策を「順序を合わせろ」止まりにし挿入位置を固定しなかったため、git がテキスト衝突と見なさず両方残した
  - **いつ起こるか**: 複数ブランチが同じ設定ファイルの同じキーに別位置で追記するとき
  - **次どうするか**: 共有設定ファイルを触る並走 feature には「挿入位置 (前後のキー名) まで固定」して指示する

- **subagent の否定的主張・自分の設計を独立検証してから受理・是正した (CLAUDE.md 順守が機能)**

  - **いつ効いたか**: subagent 報告の受理判断、自分の設計指示の妥当性判断
  - **どう続けるか**: 「否定的主張・自分の推測」は必ず独立検証を通す。特に規約・セキュリティ・契約に触る主張

  - **いつ効いたか**: 「本番で本当に直ったか」の検証局面
  - **どう続けるか**: 状態確認は「叩いて確かめる + 対照群」を基本にする。ただし **payload の中身まで照合**する (status だけで満足しない)

  - **何が良かったか**: Leader は state_mismatch を「ブラウザ経由の中継新設」で回避しようとしたが、Touri の「普通は iOS クライアント作るのでは」が本筋。Apple と対称な native idToken 方式に揃い、歪みが消えた
  - **いつ効いたか**: Google ログインの設計方針決定
  - **どう続けるか**: 回避策を組む前に「そもそも標準はどうやるか」を Touri に確認する
