### 実機FB ラウンド 2 (build 14) — 2026-07-30

14. **Touri の実機FB 4件**: 「選択できるところとできないところがある / 表の線がズレてる / モバイルアプリなのにタッチ操作しずらいの終わってる / 学科カレンダーの右上の青点はなに？いらない」+ エラーダイアログのスクショ。
15. **調査3本並列**。
    - **HTTP 400 の原因が確定**: Swift の合成 `Codable` は nil の Optional を `encodeIfPresent` で書くため**キーごと JSON から消える**。一方 zod が bare `.nullable()` (キー欠落を許さない)。EK の `location` は大半の予定で nil なので、**場所なしの予定が1件でもあればリクエスト全体が400**。読み込み対象カレンダーを1つでもONにしている全ユーザーで毎回失敗していた。さらに zValidator が raw ZodError を素通しするため iOS の `ErrorResponse` が decode できず「サーバーエラー (HTTP 400)」という**中身ゼロの文字列**に潰れ、画面からもログからも原因に辿れなかった。
    - **罫線ズレの原因が確定** (オフスクリーンでピクセル実測): 各セルが自分の上辺/左辺を描く方式 + `.frame(maxWidth: .infinity)` に `minWidth: 0` が無く**子の intrinsic 最小幅が下限として残る**。ドット2個で列幅 49.29pt を超え、3ドット行は合計376ptで345ptの枠から溢れ、角丸クリップで土日列が消えていた。**タイル化(幅を狭めた)と §2.6(ドットを3個に増やした)の掛け算**で表面化。
    - **青点は初回実装(7/1)からある仕様で Web にもある**。ほぼ全日に付く真因は装飾でなくデータで、`personalEvent.service.ts` が `source=EVENTKIT` を除外していないため iPhone 標準カレンダーのミラーが全部点になっていた。
    - 「選択できない」は**通常タップでは無効セルが1つも無い** (126点タップ実測で死に領域ゼロ)。該当は複数選択モードの学期範囲外のみで、区別が不透明度だけ (0.40 vs 0.10)。
16. **400 を先に単独で修正・本番デプロイ**。サーバー側だけの変更なので**配布済み build 13 がデプロイのみで復旧**。併せて zValidator の封筒を統一し、台帳 A6 が解消 (ベースライン 17→16)。再発防止に**実 Swift DTO を `swiftc` でビルドして出力させた逐語 fixture** を置いた。
17. **UI 4件 + 追加FB「カレンダーの横の影がまた見切れてる」を build 14 で出荷**。影は `HomeCore:73` の padding が ScrollView の外側にありクリップ境界がカードの縁と一致していたのが原因で、ScrollView を全幅にして `contentMargins` で中身側にインセットを戻し、**「影を出すとタップが死に、タップを直すと影が切れる」シーソーを構造から解消**。

## 課題点

2. **ハードコード日付とハードコード設定値がテストを自動的に腐らせる**

   - 次どうするか: gotcha 2本を追加済 (`hardcoded-future-dates-decay-into-baseline-failures.md` / `policy-constant-literal-in-test-decays-on-bump.md`)。設計docのテスト仕様に日付リテラルを書かせない。

3. **ベースライン失敗の山に本物のバグが隠れていた (再発)**

   - 次どうするか: Web 節を新設済。新しいテストスイートを足したら台帳に節を作る。

4. **正典ドキュメントが出荷済みコードと矛盾していた**
   - 何が課題か: `DESIGN.md` が build 11 でタイル化を出荷した後も full-bleed のままだった。D2 §14 が置換を予告していたのに実行されず落ちた。
   - いつ起こるか: 設計docに「置換する」と書いても、実装レーンは docs を触らないので誰も実行しない。
   - 次どうするか: doc の置換は Leader が明示的にタスク化して architect に投げる (今回そうした)。予告だけで終わらせない。

5. **★ テストのしやすさのために本番の描画構造を歪めた (最大の反省)**
   - 何が課題か: build 14 で罫線ズレを直すとき、標準の `.frame(minWidth: 0, maxWidth: .infinity)` で足りたのに、**「等幅性を純関数としてテストで固定できるように」という理由で自作 `Layout` プロトコル実装を選んだ**。テストは緑になったが、`place(proposal:)` は幅を提案するだけで強制しないため実機の描画と当たり判定がズレ、Touri から「特殊な実装しないで欲しい。シンプルにカレンダーで実装すべき実装をして欲しい」と言われて build 15 で撤回した。
   - いつ起こるか: 「検証可能性」を設計の評価軸に入れたとき。純関数に切り出せる案が、標準部品を使う案より高く見える。
   - 次どうするか: **標準部品で足りる領域に自作実装を持ち込まない**。テストのしやすさは設計の目的ではなく副産物。7列等幅グリッドのような解決済みの問題は framework に任せ、テストは「framework が保証している前提が崩れていないか」を見る程度に留める。

6. **ユニットテストが緑のまま実機で死ぬ層が残っている**
   - 何が課題か: 実機FB 3ラウンドで出た不具合は**全件ユニット緑**だった。400 は「TS でテストを書く限り原理的に検出できない非対称」(Swift encoder のキー欠落)、罫線とタップ範囲は「レイアウトが実際にどう並ぶか」を誰も測っていなかった、タップ判定は「ジェスチャの競合」でテスト可能な層に現れない。
   - いつ起こるか: クライアントとサーバーで別言語のシリアライズ契約 / SwiftUI のレイアウトとジェスチャ。
   - 次どうするか: (a) request 契約は**実クライアントが吐いたバイト列を fixture にする** (今回 `swiftc` で生成した形を定着させる)。(b) レイアウトは `ImageRenderer` + `GeometryReader` でオフスクリーン実測できる (今回確立)。(c) **ジェスチャは実機でしか測れない**と割り切り、設計時に「実機ゲート項目」として明示的に切り出す。

7. **検証要求を積みすぎて成果が着地しなかった**
   - 何が課題か: build 15 の実装で検証条件を5つ課した結果、xcodebuild/XCUITest のサイクルを回り続けて**45分間コミットもビルド確認も出ない**状態を作り、Touri から3回「進んでる？」と聞かれた。原因が確定した後も再現フェーズを先に踏ませていたのも無駄。
   - いつ起こるか: 実機FBへの緊急対応で、品質を担保しようとして手順を足したとき。
   - 次どうするか: **緊急修正では「ビルドが通ったら一旦報告」を既定にする**。検証は Leader 側で追う。原因が確定している修正に再現フェーズを課さない。
   - 副産物: 進捗確認で**シンボリックリンクの mtime/size を見て「動いていない」と誤判定**した。エージェント出力は symlink なので実体を見る必要がある (role note 化済)。

8. **Codex が使えない期間の運用**
   - 何が課題か: `codex exec` が usage limit (〜8/3) で、しかも **exit 0 を返して何もしない**ことがある。developer が気付いたのは `git status` が空だったから。
   - 次どうするか: subagent の指示に最初から「codex が usage limit なら待たずに自力実装せよ」「exit 0 でも `git status` で確認せよ」と書く。memory 更新済。
