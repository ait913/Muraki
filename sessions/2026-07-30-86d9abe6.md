## 課題点

  - **次どうするか**: 生成物の出所を `.knowledge/` か `CLAUDE.md` の「外部リソース」に 1 行で書く。今回は設計doc §3.6 に原画の絶対パスが入ったので、次は doc から辿れる

- **subagent が API エラーで死ぬと自己申告が失われる**
  - **何が課題か**: P2〜P4 の developer が最終報告の書き出し中に落ち、実装は完走していたのに「設計と食い違った点」の申告がゼロになった。ここを失うと設計との整合を確かめる手段が Reviewer のテストだけになる
  - **いつ起こるか**: 長時間・大出力のエージェント (今回は 20 分超)
  - **次どうするか**: `SendMessage` で**再開して報告だけ回収できる** (今回成功)。その際「ファイルを変更するな」を明示する — 並列で別エージェントが同じ worktree にいるため。長い実装は「フェーズごとに中間報告を吐かせる」形も検討

- **未コミットの実装は「修正前の状態」を git から取り出せない**
  - **何が課題か**: レビュー指摘の修正が「効いた」ことを示すには修正前で赤くなる必要があるが、実装が未コミットだと上書きで消える。今回は Reviewer が召集時に tar バックアップを取っていたので実証できた
  - **いつ起こるか**: 「コミットするな」で走らせた developer の成果に修正を重ねるとき
  - **次どうするか**: レビュー前に**フェーズ完了時点でコミットさせる**か、Reviewer に tar 退避を義務化する (後者は `role/reviewer.md` に追記済)

- **subagent の実測値が 2 件ずれた**

  - **いつ起こるか**: 画像・レイアウトなど連続量を扱う調査
  - **次どうするか**: 数値を根拠に使う主張には**測定の定義を併記させる**。今回は結論が変わらなかったので受理したが、変わる場合はセカンドオピニオンに回す
