## 課題点

- 本番 DB のポート公開を「試して戻す」で 2 回やった
  - **何が課題か**: 1 回目で exited になった時点で「公開 restart は落ちる」と判断すべきだった。2 回目は別ポートの仮説検証で、本番 DB を再び落とした (実害は Coolify 表示上のみで API は生きていたが、判断としては軽率)
  - **いつ起こるか**: 本番の状態を変える操作を「戻せるから」と繰り返すとき
  - **次どうするか**: 本番の状態変更は 1 回失敗したら止めて代替 (今回なら backup API) を先に探す。knowledge に罠として記録済み

- ドメイン移動で審査中の /privacy に 4 分の穴を開けた
  - **何が課題か**: knowledge の `force_domain_override` 手順を実測せずに信じ、失敗レスポンス (HTML) を見ずに次の破壊ステップ (旧 app から外す) に進んだ
  - **いつ起こるか**: 複数ステップの破壊操作を 1 つの Bash に連結したとき
  - **次どうするか**: 破壊操作の前段の応答を JSON として検証してから次に進む (`python3 -c json.load` で落とす)。knowledge は置換済み

- Codex 生成のテストが限流の数値を hardcode していた
  - **何が課題か**: 数値を 1 つ変えるたびに 5 テストを手で追従。Codex は「調整可能に 1 箇所へ」と指示されても、テスト側は定数を直書きする
  - **いつ起こるか**: 初期値の運用調整が前提の設定 (限流・quota) を Codex にテストさせるとき
  - **次どうするか**: 召集時に「テストは `DefaultLimits().Policies[name].Burst` 等から数値を引く。リテラルを書くな」と明示する
- 限流の初期値はコード監査だけでは決まらない
  - **何が課題か**: 監査 doc の予算表はサーバー視点で妥当だったが、出荷済みクライアントの送信パターン (バースト・再試行なし) と突合していなかった。ゲートで Codex がクライアントコードまで読んで拾った
  - **いつ起こるか**: 既に配布済みのクライアントがある API に制限を入れるとき
  - **次どうするか**: 限流設計の入力に「クライアントの最大バースト実測 (コード grep)」を必須項目として設計 doc テンプレに入れる
- 3 レーン並列 → 共有 test DB で migration version が衝突
  - **何が課題か**: privacy レーンが 0006 を当てた後、edge レーンのテストが "no migration found for version 6" で起動不能
  - **いつ起こるか**: 同一 Postgres コンテナを複数 worktree で使い回し、片方だけ migration を足すとき
  - **次どうするか**: レーンごとに `docker compose down -v` してから回す (今回の対処)。恒久策は worktree ごとに別ポートのコンテナ (known-failures の P4 実績と同じ)
- 就寝前の認証確認が 1 往復では終わらなかった
  - **何が課題か**: 「ASC は API キー保存してるよ」= Web セッションが別物だと伝わっていなかった。chrome-login.sh も MCP ラッパーが profile を掴んでいて初回失敗
  - **いつ起こるか**: API と Web UI 両方が要る外部サービス (ASC の App Privacy)
  - **次どうするか**: 「API キー」と「ブラウザのログインセッション」を分けて、なぜ Web が要るか (App Privacy は API 非対応) を最初の依頼文に書く。pkill は Leader が先にやってから依頼する
