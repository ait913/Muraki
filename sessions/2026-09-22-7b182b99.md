## 課題点

- **Firebase project が二重に出来た**: 何が課題か = CLI 失敗 → Console で作ってもらう → CLI 再試行、の順で 2 つ目が出来た / いつ起こるか = 「ToS 同意だけしてもらう」つもりが Touri は作り切っていた (指示が「同意で閉じても作っても OK」と両論だった) / 次どうするか = 初回は「Console で作り切ってもらい CLI は list だけ」に一本化する
- **設計 doc の Codex レビューが 3 巡 (RED 7 → 4 → 5) 続いた**: 何が課題か = 2 巡目以降は doc 内のサンプルコードの整合性 (シグネチャ・期待値・戻り値型) の指摘で、設計判断ではない / いつ起こるか = Architect が実装例を doc に多く書くほど、例同士の不整合が生まれる / 次どうするか = Architect に「シグネチャは 1 箇所で宣言し他は参照」を最初から指示する。3 巡目で止めて Leader 目視に切り替えた判断は正しかった
- **設計の allowlist と負のコントロールが矛盾していた**: 何が課題か = §6-3a の route/host allowlist に dev 文字列を置けば prod バイナリに残る。Codex 3 巡でも検出されず、実バイナリの `strings` で初めて出た / いつ起こるか = 「prod から完全に取り外す」要件と「分類語彙にデータとして持つ」実装が同居するとき / 次どうするか = 負のコントロールは設計段階で「どの文字列がどの経路で残り得るか」まで列挙させる。実バイナリ測定は早めに 1 回入れる
- **Coolify の deployments 応答形と GET→POST 変更で 2 回分 (計 16 分) 空ポーリングした**: 何が課題か = `.[]` 前提の jq が object 応答で毎回失敗しても loop が回り続けた / 次どうするか = ポーリング前に 1 回だけ応答形を目視、jq エラーを `|| break` にする (knowledge に追記済)
- **同一 worktree で Developer (Codex) と Reviewer が並走し、Reviewer のステージ済ファイルが Leader のコミットに混入**: 実害なしだが、`git add <paths>` でも index に既にあるものは commit される / 次どうするか = 並走中のコミットは `git commit -- <paths>` にするか、Reviewer 完了まで待つ
