## 課題点

- Coolify の `scheduled-tasks execute` 裏技を忘れて entrypoint 改修に走った
  - **何が課題か**: `knowledge/tool-quirk/coolify-api.md` に「SSH なしでコンテナ内コマンドを実行する裏技」が既にあったのに、`/applications/{uuid}/execute` が 404 だった時点で「ssh 必須」と判断し、`entrypoint.sh` にバックアップ + 件数ログを足した。結果的に毎デプロイの自動バックアップになり有益だったが、knowledge を引かずに設計外の変更を増やした
  - **いつ起こるか**: Touri 不在で ssh (Cloudflare Access) が使えない時の本番 DB 操作
  - **次どうするか**: 本番コンテナを触る前に `grep -n "SSH なし" knowledge/tool-quirk/coolify-api.md`。バックアップの件数確認やファイル存在確認は scheduled-tasks execute で取れる
- 設計 doc の挙動仕様が既存インフラの挙動と食い違った (#X8 非 JSON → 400)
  - **何が課題か**: Architect が「zValidator は 400 を返す」と仮定して書き、Reviewer がテストで初めて 500 と判明 (全ルート共通の既存挙動)
  - **いつ起こるか**: 既存の共有ミドルウェアの境界挙動 (malformed body、巨大 body 等) を仕様に含める時
  - **次どうするか**: Architect はエラー系の挙動仕様に既存ルートでの実測 (`curl -d 'not json'`) を 1 本添える。Reviewer は食い違いを「設計の前提違い」と帰属して YELLOW にしたのは正しかった
- ssh aisaba のプローブが Touri の Mac でブラウザを開いた
  - **何が課題か**: `ssh -o BatchMode=yes` でも cloudflared が Access ログイン URL をブラウザで開こうとする (無人時に邪魔)
  - **いつ起こるか**: Cloudflare Access のセッションが切れている状態で ssh を叩いた時
  - **次どうするか**: 無人時は ssh を叩かず、まず Coolify API (logs / scheduled-tasks execute) で代替する
- Chrome のログイン手順で chrome-devtools MCP が落ちる (既知、2 回目)
  - **何が課題か**: `pkill` で MCP サーバーが切断され、以降そのセッションでは使えない。`ascweb.js` の puppeteer-core も Muraki に無く都度 install
  - **次どうするか**: knowledge に追記済 (chrome-for-testing.md)。恒久策は `scripts/` に `package.json` を置いて puppeteer-core を固定するか、ログインを別セッションでやる
