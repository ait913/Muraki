## 課題点

- テスト結果の判定とマージ / push を 1 コマンドに繋げた
  - **何が課題か**: wasawasa でテスト exit 1 を読む前に ff-merge → push が走り、webhook デプロイが始まった (キャンセルで無事)
  - **いつ起こるか**: 背景実行の長いテストの「完了通知」を受けて、結果確認と次の操作を 1 つの Bash にまとめた時
  - **次どうするか**: 判定が要る操作は「結果を出す」「読む」「進む」を別コマンドに分ける (memory `feedback_gate_before_merge`)
- ローカルの並列負荷でテストの hook がタイムアウトする
  - **何が課題か**: wasawasa の `p2-authz` (埋め込み Postgres + built server の beforeAll) が 120 秒を超えた。単独では 239/239 緑
  - **いつ起こるか**: atender のテスト + omatase の pnpm/turbo ビルドを同じ Mac で同時に走らせた時
  - **次どうするか**: 埋め込み DB を立てる系のテストは他の重い処理と重ねない。落ちたら「単独再実行」を最初の切り分けにする
- グローバル pnpm (9.15) と `packageManager` ピン (11.20) の取り違え
  - **何が課題か**: omatase の lockfile が 9 系の書式で書き換わった。PJ の CLAUDE.md には `corepack pnpm` と書いてあったのに script で素の `pnpm` を呼んだ
  - **いつ起こるか**: 複数 PJ を同じ script 雛形で回した時
  - **次どうするか**: pnpm 系は常に `corepack pnpm`。`CI=true` も付ける (TTY 無しの modules purge 確認で止まる)
- zsh の単語分割で for ループが空回り (2 回)
  - **何が課題か**: Coolify deployment uuid の 2 行変数と `set -- $pair` が分割されず、ポーリングが 10 分空回り
  - **いつ起こるか**: Bash ツールで bash 流のループを書いた時
  - **次どうするか**: `bash -c` で包む (knowledge `tool-quirk/bash-tool-zsh-no-word-splitting.md`)
- CI の deploy job が Coolify の API 変更 (GET → POST) で静かに壊れていた
  - **何が課題か**: omatase の Actions deploy が 405 で failure になっていたが、webhook が配備していたので気付かなかった
  - **いつ起こるか**: Coolify を上げた後の最初の main push
  - **次どうするか**: 修正済 (`62bf472`)。他 PJ の Actions / スクリプトに GET の `/deploy` が残っていないか次に触る時に確認 (kinketsu / omatase の CLAUDE.md は直した)
- docker.io → docker-ce の入替で docker.socket が止まり、dockerd が start-limit に入った
  - **何が課題か**: パッケージ入替で socket unit の定義が変わり「no open socket file descriptor left」の状態になる。dockerd は socket activation 前提なので 3 回失敗して止まる。apt の postinst は自動で直さない
  - **いつ起こるか**: 稼働中に Docker のパッケージ系統を入れ替えた時 (同系統の version up では起きない)
  - **次どうするか**: 入替直後に `systemctl reset-failed docker.socket docker; systemctl restart docker.socket docker` を手順に組み込む (スクリプトに追記済みではないので次回は手で)。再起動で消える問題なので、再起動が許される窓で入替えるのが楽
- bloom の dev 環境 1 本が別系列の migration で壊れていて dev ゲートが踏めなかった
  - **何が課題か**: dev1 の DB が next-features 系列 (0021 まで) + master の 0022 混入 + 0023 dirty で、どのブランチのビルドも healthcheck を通らない。10/20 から壊れていたが「retired のリリースが載った環境」なので誰も見ていなかった
  - **いつ起こるか**: 版を持たない検証ブランチ (`version/none/*`) を乗せた環境に、番号が衝突する migration を持つ別ブランチを一度でもデプロイした時
  - **次どうするか**: `version/none/*` を乗せる環境は DB を作り直す前提で扱う (devseed-reset)。wasawasa の env_status で `current_release.status=retired` の環境は棚卸し対象に入れる

## いい点

- 負のコントロールを機械的に回した
  - **何が良かったか**: meishilink / kinketsu / atender の既存失敗を「更新前の依存で同じか」を stash → install → test で確認し、依存更新の責任範囲を切り分けた
  - **いつ効いたか**: 台帳が無い PJ (meishilink / kinketsu) で、失敗を「時刻依存」「テスト陳腐化」に分類して台帳を新設できた
  - **どう続けるか**: 依存更新では必ず同じ手順。新規の失敗が出た時だけ深掘り
- 実機の実バージョンで判断した
  - **何が良かったか**: Dockerfile の tag だけでなく `docker exec node -v` / `/proc/<pid>/exe` の Go 版 / `pip freeze` / `psql version()` で稼働中の実体を取った。PostGIS 16.4 (2024 年) や Go 1.26.5 の 8 月ビルドはこれで見つかった
  - **いつ効いたか**: 「再ビルドだけで済む PJ」と「repo を変えないと直らない PJ」の仕分け
  - **どう続けるか**: 棚卸しは実機から。tag は信用しない
- Researcher に外部調査を切り出し、Leader は実機とローカル監査に専念した
  - **何が良かったか**: 10 系統の advisory 調査 (37 tool call) を並行させ、Leader 側は `pnpm audit` / `govulncheck` / `pip-audit` と SSH 実測を進めた
  - **いつ効いたか**: 報告が揃った時点で「要対応リスト」と「到達しない項目」を即座に突合できた
  - **どう続けるか**: 横断調査は Researcher、裏取りと実測は Leader の分担を保つ
- 削除前にデータを手元に退避した
  - **何が良かったか**: サービス終了 3 件は pg_dump / SQLite を `Muraki/.tmp/retired-20261022/` に取ってから `delete_volumes=true` で消した。サーバー上の一時ファイルは即削除
  - **いつ効いたか**: 削除が「元に戻せる操作」になった
  - **どう続けるか**: 終了・削除は必ず退避 → 削除 → 消滅確認の順
