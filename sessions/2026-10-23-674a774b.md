  - **何が課題か**: memory に「subagent は Sonnet 既定」が 2 回分あったのに Agent 呼び出しで `model` を省略した。省略 = 親モデル継承 = 最高コスト
  - **いつ起こるか**: セッション冒頭、要件整理から勢いで召集する時
  - **次どうするか**: memory に「Agent の model は毎回明示」を追記済。以降の 4 召集は全て明示した (Architect opus / Developer・Reviewer sonnet)
- Architect が 2 回 (初稿 315k + Codex 反映 392k) で 700k token
  - **何が課題か**: 1,500 行の設計 doc を opus で書き、Codex 11 件を折り返すとこの量になる。認証 IdP なので厚さ自体は妥当だが、Phase 1 の UI (§12) と開発フロー表 (§18) は sonnet でも書ける
  - **いつ起こるか**: 新規 PJ の Phase 1 設計
  - **次どうするか**: 設計 doc の骨格 (状態機械・ゲート・データモデル・挙動表) だけ opus、UI 具体化とフロー表は sonnet に分けて書かせる
- 実装の Codex はスライス 6 本で手直し 4 件。typecheck では拾えず、起動スモークで初めて出た (hook に id が届かない / `input: false` が profile を落とす / provider が空配列を拒否)
  - **何が課題か**: better-auth の plugin 境界の実行時挙動は型に出ない
  - **いつ起こるか**: better-auth の hook / additionalFields / oauth-provider を使う実装
  - **次どうするか**: Developer の停止条件に「起動 + 1 本の end-to-end スモーク」を入れたのが効いた。次回も必須にする

## いい点

- Codex のセカンドオピニオンを設計 doc 段階で入れた
  - **何が良かったか**: YELLOW 11 件のうち 2 件 (refresh のフォールバック / code 交換の失効ゲート欠落) は実装後に見つけると設計からやり直しになる類。read-only の `codex exec` 1 発 (Claude 側 token ほぼゼロ)
  - **いつ効いたか**: 認証・失効の状態機械を持つ設計
  - **どう続けるか**: 認証・課金・データ削除に触る設計は承認ゲート前に Codex 突合を既定にする。否定的主張は doc 本文で裏取りしてから Architect に戻す (今回 2 件を Leader が確認)
- Reviewer の優先順位を「2FA 未完了 / 許可表 / 失効ゲート / 招待 / TOTP / 最後の owner」と明示した
  - **何が良かったか**: 284 本中、優先 1 が全通過で失敗は管理画面に集中 → YELLOW 判定が迷わず出た。Developer が疑った 2 点を負のテストに回したら 1 件 (client PATCH 500) が実装バグとして確定
  - **いつ効いたか**: 設計 doc の挙動表が 100 行超の時
  - **どう続けるか**: Reviewer ブリーフに「優先 1 の行 id」と「Developer の疑い」を必ず入れる
- subagent の再開 (SendMessage) で修正往復
  - **何が良かったか**: Architect の Codex 反映と Reviewer のテスト修正は文脈キャッシュ付きで再開でき、新規召集より安い。Reviewer 再開は 15 tool call で完了
  - **どう続けるか**: 同じ成果物の修正は新規召集でなく再開
